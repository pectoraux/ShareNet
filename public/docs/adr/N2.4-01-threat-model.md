# N2.4-01 — Threat Model

**Status:** DRAFT (REVISED) — awaiting review

**Parent:** N2.4-00 Protocol Evolution Charter (approved)

**Baseline:** N2.3 frozen @ `425eccb` (tag: `v2.3.0-protocol`)

---

## 1. Scope

This threat model covers the N2.4 design space: the additional distributed
networking capabilities introduced after the N2.3 freeze. It covers threats
from the circuit boundary outward — gateway operation, route recovery,
transport independence, mobile node lifecycle, and capability negotiation.

Threats already mitigated by N2.3 (replay, TTL tampering, nonce reuse,
sequence exhaustion, predecessor substitution, destination substitution,
circuit expiry) are assumed closed and are referenced, not re-analyzed.

---

## 2. Security Assumptions

### Assumed secure (N2.3 frozen invariants)

- Ed25519 signature security (identity binding)
- X25519 DH key agreement (forwarding key derivation)
- ChaCha20-Poly1305 AEAD (per-hop confidentiality + integrity)
- SHA-256 collision resistance (commitment hashes, authorization roots)
- Canonical CBOR encoding (deterministic, cross-implementation)
- Circuit-owned sequence allocation (no nonce reuse)
- Per-hop TTL authentication (no forwarding loop injection)
- Circuit expiration (bounded lifetime)
- Profile dispatch (explicit version, no downgrade via AEAD failure)

### Assumed insecure

- Network transport (TCP/UDP/QUIC/BLE): subject to eavesdropping,
  modification, injection, delay, reordering, dropping
- Node identity-to-network-address binding: mutable (IP changes, NAT)
- Peer timing: unreliable (clocks drift, messages delayed)
- Storage: ephemeral (devices sleep, reboot, lose state)

## 3. Assets

| Asset | Protected by | Compromise impact |
|-------|--------------|-------------------|
| User plaintext (application traffic) | Per-hop AEAD + onion encryption | Privacy loss, content exposure |
| Circuit forwarding keys | X25519 DH + HKDF derivation | Relay can decrypt transit traffic |
| Node Ed25519 private key | OS key storage | Identity theft, impersonation |
| Circuit identity (circuit_id) | Random generation + cryptographic binding | Traffic correlation, replay |
| Route topology | CommittedRoute signatures | Topology leak, route manipulation |
| Gateway policy | (N2.4 — to be defined) | Exit abuse, censorship |
| Node capabilities | (N2.4 — to be defined) | Capability spoofing |
| Relay availability state | (N2.4 — to be defined) | Route disruption, DoS |

## 4. Actors

### 4.1 Source (circuit initiator)

- Creates circuits, sends forward traffic.
- Owns the forward sequence allocator.
- May receive reverse traffic (N2.4).
- Holds Ed25519 identity key + ephemeral X25519 secret.

### 4.2 Relay (transit node)

- Accepts circuit handshakes, installs forwarding state.
- Forwards packets (peels for forward, adds for reverse).
- Holds X25519 circuit private key + forwarding state.
- May be malicious (colludes, drops, reorders, inspects).

### 4.3 Gateway (terminal node)

- Receives forward traffic, delivers plaintext locally.
- May originate reverse traffic (N2.4).
- May provide Internet egress (N2.4 — if capability advertised).
- Holds X25519 circuit private key + terminal forwarding state.

### 4.4 Internet destination (outside ShareNet)

- Not a ShareNet participant.
- Reached only through a gateway's Internet egress (N2.4).
- Cannot authenticate ShareNet-internal traffic.

### 4.5 Adversary

- On-path network observer (can read/modify/inject/delay/drop).
- Malicious relay (has valid forwarding state, may deviate from protocol).
- Malicious gateway (may inspect, modify, or censor Internet traffic).
- Sybil attacker (creates many node identities to influence routing).
- Network adversary (controls transport, can partition, replay, inject).

## 5. Threat Categories

### 5.1 Malicious Relay

**Threat:** A relay with valid forwarding state deviates from the protocol.

| Attack | Mitigated by | Residual risk |
|--------|-------------|---------------|
| Drop packets | End-to-end detection (N2.4 recovery) | Cannot prevent; can detect + reroute |
| Reorder packets | Per-direction sequence + replay window | Bounded by window size |
| Selective degradation | Quality monitoring (N2.4) | Hard to distinguish from network loss |
| Inspect payload | Onion AEAD (relay sees only ciphertext) | Payload confidentiality protected; metadata + traffic analysis remain risks |
| Substitute successor | Successor from installed state, not packet | None (state-bound) |
| Tamper TTL | Per-hop TTL authentication in AAD | None (AEAD fails) |
| Replay old packets | check-before-AEAD, commit-after-AEAD | None (replay window rejects) |
| Forge forwarding state | SignedHopAuthorization (source-signed) | None (signature verification) |
| Collude with another relay | Each relay has independent key; collusion reveals only colluding hops' layers | Non-colluding hops remain protected; colluding successive relays can correlate |
| Lie about capabilities | (N2.4) Explicit capability advertisement + authentication | Gateway/relay capability must be verifiable |

**Refined confidentiality statement:**

```
Cryptographic payload confidentiality against a non-colluding relay
    ✅ PROTECTED (onion AEAD)

Metadata confidentiality (packet size, timing, count)
    ❌ NOT PROTECTED

Traffic analysis resistance
    ❌ NOT PROTECTED

Confidentiality against colluding relays possessing successive layers
    ❌ NOT PROTECTED (colluding endpoints can correlate)
```

### 5.2 Malicious Gateway

**Threat:** The terminal gateway (Internet egress) is malicious.

This is a **new threat class** introduced by N2.4 Internet gateway operation.

| Attack | Mitigated by | Residual risk |
|--------|-------------|---------------|
| Observe destination/connection metadata | Inherent (terminal hop) | Gateway sees destination IP/hostname, connection timing, traffic volume |
| Inspect unencrypted application plaintext | Inherent (terminal hop delivers ShareNet payload) | Gateway sees plaintext for unencrypted application protocols |
| Decrypt TLS-protected traffic | Cannot (TLS is end-to-end user → destination) | Gateway cannot decrypt correctly implemented HTTPS unless user voluntarily terminates TLS at gateway |
| Modify Internet responses | (N2.4) Response integrity must be defined | Gateway can alter responses before they enter ShareNet |
| Censor destinations | (N2.4) Exit policy must be transparent | Gateway can refuse to connect to certain destinations |
| Impersonate services | TLS end-to-end (user → destination) is out of ShareNet scope | Gateway can MITM if user doesn't verify TLS |
| Traffic correlation | (N2.4) Gateway sees both ShareNet ingress + Internet egress | Timing correlation possible |
| Abuse user traffic | (N2.4) Policy + auditing | Gateway can inject ads, tracking, etc. |

**Key architectural decision required:**
- Does the gateway see ShareNet payload? (Yes — terminal hop by design)
- Is TLS end-to-end enforced? (Should be recommended, not protocol-enforced)
- Is gateway policy authenticated? (Should be — signed policy hashes)

**Refined gateway visibility statement:**

```
Gateway can observe:
    - destination/connection metadata (IP, hostname, port, timing, volume)
    - plaintext for unencrypted application protocols

Gateway cannot decrypt:
    - correctly implemented end-to-end encrypted applications
      (e.g. HTTPS with valid TLS certificate verification)
    unless the user/application voluntarily terminates encryption at the gateway
```

### 5.3 Sybil Nodes

**Threat:** An attacker creates many node identities to influence routing,
discovery, reputation, or resource allocation.

**Critical distinction:** Ed25519 identity establishes cryptographic identity
uniqueness — "this is really Node A873." It does NOT establish Sybil
resistance — "Node A873 represents an independent trustworthy participant."

A Sybil attacker can generate valid Ed25519 keys for every fake node. Each
identity is cryptographically valid and can sign advertisements and route
acceptances.

| Attack | Mitigated by | Status |
|--------|-------------|--------|
| Sybil identity creation | Ed25519 signatures (N2.3) | ✅ Cryptographically valid (but not Sybil-resistant) |
| Sybil route influence | Signed acceptances prevent forgery, but do not prevent malicious authenticated participation | 🔲 OPEN |
| Sybil reputation gaming | (N2.4) Reputation system TBD | 🔲 OPEN |
| Sybil resource exhaustion | (N2.4) Admission control + quotas | 🔲 OPEN |
| Sybil discovery flooding | N2.1.1: RemoteNodeHint is non-authoritative | PARTIALLY MITIGATED (hints are diagnostic, not routing) |

**Key architectural decision required:**
- Is there a Sybil resistance mechanism (proof-of-work, stake, invite)?
- Or is the network permissioned/curated?
- N2.4-02 Capability System MUST depend on the outcome of this decision.

### 5.4 Route Manipulation

**Threat:** An attacker manipulates routing decisions.

**Critical distinction:** Signed route acceptances prevent route **forgery**
(a fake route that no relay agreed to). They do NOT prevent **malicious
authenticated participation** — a set of authenticated malicious nodes can
legitimately sign acceptances for a bad route.

| Attack | Mitigated by | Status |
|--------|-------------|--------|
| Route forgery (fake route no relay agreed to) | CommittedRoute signed acceptances | ✅ CLOSED |
| Malicious authenticated route (all relays are real but malicious) | None — signatures are valid | 🔲 OPEN (inherent risk) |
| Fake gateway availability | (N2.4) Gateway capability must be authenticated | 🔲 OPEN |
| Topology poisoning | N2.1.1: RemoteNodeHint is non-authoritative | PARTIALLY MITIGATED |
| Stale advertisements | (N2.4) Capability advertisement needs freshness | 🔲 OPEN |

**Refined route security statement:**

```
Cryptographic route integrity (no forgery)
    ✅ PROTECTED (signed acceptances)

Route quality / honesty / availability
    ❌ NOT PROTECTED (signatures don't guarantee good behavior)

Sybil resistance
    ❌ NOT PROTECTED (open question for N2.4-02)
```

### 5.5 Capability/Authorization Abuse

**NEW threat category.** Because N2.4 introduces explicit capabilities, an
attacker may present capabilities they do not actually provide or are not
authorized to provide.

| Attack | Mitigated by | Status |
|--------|-------------|--------|
| Fake capability advertisement ("I am INTERNET_GATEWAY") | (N2.4) Capability authentication | 🔲 OPEN |
| Capability without authorization (has the key but not the policy) | (N2.4) Authorization model | 🔲 OPEN |
| Capability policy violation (advertises unlimited, enforces limited) | (N2.4) Policy verification | 🔲 OPEN |
| Capability downgrade (forces lower-quality gateway) | (N2.4) User choice + capability negotiation | 🔲 OPEN |
| Observed capability spoofing (claims bandwidth it doesn't have) | (N2.4) Resource verification | 🔲 OPEN |

**Key distinctions:**

```
Identity authentication     = "who are you?"        (N2.3: Ed25519)
Capability authentication   = "what can you do?"    (N2.4: signed capability)
Capability authorization    = "are you allowed?"    (N2.4: policy/permission)
Capability policy           = "what are the rules?" (N2.4: exit policy)
Observed capability         = "what did you do?"   (N2.4: monitoring)
```

### 5.6 Availability Attacks

**Threat:** Denial-of-service against the mesh.

| Attack | Mitigated by | Status |
|--------|-------------|--------|
| Circuit flooding | (N2.4) Per-relay admission control | 🔲 OPEN |
| Relay resource exhaustion | (N2.4) Quotas: max circuits per relay | 🔲 OPEN |
| Connection churn | (N2.4) Rate limiting on circuit establishment | 🔲 OPEN |
| Storage abuse | (N2.4) Bounded replay window + expiry | PARTIALLY MITIGATED (N2.3 has expiry) |
| Packet amplification | TTL limits forwarding depth (max ROUTE_MAX_HOPS) | ✅ CLOSED |

### 5.7 Privacy Threats

**Threat:** An observer infers user identity, destination, or traffic patterns.

| Attack | Mitigated by | Status |
|--------|-------------|--------|
| Source identification | Onion encryption (relay sees only predecessor) | PARTIALLY MITIGATED (first relay knows source) |
| Destination identification | Gateway sees destination + connection metadata | 🔲 INHERENT RISK |
| Traffic correlation | (N2.4) Padding + timing obfuscation TBD | 🔲 OPEN |
| Node ownership inference | (N2.4) Node identity is Ed25519, not IP | PARTIALLY MITIGATED |
| Circuit fingerprinting | (N2.4) Uniform packet sizing TBD | 🔲 OPEN |

### 5.8 Mobile Threats

**Threat:** Mobile node behavior disrupts protocol assumptions.

| Attack | Mitigated by | Status |
|--------|-------------|--------|
| IP change mid-circuit | (N2.4) Circuit is identity-bound, not IP-bound | 🔲 OPEN |
| NAT rebinding | (N2.4) Reconnection logic TBD | 🔲 OPEN |
| Sleep/wake cycle | (N2.4) Circuit expiry + re-establishment | PARTIALLY MITIGATED (expiry is correct behavior) |
| Intermittent connectivity | (N2.4) Heartbeat/liveness TBD | 🔲 OPEN |

### 5.9 Economic / Incentive Threats

**Threat:** Economic incentives compromise protocol security.

| Attack | Mitigated by | Status |
|--------|-------------|--------|
| Routing for profit (relay drops low-paying circuits) | Protocol correctness ≠ economic reward | ⚠️ DESIGN CONSTRAINT |
| Gateway monopoly | (N2.4) Multiple gateways + user choice | 🔲 OPEN |
| Bribery (relay paid to inspect/collude) | Onion encryption (relay can't inspect) | PARTIALLY MITIGATED (collusion with gateway still possible) |

**Key architectural principle:**
> Protocol correctness MUST NOT depend on economic incentives.
> Rewards MUST NOT influence routing security decisions unless formally designed.

## 6. Attack Scenarios

### Scenario A — Malicious relay + gateway collusion

```
A → B(malicious) → G(malicious) → Internet

B and G share their forwarding keys.
B reveals layer_B (but not inner layers — it can't peel further).
G sees destination metadata + plaintext (for unencrypted protocols).
Together: B + G can correlate timing, source, destination.
```

**Residual risk:** Cannot prevent collusion at the endpoints. Mitigation:
multiple disjoint circuits, route diversity, traffic padding.

### Scenario B — Gateway MITM

```
User → ShareNet → Gateway → "google.com"

Gateway intercepts TLS, presents fake certificate.
```

**Mitigation:** TLS is end-to-end (user → destination). The gateway is a
transport relay, not a TLS terminator. User's TLS stack must verify the
destination's certificate, not the gateway's. **ShareNet does not provide
TLS termination.** If the user delegates TLS to the gateway, that is an
application-layer decision outside ShareNet's protocol boundary.

### Scenario C — Sleep/wake circuit break

```
Mobile node A establishes circuit A → B → C → G.
A goes to sleep for 2 hours.
Circuit expires.
A wakes up.
Circuit is gone.
```

**Mitigation (N2.4):** Detect expiry on wake, re-establish circuit.
The circuit_id changes (new handshake). The sequence namespace is fresh.
No stale state. This is the correct behavior — circuits are bounded.

### Scenario D — Sybil route flooding

```
Attacker creates 10,000 fake nodes with valid Ed25519 keys.
Floods discovery with valid advertisements.
Tries to route traffic through Sybil relays.
```

**Mitigation (N2.3):** Each fake node has a valid identity. Signed
acceptances prevent route forgery (a fake route no relay agreed to), but
do NOT prevent Sybil nodes from legitimately participating in routes.
The topology layer (N2.1.1) separates RemoteNodeHint (non-authoritative)
from AuthenticatedNodeRecord (authoritative) — but an authenticated
Sybil node can produce a valid AuthenticatedNodeRecord.

**Sybil resistance is OPEN.** N2.4-02 Capability System MUST address
this: either permissioned/curated admission, proof-of-work, stake,
or explicit acceptance of the Sybil risk with mitigations.

### Scenario E — Transport replay across circuits

```
Attacker captures a packet from circuit 1.
Injects it into circuit 2.
```

**Mitigation (N2.3):** The AAD binds circuit_id. The relay's forwarding
state is keyed by circuit_id. A packet from circuit 1 has circuit_1's
circuit_id; circuit 2's relay state lookup misses → UnknownCircuit. Even
if the circuit_id matched (same circuit), the replay window rejects
duplicate seq.

### Scenario F — Capability spoofing

```
Attacker advertises: "I am INTERNET_GATEWAY, I allow all destinations."
User selects this gateway.
Gateway censors, logs, or modifies traffic.
```

**Mitigation (N2.4):** Capability must be authenticated (signed). Policy
must be transparent (signed policy hash). User consent must be explicit.
But: an authenticated malicious gateway can still violate its own
advertised policy. Mitigation: reputation, auditing, multi-gateway choice.

## 8. Residual Risks

1. **Gateway sees destination metadata + unencrypted plaintext** — inherent
   in the terminal-hop design. Gateway can observe destination, timing,
   volume, and plaintext for non-TLS protocols. Mitigation: end-to-end TLS
   (application layer). ShareNet does not provide TLS termination.

2. **First relay knows source** — inherent in forward routing. The source
   sends directly to the first relay. Mitigation: entry-guard model (TBD).

3. **Timing correlation** — an on-path observer who sees both the source's
   ingress and the gateway's egress can correlate timing. Mitigation:
   padding + timing obfuscation (N2.4, if required).

4. **Collusion at endpoints** — if the first relay and the gateway collude,
   they can deanonymize the user. Mitigation: route diversity, multiple
   circuits, trust model (TBD).

5. **Transport-level identification** — if the transport (TCP) is
   fingerprintable, an observer can correlate circuits across transport
   sessions. Mitigation: transport multiplexing (N2.4).

6. **Malicious authenticated participation** — authenticated nodes can
   legitimately sign route acceptances while being malicious. Signatures
   prevent forgery, not dishonesty. Mitigation: reputation, diversity,
   detection (N2.4).

7. **Sybil identities** — Ed25519 provides identity uniqueness but not
   Sybil resistance. An attacker can create unlimited valid identities.
   Mitigation: admission control, proof-of-work/stake/invite (N2.4-02).

## 9. Non-Goals

This threat model does NOT address:

- Application-layer security (TLS, DNSSEC, etc.) — ShareNet provides
  transport, not application security.
- Economic model design — Civic Points, rewards, payments are separate.
- Censorship of the ShareNet protocol itself (transport-layer blocking).
- Physical security of devices (compromised private keys).
- Quantum computing threats (post-quantum migration is a future concern).
- Legal/regulatory compliance.
