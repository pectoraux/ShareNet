# N2.4-01 — Threat Model

**Status:** DRAFT — awaiting review

**Parent:** N2.4-00 Protocol Evolution Charter (approved)

**Baseline:** N2.3 frozen @ `425eccb` (tag: `v2.3.0-protocol`)

---

## 1. Scope

This threat model covers the N2.4 design space: the additional distributed
networking capabilities introduced after the N2.3 freeze. It covers threats
from the circuit boundary outward — gateway operation, route recovery,
transport independence, mobile node lifecycle, and capability negotiation.

Threats already mitigated by N2.3 (replay, TTL tampering, nonce reuse,
sequence exhaustion, predecessor substitution, destination substitution,
circuit expiry) are assumed closed and are referenced, not re-analyzed.

---

## 2. Security Assumptions

### Assumed secure (N2.3 frozen invariants)

- Ed25519 signature security (identity binding)
- X25519 DH key agreement (forwarding key derivation)
- ChaCha20-Poly1305 AEAD (per-hop confidentiality + integrity)
- SHA-256 collision resistance (commitment hashes, authorization roots)
- Canonical CBOR encoding (deterministic, cross-implementation)
- Circuit-owned sequence allocation (no nonce reuse)
- Per-hop TTL authentication (no forwarding loop injection)
- Circuit expiration (bounded lifetime)
- Profile dispatch (explicit version, no downgrade via AEAD failure)

### Assumed insecure

- Network transport (TCP/UDP/QUIC/BLE): subject to eavesdropping,
  modification, injection, delay, reordering, dropping
- Node identity-to-network-address binding: mutable (IP changes, NAT)
- Peer timing: unreliable (clocks drift, messages delayed)
- Storage: ephemeral (devices sleep, reboot, lose state)

## 3. Assets

| Asset | Protected by | Compromise impact |
|-------|--------------|-------------------|
| User plaintext (application traffic) | Per-hop AEAD + onion encryption | Privacy loss, content exposure |
| Circuit forwarding keys | X25519 DH + HKDF derivation | Relay can decrypt transit traffic |
| Node Ed25519 private key | OS key storage | Identity theft, impersonation |
| Circuit identity (circuit_id) | Random generation + cryptographic binding | Traffic correlation, replay |
| Route topology | CommittedRoute signatures | Topology leak, route manipulation |
| Gateway policy | (N2.4 — to be defined) | Exit abuse, censorship |
| Node capabilities | (N2.4 — to be defined) | Capability spoofing |
| Relay availability state | (N2.4 — to be defined) | Route disruption, DoS |

## 4. Actors

### 4.1 Source (circuit initiator)

- Creates circuits, sends forward traffic.
- Owns the forward sequence allocator.
- May receive reverse traffic (N2.4).
- Holds Ed25519 identity key + ephemeral X25519 secret.

### 4.2 Relay (transit node)

- Accepts circuit handshakes, installs forwarding state.
- Forwards packets (peels for forward, adds for reverse).
- Holds X25519 circuit private key + forwarding state.
- May be malicious (colludes, drops, reorders, inspects).

### 4.3 Gateway (terminal node)

- Receives forward traffic, delivers plaintext locally.
- May originate reverse traffic (N2.4).
- May provide Internet egress (N2.4 — if capability advertised).
- Holds X25519 circuit private key + terminal forwarding state.

### 4.4 Internet destination (outside ShareNet)

- Not a ShareNet participant.
- Reached only through a gateway's Internet egress (N2.4).
- Cannot authenticate ShareNet-internal traffic.

### 4.5 Adversary

- On-path network observer (can read/modify/inject/delay/drop).
- Malicious relay (has valid forwarding state, may deviate from protocol).
- Malicious gateway (may inspect, modify, or censor Internet traffic).
- Sybil attacker (creates many node identities to influence routing).
- Network adversary (controls transport, can partition, replay, inject).

## 5. Threat Categories

### 5.1 Malicious Relay

**Threat:** A relay with valid forwarding state deviates from the protocol.

| Attack | Mitigated by | Residual risk |
|--------|-------------|---------------|
| Drop packets | End-to-end detection (N2.4 recovery) | Cannot prevent; can detect + reroute |
| Reorder packets | Per-direction sequence + replay window | Bounded by window size |
| Selective degradation | Quality monitoring (N2.4) | Hard to distinguish from network loss |
| Inspect payload | Onion AEAD (relay sees only ciphertext) | None (cryptographically protected) |
| Substitute successor | Successor from installed state, not packet | None (state-bound) |
| Tamper TTL | Per-hop TTL authentication in AAD | None (AEAD fails) |
| Replay old packets | check-before-AEAD, commit-after-AEAD | None (replay window rejects) |
| Forge forwarding state | SignedHopAuthorization (source-signed) | None (signature verification) |
| Collude with another relay | Each relay has independent key; collusion reveals only colluding hops' layers | Non-colluding hops remain protected |
| Lie about capabilities | (N2.4) Explicit capability advertisement + authentication | Gateway/relay capability must be verifiable |

### 5.2 Malicious Gateway

**Threat:** The terminal gateway (Internet egress) is malicious.

This is a **new threat class** introduced by N2.4 Internet gateway operation.

| Attack | Mitigated by | Residual risk |
|--------|-------------|---------------|
| Inspect user plaintext | Gateway MUST receive plaintext (terminal hop) | **Inherent** — gateway sees destination + content |
| Modify Internet responses | (N2.4) Response integrity must be defined | Gateway can alter responses before they enter ShareNet |
| Censor destinations | (N2.4) Exit policy must be transparent | Gateway can refuse to connect to certain destinations |
| Impersonate services | (N2.4) TLS end-to-end (user → destination) is out of ShareNet scope | Gateway can MITM if user doesn't verify TLS |
| Traffic correlation | (N2.4) Gateway sees both ShareNet ingress + Internet egress | Timing correlation possible |
| Abuse user traffic | (N2.4) Policy + auditing | Gateway can inject ads, tracking, etc. |

**Key architectural decision required:**
- Does the gateway see plaintext? (Yes — terminal hop by design)
- Is TLS end-to-end enforced? (Should be recommended, not protocol-enforced)
- Is gateway policy authenticated? (Should be — signed policy hash)

### 5.3 Sybil Nodes

**Threat:** An attacker creates many node identities to influence routing,
discovery, reputation, or resource allocation.

| Attack | Mitigated by | Residual risk |
|--------|-------------|---------------|
| Route influence (many fake relays) | (N2.4) Route requires signed acceptances from authenticated nodes | Fake nodes can't sign valid acceptances without real keys |
| Discovery poisoning | N2.1.1 topology: RemoteNodeHint ≠ AuthenticatedNodeRecord | Unauthenticated hints are marked as non-authoritative |
| Reputation gaming | (N2.4) Reputation system TBD | If reputation exists, Sybil resistance needed |
| Resource exhaustion | (N2.4) Admission control + quotas | Without quotas, fake nodes can exhaust circuit slots |

**Key architectural decision required:**
- Is there a Sybil resistance mechanism (proof-of-work, stake, invite)?
- Or is the network permissioned/curated?

### 5.4 Route Manipulation

**Threat:** An attacker manipulates routing decisions.

| Attack | Mitigated by | Residual risk |
|--------|-------------|---------------|
| Fake shortest path | CommittedRoute requires signed acceptances | Cannot forge without real keys |
| Fake gateway availability | (N2.4) Gateway capability must be authenticated | Fake "I am a gateway" advertisement possible without auth |
| Topology poisoning | N2.1.1: RemoteNodeHint is non-authoritative | Hints are diagnostic, not routing |
| Stale advertisements | (N2.4) Capability advertisement needs freshness | Stale "gateway is up" can misdirect |

### 5.5 Availability Attacks

**Threat:** Denial-of-service against the mesh.

| Attack | Mitigated by | Residual risk |
|--------|-------------|---------------|
| Circuit flooding | (N2.4) Per-relay admission control | Without limits, relay memory exhausts |
| Relay resource exhaustion | (N2.4) Quotas: max circuits per relay | Attacker can exhaust until quota |
| Connection churn | (N2.4) Rate limiting on circuit establishment | Rapid create/teardown cycles |
| Storage abuse | (N2.4) Bounded replay window + expiry | Unbounded state if no expiry |
| Packet amplification | TTL limits forwarding depth (max ROUTE_MAX_HOPS) | Bounded by TTL |

### 5.6 Privacy Threats

**Threat:** An observer infers user identity, destination, or traffic patterns.

| Attack | Mitigated by | Residual risk |
|--------|-------------|---------------|
| Source identification | Onion encryption (relay sees only predecessor) | First relay knows source |
| Destination identification | Gateway sees plaintext + destination | Gateway knows destination |
| Traffic correlation | (N2.4) Padding + timing obfuscation TBD | Timing analysis possible |
| Node ownership inference | (N2.4) Node identity is Ed25519, not IP | IP changes don't break identity |
| Circuit fingerprinting | (N2.4) Uniform packet sizing TBD | Packet size leaks information |

**Key architectural decision required:**
- Is traffic analysis resistance a protocol requirement or an application concern?
- Should packets be padded to a uniform size?

### 5.7 Mobile Threats

**Threat:** Mobile node behavior disrupts protocol assumptions.

| Attack | Mitigated by | Residual risk |
|--------|-------------|---------------|
| IP change mid-circuit | (N2.4) Circuit is identity-bound, not IP-bound | Transport connection breaks; recovery needed |
| NAT rebinding | (N2.4) Reconnection logic TBD | Existing transport sessions break |
| Sleep/wake cycle | (N2.4) Circuit expiry + re-establishment | Circuit may expire during sleep |
| Intermittent connectivity | (N2.4) Heartbeat/liveness TBD | Relay can't distinguish sleep from departure |

### 5.8 Economic / Incentive Threats

**Threat:** Economic incentives compromise protocol security.

| Attack | Mitigated by | Residual risk |
|--------|-------------|---------------|
| Routing for profit (relay prefers high-paying circuits) | (N2.4) Protocol correctness ≠ economic reward | Relay can drop low-paying circuits |
| Gateway monopoly | (N2.4) Multiple gateways + user choice | If only one gateway, no alternatives |
| Bribery (relay paid to inspect) | Onion encryption (relay can't inspect) | Collusion with gateway reveals plaintext |

**Key architectural principle:**
> Protocol correctness MUST NOT depend on economic incentives.
> Rewards MUST NOT influence routing security decisions unless formally designed.

## 6. Attack Scenarios

### Scenario A — Malicious relay + gateway collusion

```
A → B(malicious) → G(malicious) → Internet

B and G share their forwarding keys.
B reveals layer_B (but not inner layers — it can't peel further).
G sees plaintext + destination.
Together: B + G can correlate timing, source, destination.
```

**Residual risk:** Cannot prevent collusion at the endpoints. Mitigation:
multiple disjoint circuits, route diversity, traffic padding.

### Scenario B — Gateway MITM

```
User → ShareNet → Gateway → "google.com"

Gateway intercepts TLS, presents fake certificate.
```

**Mitigation:** TLS is end-to-end (user → destination). The gateway is a
transport relay, not a TLS terminator. User's TLS stack must verify the
destination's certificate, not the gateway's. **ShareNet does not provide
TLS termination.** If the user delegates TLS to the gateway, that is an
application-layer decision outside ShareNet's protocol boundary.

### Scenario C — Sleep/wake circuit break

```
Mobile node A establishes circuit A → B → C → G.
A goes to sleep for 2 hours.
Circuit expires.
A wakes up.
Circuit is gone.
```

**Mitigation (N2.4):** Detect expiry on wake, re-establish circuit.
The circuit_id changes (new handshake). The sequence namespace is fresh.
No stale state. This is the correct behavior — circuits are bounded.

### Scenario D — Sybil route flooding

```
Attacker creates 10,000 fake nodes.
Floods discovery with fake advertisements.
Tries to route traffic through fake relays.
```

**Mitigation (N2.3):** Route requires signed acceptances from authenticated
nodes. Fake nodes without real Ed25519 keys cannot sign valid acceptances.
The topology layer (N2.1.1) already separates RemoteNodeHint (non-authoritative)
from AuthenticatedNodeRecord (authoritative).

### Scenario E — Transport replay across circuits

```
Attacker captures a packet from circuit 1.
Injects it into circuit 2.
```

**Mitigation (N2.3):** The AAD binds circuit_id. The relay's forwarding
state is keyed by circuit_id. A packet from circuit 1 has circuit_1's
circuit_id; circuit 2's relay state lookup misses → UnknownCircuit. Even
if the circuit_id matched (same circuit), the replay window rejects
duplicate seq.

## 8. Residual Risks

1. **Gateway sees plaintext** — inherent in the circuit model. The gateway
   is the terminal hop. Mitigation: end-to-end TLS (application layer).

2. **First relay knows source** — inherent in forward routing. The source
   sends directly to the first relay. Mitigation: entry-guard model (TBD).

3. **Timing correlation** — an on-path observer who sees both the source's
   ingress and the gateway's egress can correlate timing. Mitigation:
   padding + timing obfuscation (N2.4, if required).

4. **Collusion at endpoints** — if the first relay and the gateway collude,
   they can deanonymize the user. Mitigation: route diversity, multiple
   circuits, trust model (TBD).

5. **Transport-level identification** — if the transport (TCP) is
   fingerprintable, an observer can correlate circuits across transport
   sessions. Mitigation: transport multiplexing (N2.4).

---

## 9. Non-Goals

This threat model does NOT address:

- Application-layer security (TLS, DNSSEC, etc.) — ShareNet provides
  transport, not application security.
- Economic model design — Civic Points, rewards, payments are separate.
- Censorship of the ShareNet protocol itself (transport-layer blocking).
- Physical security of devices (compromised private keys).
- Quantum computing threats (post-quantum migration is a future concern).
- Legal/regulatory compliance.
