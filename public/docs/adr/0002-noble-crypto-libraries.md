# ADR-0002 — @noble libraries for Ed25519 / X25519 / SHA-256 / HKDF

## Context

`00-AUDIT.md §3.1` ("BROKEN — `TinkCryptoProvider` is
non-functional") documents the central crypto failure of the audited
repository:

> `TinkCryptoProvider` derives "public keys" as
> `sha256(handle.toString())` because Tink's raw key import is not
> public API. … No signature produced on one device can be verified on
> another, anywhere in ShareNet, today.

The audit's recommendation (§3.1, restated in
`02-PROTOCOL-SPEC.md §1.2`) is:

> Every implementation must interoperate on **raw 32-byte Ed25519
> keys**. Use libsodium, BoringSSL, `ed25519-dalek`, or JCA `Ed25519`
> (Android API 33+) / BouncyCastle below that. Tink MAY be used
> internally only if raw keys round-trip byte-exactly.

This sandbox runs Next.js 16 + TypeScript (see ADR-0001). The available
Ed25519/X25519/SHA-256/HKDF options in npm are:

- `@noble/ed25519` — pure-TypeScript Ed25519, audited (Trail of Bits,
  2022), no native bindings, raw 32-byte keys by API contract.
- `@noble/curves` — Ed25519 + X25519 + more, same audit lineage,
  superset of `@noble/ed25519`.
- `@noble/hashes` — SHA-256, HKDF-SHA256, BLAKE2, etc., same lineage.
- `@stablelib/ed25519` — also pure-TypeScript, also vetted; smaller
  API surface, less actively maintained than @noble.
- `tweetnacl` — pure-JS, famous, but slow and not constant-time in
  all paths; suitable for browsers, not for a reference.
- `node:crypto` — Node's built-in Ed25519 (via OpenSSL) is fast and
  correct, but is not browser-safe (the dashboard runs in the browser
  for some flows) and exposes keys through KeyObject handles that
  reintroduce the Tink-style indirection the audit found.
- Tink (TS) — explicitly rejected by the spec; same KeysetHandle
  indirection that caused the audit finding.

The crypto primitive selection is **Tier 2** (API contract): the
choice of library is Tier 3, but the *interface shape* (raw 32-byte
keys in, 64-byte signatures out, no handle indirection) is Tier 2
because it determines whether signatures interoperate across
implementations. The audit found exactly this interface mismatch.

`04-THREAT-MODEL.md §4.2` lists "Signature verification call sites
(the audit found a `verify()` that returns `signature.size == 64`)" as
🟡 AI-implementable, mandatory human review before merge. This ADR
covers the *library selection*; the per-call-site review is tracked
separately in `SECURITY.md`.

## Decision

We adopt the @noble family as the cryptographic primitive layer in the
TypeScript reference:

- `@noble/ed25519` (≥2.0) — Ed25519 sign/verify with raw 32-byte
  public keys and 64-byte signatures.
- `@noble/curves` (≥1.0) — X25519 key agreement (for the Noise_IK
  handshake, ADR-0003).
- `@noble/hashes` (≥1.0) — SHA-256, HKDF-SHA256.

**Hard rule:** keys are `Uint8Array(32)` everywhere. No `KeyObject`,
no `KeysetHandle`, no `CryptoKey` DOM wrapper in the protocol layer.
The only place those wrappers may appear is inside a platform adapter
(L9) that converts between the platform's native key storage and the
raw 32-byte wire format, and only if the round-trip is byte-exact.

## Rationale

- **Direct fix for audit §3.1.** `@noble/ed25519.getPublicKey(secretKey)`
  returns the raw 32-byte Ed25519 public key. `signAsync(msg, secretKey)`
  returns the raw 64-byte signature. `verifyAsync(sig, msg, publicKey)`
  returns a boolean. There is no handle indirection; there is no
  `sha256(handle.toString())` failure mode.
- **Passes RFC 8032 §7.1 Test 1.** The vector
  `ed25519-rfc8032-test1-verify` in `03-identity.json` verifies the
  canonical empty-message Ed25519 signature against the canonical
  public key. This vector is generated by `@noble/ed25519` and MUST
  verify under `ed25519-dalek`, libsodium, BoringSSL, and JCA Ed25519.
  If any of those disagree, that implementation is non-conformant.
- **Passes RFC 5869 Test Case 1.** The vector
  `hkdf-sha256-rfc5869-test1` in `02-hashing.json` verifies the
  canonical HKDF-SHA256 output from RFC 5869 Appendix A. This pins
  HKDF correctness independent of language.
- **Remote-key verification works.** The audit found
  `TinkCryptoProvider.createRawVerifyHandle()` throws
  unconditionally. The vector `ed25519-verify-remote-key` in
  `03-identity.json` verifies a signature made by "Carol, a key never
  seen before" — i.e. a public key supplied at verification time, not
  pre-registered. `@noble/ed25519.verifyAsync` takes the public key as
  a parameter; there is no handle to create.
- **Audited.** The @noble libraries were audited by Trail of Bits in
  2022 (per the project's SECURITY.md). This is not equivalent to a
  fresh third-party audit of *this repository's* use of them, but it
  is materially different from Tink's situation where the *interface*
  was the bug, not the underlying library.
- **Cross-platform by construction.** @noble produces the same bytes
  on every platform (Node, browser, Deno, Bun) because it is
  pure-TypeScript with no native bindings. A signature made in a
  Next.js API route verifies in a browser worker and vice versa. This
  closes the "no signature produced on one device can be verified on
  another" finding at the API level.
- **Constant-time where it matters.** @noble's Ed25519 implementation
  uses constant-time field arithmetic. (SHA-256 and HKDF are
  inherently not secret-dependent.) This does not make the
  *TypeScript sandbox* side-channel-safe — see "Negative consequences"
  below — but it does not regress vs. the audit's baseline.

## Alternatives considered

### (a) Tink (TS) — rejected

The audit (§3.1) found Tink's raw-key import is not public API, so
`TinkCryptoProvider` derived "public keys" as `sha256(handle.toString())`.
The spec (02 §1.2) explicitly says "Tink MAY be used internally only
if raw keys round-trip byte-exactly." We have not verified that the TS
Tink binding round-trips byte-exactly, and the cost of being wrong is
the exact failure mode the audit found. Rejected.

### (b) node:crypto (OpenSSL) — rejected for the reference layer

Node's built-in Ed25519 is fast and correct, but:

- It is not browser-safe. The dashboard has browser-side flows
  (displaying descriptor verification, demo signing) that would need a
  polyfill, doubling the crypto surface.
- It exposes keys through `KeyObject` handles. The conversion to/from
  raw 32 bytes is correct today, but it is exactly the kind of
  indirection that bit Tink. The protocol layer should not depend on
  it.
- It is Node-only. A future browser-only port (PWA client) would need
  a different library, fragmenting the crypto surface.

`node:crypto` MAY be used in platform adapters (L9) where its
native-speed advantage matters (e.g. bulk SHA-256 on a large object
stream); the adapter MUST convert to raw 32-byte keys at the protocol
boundary.

### (c) tweetnacl — rejected

Famous, small, pure-JS. But:

- Not constant-time in all paths (the original djb tweetnacl had
  branches; the JS port inherits some).
- Slower than @noble by ~3-5×.
- Less actively maintained.
- The API is fine, but the maintenance trajectory is wrong for a
  reference implementation.

### (d) @stablelib/ed25519 — viable, rejected on maintenance trajectory

@stablelib is also pure-TypeScript and vetted. It is a close call. We
chose @noble because:

- @noble has had more recent audits (Trail of Bits 2022).
- @noble's API is more uniform across primitives (one `@noble/curves`
  package covers Ed25519 + X25519 + secp256k1 + P256 + ...; @stablelib
  splits these into separate packages).
- @noble is more actively maintained (more recent commits, more
  downstream consumers).

If @noble becomes unmaintained, @stablelib is the natural fallback.

### (e) Hand-roll Ed25519 from the RFC — rejected

The RFC 8032 algorithm is short enough to implement in a few hundred
lines. Do not. The threat model (§4.2) lists "Key derivation and
`NodeId` derivation" and "Signature verification call sites" as 🟡
mandatory human review. A hand-rolled Ed25519 is a 🔴 human-design
item: the field arithmetic, the Schnorr variant, and the cofactored
verification are all easy to get subtly wrong. Use a vetted library.

## Conformance impact

**No new vectors required.** The @noble libraries are exercised by the
existing suites:

- `02-hashing.json` — `sha256-empty`, `sha256-abc`, all 12
  `sig-context-*` vectors, `hkdf-sha256-rfc5869-test1`,
  `nodeid-derivation-alice`, `merkle-empty-root` (18 vectors total).
- `03-identity.json` — `ed25519-rfc8032-test1-verify`,
  `ed25519-verify-remote-key`, `ed25519-wrong-key-rejection`,
  `ed25519-cross-context-rejection`,
  `ed25519-wrong-length-signature-rejection`, `nodeid-deterministic`,
  `devicecert-sign-and-verify` (7 vectors).
- `05-merkle.json` — SHA-256 is the hash function for `leaf_hash` and
  `node_hash`; all 11 vectors transitively exercise @noble/hashes.
- `06-manifest.json` — manifest signatures use @noble/ed25519 (3
  vectors).
- `07-receipts.json` — all 4 receipt types use @noble/ed25519; the
  cross-type replay rejection vector exercises the SIG_CONTEXT domain
  separation that @noble enforces (5 vectors).
- `09-descriptors.json` — NodeDescriptor, GatewayAdvert signatures (3
  vectors).
- `10-routing.json` — RouteAdvert signatures (4 vectors).
- `11-gateway.json` — TransitRequest/Response signatures (20 vectors).
- `13-revocation.json` — revocation list signatures (3 vectors).
- `14-negative.json` — `negative-signature-valid-length-wrong-content`,
  `negative-receipt-signed-by-claimant` — both exercise
  `verifyAsync`'s rejection of plausible-but-wrong signatures (2 of
  the 15 negative vectors).

**Total: ~58 vectors directly or transitively exercise @noble.** If
@noble produces a byte that any other conformant implementation
disagrees with, CI fails.

## Migration path

**From Tink (the audited baseline):** N/A — the audited repository's
Tink code is being replaced, not migrated. Existing Tink-signed data
is not valid (the signatures were `sha256(handle.toString())`-based and
do not verify cross-device), so there is no compatibility constraint.

**To a Rust reference (future):** the Rust reference uses
`ed25519-dalek` (or `libsodium` via `sodiumoxide`). Both produce
byte-identical output to @noble for the same inputs. The conformance
vectors pin this; if they ever disagree, the Rust side is wrong (Tier 0
beats Tier 3).

**To a Kotlin/Android port:** Gemini's port uses JCA `Ed25519` (Android
API 33+) or BouncyCastle below that. Both produce byte-identical output
to @noble. Same pinning.

**If @noble becomes unmaintained or a vulnerability is found:**

1. File an ADR (superseding this one) naming the replacement
   (@stablelib/ed25519 is the leading candidate).
2. Regenerate every affected vector from the replacement library.
3. Diff against the @noble-generated vectors. If they match, the
   `generatedBy` field is updated and no implementation changes. If
   they do not match, file a separate ADR per discrepancy (the
   replacement library is presumed wrong until proven otherwise).
4. Update `package.json` and `SECURITY.md`.

## Consequences

### Positive

- Closes audit §3.1 at the API contract level. `verifyAsync` takes a
  raw 32-byte public key; there is no handle to misuse.
- Closes the "remote-key verification" failure (`createRawVerifyHandle`
  threw unconditionally). `ed25519-verify-remote-key` proves it.
- Cross-platform by construction (Node, browser, Deno, Bun). The
  "no signature verifies across devices" finding cannot recur at the
  library level.
- One library family (ed25519, curves, hashes) covers all protocol
  crypto primitives, so the audit surface is concentrated.
- The conformance suite (~58 vectors) pins @noble's output
  byte-for-byte against RFC 8032 and RFC 5869 test vectors. Any
  future drift in @noble is a CI failure here.

### Negative

- **The TypeScript sandbox is NOT side-channel-safe.** JS engines
  JIT-compile and GC, so timing guarantees are weaker than in Rust or
  C. @noble's constant-time field arithmetic helps, but the sandbox
  is still not suitable for production key storage or high-throughput
  signing. The conformance suite catches *encoding* and
  *verification* bugs; it does NOT catch timing attacks, side
  channels, or implementation-level vulnerabilities. See
  `SECURITY.md`.
- **Pure-TypeScript is slower than native.** For the conformance
  suite (small inputs, ~130 vectors) this is irrelevant. For bulk
  SHA-256 on a multi-GB object stream, @noble/hashes is 3-5× slower
  than `node:crypto`. Platform adapters (L9) MAY use `node:crypto`
  for bulk hashing and convert at the protocol boundary; the
  protocol layer uses @noble.
- **The audit lineage is library-level, not repository-level.**
  Trail of Bits audited @noble; nobody has audited *this repository's
  use of* @noble. A future repository-level audit is required before
  production. See `SECURITY.md`.
- **Dependency on a single maintainer.** @noble is primarily one
  person's work. If `paulmillr` stops maintaining it, the migration
  cost is non-trivial (see "Migration path" above).

### Neutral

- `package.json` adds three @noble dependencies. Install time
  increases by a few seconds; bundle size increases by ~50 KB
  (gzipped) for the dashboard.
