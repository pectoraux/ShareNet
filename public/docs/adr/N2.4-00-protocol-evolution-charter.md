## 1. Purpose

N2.4 defines the next evolution stage of the ShareNet circuit protocol.

N2.4 MUST extend the frozen N2.3 protocol boundary without modifying existing
N2.3 semantics.

The objective is to introduce additional distributed networking capabilities
while preserving interoperability with deployed N2.3 implementations.

---

## 2. N2.3 Compatibility Contract

The following are immutable:

- V1 packet format (5-field CBOR map)
- V1 CBOR encoding (golden vector: `11-circuit-packet-v1.json`)
- V1 AAD construction (`circuit_id ‖ seq ‖ ttl ‖ final_dst`, no domain)
- V1 nonce derivation (`circuit_id[0..8] ‖ seq`, no direction XOR)
- V1 forwarding semantics (forward-only, peel-one-layer)
- V2 packet format (8-field CBOR map with `"v": 2`)
- V2 version field (`"v": 2`, wire self-describing)
- V2 AAD domain (`"SNP/0.1/circuit/packet/v2"`)
- V2 authentication model (direction + flow_id bound in AAD)
- N2.3 replay semantics (check-before-AEAD, commit-after-AEAD, O(WINDOW))
- N2.3 sequence lifecycle (FIRST_PACKET_SEQ=1, no wrap, exhaustion at u32::MAX)
- N2.3 circuit expiration (both source + relay, `now >= expires_at`)
- N2.3 profile dispatch (PacketProfile::V1 / V2, ProfileMismatch before AEAD)

Any incompatible change requires a new protocol profile (`PacketProfile::V3`).

## 3. N2.4 Design Principles

### Principle 1 — Profiles are immutable

A released `PacketProfile` MUST never change behavior.

Evolution happens through:

```
PacketProfile::V3
```

not:

```
PacketProfile::V2 + exceptions
```

### Principle 2 — Security invariants precede implementation

Every N2.4 feature requires:
- Threat model
- State model
- Protocol invariants
- Failure behavior
- Interoperability strategy

**before code.**

### Principle 3 — Explicit capability negotiation

Nodes MUST advertise capabilities explicitly.

A node MUST NOT infer capabilities from:
- IP address
- transport type
- observed behavior
- undocumented packet fields

### Principle 4 — Fail-closed everywhere

Every new protocol path must define its failure behavior explicitly.
Unknown, malformed, or unexpected inputs MUST be rejected, not silently
accepted.

### Principle 5 — No hidden state

Protocol state transitions MUST be explicit and observable.
No implicit state derived from timing, packet counting, or heuristic
detection.

## 4. N2.4 Scope Candidates

The following areas require architectural decisions.

### 4.1 Internet Gateway Architecture

**Questions:**
- How does a node become a gateway?
- How is gateway capability advertised?
- How is gateway policy represented?
- How are users protected from malicious exits?

**Required ADR:** `N2.4-03-gateway-architecture.md`

### 4.2 Circuit Recovery

**Questions:**
When a relay disappears:

- **Option A:** Circuit teardown + rebuild (simple, interrupts traffic)
- **Option B:** Circuit migration (stateful, complex)
- **Option C:** Session continuation over replacement routes (hardest)

**Required ADR:** `N2.4-04-circuit-recovery.md`

### 4.3 Transport Independence

**Questions:**
Should circuits operate over:
- TCP
- QUIC
- UDP
- Bluetooth
- local mesh links
- future transports

**Required ADR:** `N2.4-05-transport-abstraction.md`

### 4.4 Mobile Node Lifecycle

**Questions:**
How do nodes behave during:
- sleep / wake
- IP changes
- NAT changes
- temporary disconnects

**Required ADR:** `N2.4-06-mobile-node-lifecycle.md`

### 4.5 Capability System

**Questions:**
Define:
```
Node
  ├── Identity (Ed25519, persistent)
  ├── Capabilities (Relay, Gateway, InternetGateway, ...)
  ├── Resources (bandwidth, uptime, storage)
  └── Policies (egress, transit, content)
```

**Required ADR:** `N2.4-02-capability-system.md`

### 4.6 Bidirectional Traffic (carried from N2.4 proposal)

**Questions:**
- Does N2.4 implement the reverse-direction Tor add-layer model from the
  N2.4 spec in `08-circuits.md`?
- Or does it defer bidirectional traffic to a later milestone?

**Required ADR:** `N2.4-01-bidirectional-traffic.md`

---

## 6. Explicit Non-Goals

N2.4 MUST NOT:
- Modify N2.3 packet behavior
- Remove V1 compatibility
- Silently change V2 semantics
- Introduce hidden compatibility modes
- Rely on undocumented behavior
- Break the golden wire vectors

---

## 7. Success Criteria

N2.4 is complete only when:
- Protocol changes are documented in ADRs
- New profiles have explicit identity (`PacketProfile::V3` if needed)
- Compatibility behavior is defined (V1/V2/V3 interaction matrix)
- Security invariants are proven (adversarial tests)
- Reference implementation exists
- Conformance vectors exist
- Migration strategy is documented
