# ShareNet N2.1.1 — Peer Discovery & Topology Architecture

**Status:** Design document — no implementation code in this milestone.
**Current commit:** `afe51ae33b03726e3e35beed9c5068e066bbcc6a`
**Date:** 2026-08-12

---

## 1. Product Thesis

ShareNet is a cross-platform delay-tolerant mesh network. A device without direct Internet connectivity should ultimately be able to reach the real Internet through other ShareNet nodes:

```
Client → Relay → Relay → Internet Gateway → Real Internet
```

N2.1.1 establishes the **topology subsystem** that route computation will later consume. It does NOT implement routing algorithms, Internet gateway logic, or Civic Points.

---

## 2. Core Concepts (Distinct, Not Collapsed)

| Concept | Definition |
|---------|-----------|
| **Node** | Cryptographic identity (NodeId + Ed25519 keypair) + capabilities. Stable across sessions. |
| **Advertisement** | A signed, time-bounded `NodeAdvertisement` claim about a node's current state (endpoints, capabilities, X25519 key). Fresh per issuance (sequence + nonce). |
| **AuthenticatedNodeRecord** | A verified snapshot of one advertisement instance: `VerifiedNodeDescriptor + endpoints + sequence + expiry`. The unit stored by topology. |
| **Link** | An actual, probed transport relationship between two nodes over a specific endpoint. Has liveness state and metrics. NOT the same as "I saw an advertisement." |
| **Route** | An ordered path through usable links. Already exists as `Route` (in `route.rs`). N2.1.1 does not compute routes — it produces the topology from which routes can be computed. |
| **Topology** | Current knowledge of nodes (via authenticated records) and links (via probed connections). A directed graph. |

---

## 3. State Distinctions

The topology maintains **four independent state dimensions** per peer. These are NOT collapsed into a single `PeerState` enum.

### 3.1 Identity State

```
UNKNOWN → KNOWN → REMOVED
```

- **UNKNOWN**: Never seen an authenticated advertisement from this NodeId.
- **KNOWN**: At least one advertisement has been accepted (sequence floor exists).
- **REMOVED**: Explicitly removed via `remove_peer()`. The ONLY way to erase the identity history. MUST NOT be triggered by timeout, link failure, or advertisement expiry.

**Reuse:** `AdvertisementAcceptanceStore` already implements this (via `PeerVisibility::Unknown/Active/Stale` + `remove_peer()`).

### 3.2 Advertisement State

```
CURRENT → STALE
```

- **CURRENT**: Has a valid (non-expired) `AuthenticatedNodeRecord`.
- **STALE**: The record has expired. The identity remains KNOWN. The sequence floor persists.

**Reuse:** `AdvertisementAcceptanceStore::purge_expired_records()` already transitions CURRENT → STALE without erasing the floor.

### 3.3 Reachability State

```
UNREACHABLE → REACHABLE
```

- **UNREACHABLE**: No working transport connection has been established to any of the node's advertised endpoints. The advertisement may be CURRENT, but the node cannot currently be contacted.
- **REACHABLE**: At least one link is UP.

**New:** This state is NOT in the advertisement layer. It requires link probing (Section 7). An advertisement being valid does NOT imply reachability.

### 3.4 Link State

```
DOWN → DEGRADED → UP
```

- **UP**: Link is established and functioning normally.
- **DEGRADED**: Link is established but experiencing failures or high latency (above a threshold).
- **DOWN**: Link has failed (connection lost, handshake failed, or too many consecutive failures). The link object is retained for metrics/recovery but is not usable for forwarding.

**New:** This is per-link, not per-node. A node may have one UP link and one DOWN link simultaneously.

### 3.5 Capability State (Derived)

Derived from the `AuthenticatedNodeRecord`'s `VerifiedNodeDescriptor.capabilities()`:

- **RELAY_CAPABLE**: Contains `Capability::Relay`.
- **GATEWAY_CAPABLE**: Contains `Capability::Gateway` (implies X25519 circuit key present).

These are not states that change independently — they are properties of the current authenticated record.

## 4. Directed Topology

The topology graph is **directed**. A link from A to B does NOT imply a link from B to A.

```
A ──→ B  (A can reach B)
B -X→ A  (B cannot reach A)
```

This models real-world asymmetry:
- Firewall/policy restrictions
- Transport limitations (e.g., BLE is often asymmetric)
- One-way reachability (e.g., NAT traversal)
- Gateway restrictions

**Data model:** The `Link` struct carries `local_node_id` and `remote_node_id`. A link A→B is stored separately from B→A. The `TopologyGraph` supports querying outgoing links (neighbors) and incoming links (who can reach me).

---

## 5. Node Record in Topology

The topology consumes `AuthenticatedNodeRecord` (from `node_advert.rs`), NOT raw `UnverifiedNodeDescriptor` or `GatewayAdvertisement`.

An `AuthenticatedNodeRecord` contains:
- `descriptor: VerifiedNodeDescriptor` (NodeId + Ed25519 pub + X25519 circuit pub (optional) + capabilities)
- `endpoints: Vec<TransportEndpoint>` (authenticated — covered by the advertisement signature)
- `sequence: u64` (monotonic advertisement sequence)
- `expiry: u64` (when this record expires)

**Reuse:** This type already exists and is produced by `VerifiedNodeAdvertisement::into_record()`.

## 6. Peer Directory

### 6.1 Design

```
PeerDirectory
├── AdvertisementAcceptanceStore (ordering authority — already exists)
├── Node records: HashMap<NodeId, AuthenticatedNodeRecord> (current records, from acceptance)
└── Link table: HashMap<(NodeId, NodeId, TransportEndpoint), Link> (probed connections)
```

### 6.2 Responsibilities

1. **Store known authenticated nodes** — via `AdvertisementAcceptanceStore::accept()`.
2. **Apply newer advertisements** — delegated to `AdvertisementAcceptanceStore` (sequence ordering).
3. **Reject stale advertisements** — delegated to `AdvertisementAcceptanceStore` (returns `Stale` or `Duplicate`).
4. **Expose current/stale status** — via `AdvertisementAcceptanceStore::visibility()`.
5. **Retain identity after advertisement expiry** — `PeerAcceptanceState.highest_accepted_sequence` persists.
6. **Remove identity only through explicit removal** — via `AdvertisementAcceptanceStore::remove_peer()` (transactional).
7. **Provide snapshots for topology computation** — returns all ACTIVE nodes + their links.

### 6.3 Key Principle

The `PeerDirectory` does NOT duplicate advertisement validation logic. It uses `AdvertisementAcceptanceStore` as the **single ordering authority**. The directory adds:
- Link tracking (which advertised endpoints have been probed and are UP/DOWN).
- Reachability status (does at least one link to this node exist and is it UP?).

### 6.4 API Sketch

```rust
pub struct PeerDirectory {
    acceptance: AdvertisementAcceptanceStore,
    links: HashMap<LinkKey, Link>,
}

impl PeerDirectory {
    pub fn accept_advertisement(&mut self, verified: VerifiedNodeAdvertisement)
        -> Result<AcceptanceResult, AcceptanceError>;

    pub fn add_link(&mut self, link: Link);
    pub fn update_link_state(&mut self, key: &LinkKey, state: LinkState);
    pub fn remove_link(&mut self, key: &LinkKey);

    pub fn active_nodes(&self) -> Vec<&AuthenticatedNodeRecord>;
    pub fn reachable_nodes(&self) -> Vec<NodeId>;
    pub fn gateway_capable_nodes(&self) -> Vec<&AuthenticatedNodeRecord>;
    pub fn relay_capable_nodes(&self) -> Vec<&AuthenticatedNodeRecord>;
    pub fn links_from(&self, node_id: &NodeId) -> Vec<&Link>;
    pub fn links_to(&self, node_id: &NodeId) -> Vec<&Link>;

    pub fn purge_expired(&mut self, now: u64);
}
```

## 7. Link Model

### 7.1 Link Struct

```rust
pub struct LinkKey {
    pub local_node_id: [u8; 32],
    pub remote_node_id: [u8; 32],
    pub endpoint: TransportEndpoint,
}

pub struct Link {
    pub key: LinkKey,
    pub state: LinkState,
    pub transport_type: TransportType,
    pub established_at: u64,
    pub last_success: u64,
    pub last_failure: Option<u64>,
    pub rtt_micros: Option<u64>,
    pub failure_count: u32,
    pub success_count: u32,
    pub estimated_bandwidth_bps: Option<u64>,
    pub peer_session_id: Option<[u8; 32]>,
}

pub enum LinkState {
    Up,
    Degraded,
    Down,
}

pub enum TransportType {
    Tcp,
    Ble,
    WifiDirect,
    NearbyConnections,
}
```

### 7.2 Design Principles

- A `Link` represents a **probed, authenticated transport relationship** — NOT just an advertisement.
- The `LinkKey` includes the `TransportEndpoint` — a node can have multiple links over different transports.
- Links are **directed**: `local_node_id → remote_node_id`.
- Links do NOT contain routing decisions. They contain metrics that the future route engine will consume.
- `peer_session_id` links to the existing `PeerSession` (from `session.rs`) when an SNP-IK/0.1 handshake has been performed.

## 8. Link Establishment

### 8.1 Process

```
1. Authenticated advertisement received
   → VerifiedNodeAdvertisement
   → AuthenticatedNodeRecord (via acceptance store)

2. Candidate endpoint selected
   → TransportEndpoint from the AuthenticatedNodeRecord

3. Transport connection attempted
   → AsyncTcpTransportProvider::connect() (or future BLE/Wi-Fi Direct)

4. Protocol handshake
   → perform_snp_ik_handshake_async() (initiator, pinning remote NodeId)

5. Peer authentication
   → handshake.peer_node_id == advertised NodeId?
   → If mismatch: identity substitution detected, link rejected

6. LinkUp
   → Link { state: Up, peer_session_id: Some(handshake.session_id), ... }
```

### 8.2 Key Principle

An advertisement being valid does NOT imply reachability. The link must be **probed** — an actual transport connection + protocol handshake must succeed. If the endpoint cannot be reached or the handshake fails, the link is `Down` or does not exist.

### 8.3 Reuse

- `perform_snp_ik_handshake_async` (from `snp-link/src/async_link.rs`) — the SNP-IK/0.1 handshake.
- `AsyncTcpTransportProvider` (from `async_transport.rs`) — TCP transport.
- `VerifiedNodeDescriptor` (from `descriptor.rs`) — the authenticated identity to pin against.

---

## 9. Link Authentication

### 9.1 Endpoint-Identity Binding

A discovered endpoint MUST be authenticated against the advertised node identity. The following MUST NOT be accepted:

```
Node X advertisement + endpoint belonging to Node Y = usable Link to X
```

The connection handshake (`perform_snp_ik_handshake_async`) proves the remote node's identity. The `expected_peer_node_id` parameter pins the expected identity. If the authenticated NodeId does not match the advertised NodeId, the link is rejected.

### 9.2 Reuse

- The SNP-IK/0.1 handshake already provides identity-substitution detection (tested in `n205_identity_substitution.rs` and `async_link.rs`).
- No second identity scheme is invented.

## 10. Topology Graph

### 10.1 Design

```rust
pub struct TopologyGraph {
    directory: PeerDirectory,
}

impl TopologyGraph {
    // Node operations
    pub fn accept_advertisement(&mut self, verified: VerifiedNodeAdvertisement)
        -> Result<AcceptanceResult, AcceptanceError>;
    pub fn purge_expired(&mut self, now: u64);

    // Link operations
    pub fn add_link(&mut self, link: Link);
    pub fn update_link_state(&mut self, key: &LinkKey, state: LinkState);
    pub fn remove_link(&mut self, key: &LinkKey);

    // Queries (for future route engine)
    pub fn neighbors(&self, node_id: &[u8; 32]) -> Vec<&Link>;
    pub fn reachable_gateways(&self) -> Vec<&AuthenticatedNodeRecord>;
    pub fn reachable_relays(&self) -> Vec<&AuthenticatedNodeRecord>;
    pub fn is_reachable(&self, node_id: &[u8; 32]) -> bool;
    pub fn link_state(&self, key: &LinkKey) -> Option<LinkState>;

    // Snapshot for route computation
    pub fn snapshot(&self) -> TopologySnapshot;
}
```

### 10.2 TopologySnapshot

A point-in-time view of the topology, suitable for route computation. Contains:
- Active nodes (with `AuthenticatedNodeRecord`)
- UP links (with metrics)
- Gateway-capable nodes

The snapshot is immutable — route computation operates on it without modifying live topology state.

## 11. Node Churn Model

| Event | Identity State | Advertisement State | Link State | Action |
|-------|---------------|--------------------|--------------------|--------|
| Node appears (first advertisement) | UNKNOWN → KNOWN | CURRENT | (none) | Accept record, add to directory |
| Advertisement refreshes (newer sequence) | KNOWN | CURRENT (updated) | (unchanged) | Accept new record, update directory |
| Advertisement expires | KNOWN | CURRENT → STALE | (unchanged) | Purge record, keep sequence floor |
| Link established | (unchanged) | (unchanged) | DOWN → UP | Add link to directory |
| Link fails | (unchanged) | (unchanged) | UP → DOWN | Update link state, keep link for metrics |
| Link recovers | (unchanged) | (unchanged) | DOWN → UP | Update link state |
| Node disappears (all links down) | KNOWN | (unchanged) | all DOWN | Do NOT remove identity. Do NOT call `remove_peer()`. Node is KNOWN but UNREACHABLE. |
| Node returns (new advertisement + link) | KNOWN | CURRENT (updated) | UP | Accept record, re-establish link |
| Explicit removal | KNOWN → REMOVED | (erased) | (erased) | Call `remove_peer()` — transactional, persists first |

**Key invariants:**
- KNOWN ≠ ACTIVE (identity known ≠ currently reachable)
- STALE ≠ REMOVED (expired advertisement ≠ forgotten identity)
- DOWN ≠ FORGOTTEN (link failure ≠ identity removal)

## 13. Local vs Remote Discovery

### Local Discovery
- Discovering nearby nodes via direct transport (TCP bootstrap, BLE, Wi-Fi Direct).
- The node receives `NodeAdvertisement` messages directly from peers it can physically reach.
- Endpoints in the advertisement are the peer's own declared endpoints.

### Remote Topology Propagation (Deferred to N2.1.2)
- Learning about nodes reachable through other peers.
- Requires a bounded summary/anti-entropy mechanism.
- Must NOT automatically expose local endpoint data for every node to every peer.
- Only information explicitly permitted by the protocol is propagated.

**N2.1.1 scope:** Local discovery only. The architecture defines interfaces for remote propagation but does not implement it.

## 14. Discovery Message Model

### 14.1 Minimal Message Set for N2.1.1

| Message | Purpose | Authentication |
|---------|---------|---------------|
| `HELLO` | "I am here, here is my advertisement." | Signed `NodeAdvertisement` |
| `GOODBYE` | "I am leaving." (best-effort, not relied upon) | Signed by the node's Ed25519 key |

### 14.2 Deferred Messages (N2.1.2+)

| Message | Purpose |
|---------|---------|
| `PEER_SUMMARY` | Bounded summary of known topology (NodeIds + highest sequences) |
| `PEER_REQUEST` | Request full advertisements for specific NodeIds |
| `LINK_STATUS` | Report link state to remote peers |

### 14.3 Encoding

All messages use **canonical SNP CBOR** (via `snp-cbor`). Each message is:

```
{
  messageType: tstr,     // "hello" | "goodbye" | ...
  senderNodeId: bstr,    // SHA-256("SNP/0.1 node\0" || sender_pub_key)
  payload: any,          // message-specific
  signature: bstr        // Ed25519 under SIG_CONTEXT "topology-msg"
}
```

### 14.4 Replay Handling

- `HELLO` contains a `NodeAdvertisement` which already has sequence + nonce + expiry + timestamp.
- `GOODBYE` contains a timestamp + nonce. The acceptance store's sequence floor prevents replay of old `GOODBYE` messages (a `GOODBYE` with sequence < current floor is rejected as stale).

## 15. Anti-Entropy (Design, Not Implementation)

### 15.1 Bounded Summary Mechanism (N2.1.2)

```
PeerSummary = {
  nodeId: bstr,
  sequence: uint,        // highest known advertisement sequence
  visibility: tstr,      // "active" | "stale"
  lastSeen: uint,        // when we last had a working link
}
```

- Peers exchange summaries (bounded — one entry per known node).
- A peer requests full advertisements only for nodes whose sequence is higher than what it knows.
- Summary size is bounded by the number of known peers (not the total network size).

### 15.2 Security

- Summaries are signed by the sender.
- A malicious peer cannot inject fake advertisements (the advertisements themselves are signed by the node they describe).
- A malicious peer CAN claim to know about a node it doesn't — but the receiver will request the full advertisement, and if the advertiser can't provide a valid signed advertisement, the entry is rejected.
- Excessive topology flooding is bounded by:
  - Summary size limits (max entries per message).
  - Rate limiting (max summaries per time window).
  - Sequence ordering (stale summaries are ignored).

## 16. Topology Security Model

### 16.1 Threat Analysis

| Threat | Mitigation |
|--------|-----------|
| Fake peer advertisements | Ed25519 signature verification (existing) |
| Replay | Monotonic sequence + nonce + expiry + acceptance store (existing) |
| Stale topology injection | Sequence ordering in acceptance store (existing) |
| Endpoint substitution | SNP-IK/0.1 handshake pins NodeId (existing) |
| Topology poisoning | Advertisements are self-signed by the node they describe; a relay cannot forge another node's advertisement |
| Sybil nodes | **NOT MITIGATED** — a single entity can generate many keypairs. Documented as a residual risk. Future: proof-of-work, stake, or social graph. |
| Eclipse attacks | **PARTIALLY MITIGATED** — bootstrap discovery uses a configured address list, not a single peer. Future: diversity requirements in peer selection. |
| Malicious relays | Relays see only ciphertext (I8 invariant). A relay can drop/modify OUTER frames but cannot read circuit payloads. |
| Fake gateway claims | Gateway capability + X25519 key are inside the signed advertisement. A non-gateway cannot forge gateway capability without the private key. |
| Excessive topology flooding | Bounded summary size + rate limiting (design, not yet implemented). |
| Route amplification | Topology is a local view, not a global broadcast. Each node maintains its own graph. |

### 16.2 Residual Risks (Documented)

- **Sybil resistance**: Not implemented. A node can create unlimited identities.
- **Eclipse resistance**: Partially mitigated via bootstrap list diversity. Not fully designed.
- **Local persistence security**: The persistence file is not authenticated. Local filesystem access can modify the sequence floor. Platform-specific secure storage is deferred.
- **Topology propagation privacy**: N2.1.2 must carefully design what information is propagated to which peers.

## 17. Topology Metrics

Metrics collected per-link for future route computation:

| Metric | Source | Type |
|--------|--------|------|
| Hop count | Topology graph (path length) | Derived |
| RTT | Link probing (round-trip time) | Measured |
| Success rate | Link failure/success counters | `success_count / (success_count + failure_count)` |
| Availability | `uptime / (uptime + downtime)` over a window | Derived |
| Bandwidth estimate | Link probing (optional) | Measured |
| Transport quality | Transport-type-specific (e.g., BLE signal strength) | Platform-specific |
| Congestion | Frame queue depth / latency variance | Measured (future) |
| Gateway capacity | Gateway self-reported (optional, unsigned) | Metadata |
| Route stability | How long a route has been viable | Derived |

**N2.1.1 scope:** RTT, success rate, and failure count are collected. Other metrics are designed but not implemented.

## 18. Gateway as Capability

An Internet gateway is NOT a separate subsystem. It is a node whose `AuthenticatedNodeRecord.descriptor.capabilities()` contains `Capability::Gateway`.

The topology graph supports:
```rust
pub fn reachable_gateways(&self) -> Vec<&AuthenticatedNodeRecord>;
```

This returns all nodes that:
1. Have a CURRENT advertisement (not STALE).
2. Advertise `Capability::Gateway`.
3. Have at least one UP link.
4. Have an X25519 circuit public key (required for Gateway capability — enforced by `NodeAdvertisement::verify_into_verified()`).

The future route engine will call this to find candidate destinations.

## 20. Persistence Requirements

### 20.1 What is Persisted

| Data | Persisted? | Format | Existing? |
|------|-----------|--------|-----------|
| Peer acceptance state (NodeId + Ed25519 pub + highest_sequence) | YES | `SNPA` format | Yes (`AdvertisementAcceptanceStore`) |
| Node's own advertisement sequence | YES | `SNSQ` format | Yes (`AdvertisementSequenceStore`) |
| Current `AuthenticatedNodeRecord` per peer | NO | — | Records are ephemeral (re-derived from advertisements) |
| Link state (UP/DOWN, metrics) | NO (N2.1.1) | — | Links are re-established on restart |
| Topology graph | NO (N2.1.1) | — | Rebuilt from discovery on restart |

### 20.2 Rationale

- Acceptance state MUST be persisted (monotonicity invariant).
- Current records are NOT persisted (they expire; re-discovery is the correct behavior).
- Link state is NOT persisted (links are transport-specific and may not survive restart).
- The topology graph is rebuilt from local discovery on restart.

### 20.3 Future

- Link state persistence may be added for faster recovery after restart.
- Topology cache persistence may be added for faster convergence after restart.
- Both are explicitly deferred.

## 23. Threat Model Additions

### 23.1 New Attack Surfaces

| Surface | Threat | Mitigation |
|---------|--------|-----------|
| Topology graph | Poisoning via fake links | Links require a successful SNP-IK/0.1 handshake (authenticated) |
| Link probing | DoS via forcing many probe attempts | Rate limiting (max probes per time window) |
| Discovery | Amplification via HELLO flooding | Rate limiting + bounded advertisement size |
| Persistence | Local file tampering | Documented limitation; platform-specific secure storage deferred |

### 23.2 Non-Mitigated Risks

- **Sybil attack**: A single entity can create many keypairs and advertise many nodes. Not mitigated in N2.1.1.
- **Eclipse attack**: An attacker controls all of a node's peers. Partially mitigated by bootstrap list diversity. Not fully designed.
- **Traffic analysis**: An observer can infer topology from link patterns. Not mitigated.

## 24. Explicit Non-Goals

- Route computation (pathfinding algorithms)
- Internet gateway traffic forwarding
- Civic Points / economic rewards
- Android / iOS / Windows platform-specific code
- BLE / Wi-Fi Direct / Nearby Connections transport
- Remote topology propagation (anti-entropy, peer summary exchange)
- Topology persistence (beyond acceptance state)
- Sybil resistance
- Traffic analysis resistance
- OS-level transparent Internet (VPN service, tun/tap)

## 25. Open Architectural Decisions

| Decision | Options | Recommendation | Defer to |
|----------|---------|---------------|----------|
| Link probing frequency | Fixed interval vs adaptive | Adaptive (start fast, slow down when stable) | N2.1.1 implementation |
| Degraded threshold | RTT multiplier vs absolute | RTT multiplier (e.g., >3× median) | N2.1.1 implementation |
| Link recovery | Auto-retry vs manual | Auto-retry with exponential backoff | N2.1.1 implementation |
| Topology snapshot format | Clone all vs reference | Reference (avoid copying large graphs) | N2.1.1 implementation |
| Discovery protocol port | Fixed vs dynamic | Dynamic (ephemeral) for reference; configurable | N2.1.1 implementation |
| HELLO message size limit | Fixed cap vs negotiable | Fixed cap (64 KiB — matches advertisement limit) | N2.1.1 implementation |
| Link metrics persistence | Persist vs ephemeral | Ephemeral (N2.1.1); persist in future | N2.2+ |
| Remote propagation scope | Full vs capability-filtered | Capability-filtered (only propagate what's needed) | N2.1.2 |

## 26. Architecture Summary

```
                 EXISTING (N2.1.0.x)
                 ═══════════════════
    NodeAdvertisement (signed)
           ↓
    VerifiedNodeAdvertisement (stateless verify)
           ↓
    AdvertisementAcceptanceStore (stateful, persistent)
           ↓
    AuthenticatedNodeRecord (verified snapshot)
           ↓
    PeerVisibility: Unknown / Active / Stale


                 NEW (N2.1.1)
                 ═══════════
    PeerDirectory
    ├── AdvertisementAcceptanceStore (reuse)
    └── Link table (new)
         ↓
    Link (directed, per-endpoint)
    ├── LinkState: Up / Degraded / Down
    ├── Metrics: RTT, success/failure counts
    └── PeerSession (reuse from session.rs)
         ↓
    TopologyGraph
    ├── Nodes (from PeerDirectory)
    ├── Directed Links (from Link table)
    ├── Queries: neighbors, reachable_gateways, reachable_relays
    └── Snapshot (for future route engine)


                 FUTURE (N2.1.2+)
                 ════════════════
    Remote Topology Propagation
    ├── PeerSummary exchange
    ├── Anti-entropy
    └── Topology security hardening

    Route Engine (N2.1.3+)
    ├── Path computation
    ├── Route selection
    └── RouteCommitment (reuse from route.rs)

    Internet Gateway (N2.2+)
    ├── Traffic forwarding
    └── OS-level integration
```

## 27. Deliverable Summary

This document constitutes the N2.1.1 architecture design. No implementation code is committed in this milestone. The design is grounded in the existing ShareNet source code and reuses:

- `NodeAdvertisement` / `VerifiedNodeAdvertisement` / `AuthenticatedNodeRecord` (from `node_advert.rs`)
- `AdvertisementAcceptanceStore` / `AdvertisementSequenceStore` (from `node_advert.rs`)
- `VerifiedNodeDescriptor` / `TransportEndpoint` (from `descriptor.rs`)
- `perform_snp_ik_handshake_async` / `AsyncLink` (from `snp-link/src/async_link.rs`)
- `AsyncTcpTransportProvider` (from `async_transport.rs`)
- `PeerSession` (from `session.rs`)
- `NodeIdentity` / `Capability` (from `identity.rs`)
- Canonical CBOR (from `snp-cbor`)
- Ed25519 / X25519 / SHA-256 / AEAD (from `snp-crypto`)

The next step is implementation of the N2.1.1 design, followed by N2.1.2 (remote topology propagation) and N2.1.3 (route computation).
