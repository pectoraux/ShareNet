# N2.4-06 — Mobile Node Lifecycle

**Status:** PROPOSED — awaiting review

**Parent:** N2.4-05 Transport Abstraction (approved, `268b5a6`)

**Baseline:** N2.3 frozen @ `425eccb` (tag: `v2.3.0-protocol`)

**Approved dependencies:** N2.4-00 Charter, N2.4-01 Threat Model, N2.4-02 Capability System, N2.4-03 Gateway Architecture, N2.4-04 Circuit Recovery, N2.4-05 Transport Abstraction

---

## 1. Problem Statement

ShareNet targets mobile devices — Android phones, iPhones, laptops that sleep,
RPi nodes on unstable power. These devices change networks (Wi-Fi → cellular),
sleep and wake, get background-suspended by the OS, and lose connectivity
temporarily. The architecture must handle these lifecycle events **without
modifying the frozen N2.3 circuit protocol** and **without creating a
parallel mobility protocol**.

N2.4-05 defined the `Link` trait (transport abstraction) with a clear
lifecycle: Links are established, carry frames, and die (liveness timeout or
transport teardown). N2.4-04 defined `TransportSession` (session continuity
across circuit replacement) and circuit recovery (R0/R1/R2). N2.4-06 defines
how **mobility events** map onto these existing mechanisms — it introduces no
new cryptographic protocol and no new wire format.

### The non-negotiable constraint

> **N2.4-06 MUST NOT modify the frozen N2.3 packet semantics.**

Mobility is handled **above** the circuit layer (via N2.4-04 TransportSession
survival) and **below** the circuit layer (via N2.4-05 Link replacement).
The frozen N2.3 V1/V2 circuit packet is unaware of mobility. No
`PacketProfile::V3` (deferred to N2.4-07).

## 2. Architecture Overview

```
Application
    ↑ sees: session continuity OR honest degradation
Mobile Node Lifecycle  (N2.4-06 — this ADR)
    coordinates: when Links are established/torn down,
                 when TransportSessions are preserved/dropped,
                 when circuits are recovered, when the node degrades
TransportSession layer  (N2.4-04 — session continuity)
    ↑ survives circuit replacement; dies on source process restart
Circuit layer  (N2.3 FROZEN — V1/V2 packet)
    ↑ unaware of mobility
Link layer  (N2.4-05 — L8 Transport Abstraction)
    ↑ Links die on transport teardown, liveness timeout, or sleep
L9 platform adapters  (TCP / QUIC / BLE / ... — implementation deferred)
```

**Key principle:** N2.4-06 does NOT introduce a new protocol layer. It is a
**coordination layer** that maps platform lifecycle events (sleep, wake, IP
change, background suspension) onto the existing N2.4-04/N2.4-05 mechanisms.
The mobile node lifecycle is **stateless** — it does not carry cryptographic
state; it coordinates state owned by N2.4-04 (TransportSession) and N2.4-05
(Link).

## 3. Mobile Node Lifecycle States

### 3.1 NodeLifecycleState (normative)

```text
NodeLifecycleState =
    ACTIVE          // node is foreground, network is up, Links are live
  | DEGRADED        // some Links are Degraded/Dead; node is reducing activity
  | BACKGROUND      // OS has backgrounded the process; Links may be suspended
  | SUSPENDED       // OS has suspended the process (Doze, App Nap, screen off)
  | DISCONNECTED    // no network at all; all Links are Dead
  | OFFLINE         // no peers, no gateway; only local content available
```

### 3.2 State transitions (normative)

```text
ACTIVE
    ↓ [OS backgrounds the process / screen off]
BACKGROUND
    ↓ [OS suspends (Doze / App Nap / memory pressure)]
SUSPENDED
    ↓ [OS kills the process or device powers off]
(process restart → ACTIVE via fresh start, §7)

ACTIVE / BACKGROUND
    ↓ [network change: IP change, Wi-Fi→cellular, NAT change]
    → Link replacement (N2.4-05 §7.4) + TransportSession survival (N2.4-04)
    → state remains ACTIVE or BACKGROUND (the node does not enter DISCONNECTED
      if at least one Link can be re-established within LIVENESS_TIMEOUT)

ACTIVE / BACKGROUND / SUSPENDED
    ↓ [all Links Dead (network lost, liveness timeout)]
DISCONNECTED
    ↓ [no peers / no gateway reachable]
OFFLINE
    ↓ [process restart or network restored]
ACTIVE (re-established from scratch — fresh Links, fresh circuits,
        TransportSession recovery per N2.4-04 §7.5)
```

### 3.3 State transition invariants

1. **SUSPENDED is platform-enforced, not ShareNet-chosen.** The node enters
   SUSPENDED because the OS suspends the process (Android Doze, iOS background
   suspension, macOS App Nap, Windows Modern Standby). ShareNet cannot prevent
   this; it can only prepare for it (§5).
2. **DISCONNECTED is Link-layer-determined.** The node enters DISCONNECTED when
   all Links are Dead (N2.4-05 `LivenessState == Dead`). The mobile lifecycle
   layer does not independently detect network loss — it observes Link deaths.
3. **OFFLINE is peer-determined.** The node enters OFFLINE when it cannot
   discover or reach any peer or gateway. This is a discovery/routing concern
   (L4/L6), not a transport concern.
4. **Recovery from DISCONNECTED/OFFLINE follows N2.4-04.** When the network
   returns, the node establishes fresh Links (N2.4-05 §7.4 — fresh SNP-IK/0.1
   handshakes), recovers TransportSessions (N2.4-04 §7.5 — new TSID + new
   root on process restart; or existing TSID + new circuit if the process
   survived), and re-establishes circuits (N2.4-04 R0/R1/R2).

## 4. IP / Address Changes

### 4.1 The problem

A mobile device changes IP address when:
- Switching from Wi-Fi to cellular (or vice versa).
- The cellular tower assigns a new IP.
- The Wi-Fi DHCP lease renews with a different address.
- NAT rebinding changes the external address.

The node's `TransportEndpoint` changes, but its `NodeId` (Ed25519 identity)
does not.

### 4.2 Architecture (normative)

An IP/address change is a **Link replacement** — the old Link (on the old IP)
dies, and a new Link (on the new IP) is established. This is handled entirely
by N2.4-05's Link lifecycle:

```text
IP change detected (or old Link goes Dead)
    ↓
old Link(s) die (liveness timeout or transport teardown)
    ↓
N2.4-05 §7.4: old LinkKeys invalid; fresh transport connections;
    fresh SNP-IK/0.1 handshakes (new link_key, new sequence space)
    ↓
N2.4-04: affected circuits recover (R1 if relay-only, R2 if gateway also
    unreachable); TransportSession survives (if process survived — existing
    TSID + new circuit; if process restarted — new TSID + new root per §7.5)
    ↓
routing layer (L6) re-discovers routes over the new Links
    ↓
node returns to ACTIVE (or DEGRADED if some Links cannot be re-established)
```

### 4.3 QUIC migration as one mechanism

QUIC connection migration (RFC 9000 §9) MAY allow a peer's IP to change
without tearing down the QUIC connection — the `link_key` and sequence space
are preserved. N2.4-05 §10.2 invariant: **QUIC migration MUST NOT change the
authenticated ShareNet NodeId or silently substitute peer identity.** IP
endpoint change ≠ NodeId change.

QUIC migration is ONE mechanism for handling IP changes. Other mechanisms:
- **TCP Link replacement:** the old TCP Link dies; a fresh TCP Link is
  established on the new IP. The `link_key` changes (fresh SNP-IK/0.1
  handshake); the `NodeId` is unchanged (same Ed25519 key). Circuits using
  the old Link recover via N2.4-04 R1.
- **BLE/Wi-Fi Direct:** BLE and Wi-Fi Direct Links are not IP-addressed; IP
  changes do not affect them. A BLE Link survives a Wi-Fi→cellular handoff.

### 4.4 NAT changes

NAT rebinding (the external NAT mapping changes without the device's local IP
changing) is detected as a Link death — the old NAT mapping stops forwarding,
the Link's keepalive times out, and the Link transitions to Dead. Recovery is
the same as IP change (§4.2): Link replacement + circuit recovery.

For TCP, NAT rebinding typically kills the TCP connection (RST or timeout).
For QUIC, connection migration MAY survive a NAT rebinding (the QUIC
connection ID is route-independent). For UDP, the NAT mapping may change
without the application noticing (the Link's keepalive eventually detects it).

## 5. Sleep / Wake

### 5.1 The problem

When a device sleeps (screen off, lid closed, OS suspend):
- The network stack may be suspended (no packet delivery).
- TCP connections may be reset by the OS or NAT timeout.
- BLE/Wi-Fi Direct may be suspended (Android Doze restricts background
  scanning/advertising).
- The process may be suspended (Android Doze, iOS background suspension).

When the device wakes:
- The network stack resumes.
- Links may be Dead (liveness timeout elapsed during sleep).
- The node must re-establish connectivity.

### 5.2 Sleep behavior (normative)

```text
device sleep detected (screen off / OS suspend / Doze)
    ↓
[node lifecycle layer enters SUSPENDED]
    ↓
[no proactive Link teardown — the OS suspends the process;
 Links will die naturally via liveness timeout or transport teardown]
    ↓
[TransportSession state is NOT persisted across sleep — it lives in
 process memory; if the process survives sleep, the TransportSession
 survives; if the OS kills the process, N2.4-04 §7.5 source-restart
 semantics apply (new TSID + new root)]
    ↓
[Link state is NOT persisted (N2.4-05 §7.4) — on wake, fresh Links
 are established via fresh SNP-IK/0.1 handshakes]
```

**Normative rules:**
- The node MUST NOT attempt to keep Links alive during sleep. OS power
  management will suspend the network stack; fighting it drains battery and
  may violate platform policy (Android Doze, iOS background rules).
- The node MAY register for wake-up notifications (Android `AlarmManager`,
  iOS `BGTaskScheduler`, macOS `NSWorkspaceDidWakeNotification`) to re-establish
  connectivity promptly on wake. This is a platform concern (L9), not an L8
  concern.
- The node MUST NOT assume Links survive sleep. On wake, the node treats all
  pre-sleep Links as Dead (they either timed out during sleep or were reset by
  the OS). Fresh Links are established.

### 5.3 Wake behavior (normative)

```text
device wake detected
    ↓
[node lifecycle layer exits SUSPENDED → ACTIVE or BACKGROUND]
    ↓
[all pre-sleep Links are Dead — treat as Link deaths]
    ↓
[N2.4-05 §7.4: fresh transport connections; fresh SNP-IK/0.1 handshakes]
    ↓
[if process survived sleep:
    TransportSession survives (existing TSID, existing root key);
    circuits recover via N2.4-04 R0/R1/R2 (new circuit_id, fresh keys,
    same TSID — the session is continuous within the same process runtime)]
    ↓
[if process was killed during sleep (OS memory pressure):
    N2.4-04 §7.5: source restart — new TSID + new root;
    fresh transport-session binding; fresh circuits]
    ↓
[routing layer re-discovers routes over the new Links]
    ↓
node returns to ACTIVE (or DEGRADED if some Links cannot be re-established)
```

**Key distinction:** sleep ≠ process restart. If the process survives sleep
(common on desktop, less common on mobile), the TransportSession is continuous
(same TSID, same root key) — only Links and circuits are replaced. If the OS
kills the process during sleep, N2.4-04 §7.5 source-restart semantics apply
(new TSID + new root).

## 6. Background Suspension

### 6.1 The problem

Mobile OSes restrict background processes:
- **Android (Doze / App Standby):** background processes are restricted to
  limited network windows (maintenance windows). Sustained background relaying
  requires a foreground service with a persistent notification
  (`FOREGROUND_SERVICE_DATA_SYNC` + `FOREGROUND_SERVICE_CONNECTED_DEVICE` on
  Android 14+). Without a foreground service, Links will time out.
- **iOS:** background execution is severely restricted. Background sockets are
  suspended. `NEPacketTunnelProvider` provides Mode C for the device's own
  traffic but cannot serve as a relay/gateway for other nodes. Background
  MultipeerConnectivity is limited.
- **macOS (App Nap):** backgrounded apps may have their timers throttled.
- **Windows (Modern Standby):** connected standby may maintain network but
  timers are throttled.

### 6.2 Architecture (normative)

Background suspension is a **platform event** that the node lifecycle layer
maps to `NodeLifecycleState` transitions:

```text
OS backgrounds the process (no foreground service, or Doze, or iOS background)
    ↓
[node lifecycle layer enters BACKGROUND]
    ↓
[Links may be suspended — keepalives may not be delivered;
 Link liveness degrades (N2.4-05 §7: Live → Degraded → Dead)]
    ↓
[the node SHOULD NOT initiate new circuits while in BACKGROUND
 (they may fail mid-establishment when the OS suspends the process)]
    ↓
[existing TransportSessions are preserved (in process memory);
 if the process is killed, N2.4-04 §7.5 applies]
    ↓
[when the process returns to foreground:
 node exits BACKGROUND → ACTIVE;
 fresh Links established; circuits recovered via N2.4-04]
```

### 6.3 Platform-specific behavior contracts (normative boundary)

N2.4-06 defines the **contract** each platform must satisfy. Implementation
is deferred to L9 adapters (platform-specific code, per invariant I11).

| Platform | Background contract | Relay/gateway in background |
|----------|--------------------|-----------------------------|
| Android (with FGS) | Foreground service keeps the process alive; Links survive background | ✅ Permitted (FGS + notification required) |
| Android (without FGS) | Doze restricts network; Links degrade | ❌ Not sustainable; node enters BACKGROUND then DISCONNECTED |
| iOS | Background sockets suspended; Links die | ❌ iOS is client-only for mesh (spec/03-PLATFORM-MATRIX.md:98) |
| macOS | App Nap throttles timers; Links may degrade | ⚠️ Laptops sleep — poor COMMUNITY_RELAY |
| Windows | Modern Standby may maintain network | ⚠️ Timers throttled; Links may degrade |
| Linux/RPi | systemd; full background control | ✅ Reference platform — always-on |

### 6.4 Foreground service requirement (normative for Android)

A node acting as `RELAY` or `INTERNET_GATEWAY` on Android MUST run a foreground
service with a persistent notification (spec/03-PLATFORM-MATRIX.md:55). Without
it, the OS will suspend the process during Doze, Links will time out, and the
node will enter DISCONNECTED. This is a platform requirement, not an
architectural choice — N2.4-06 defines the contract; the Android L9 adapter
implements it.

### 6.5 Graceful degradation ladder (normative)

When a mobile node cannot sustain its current capability level, it degrades
along the ladder from spec/03-PLATFORM-MATRIX.md:158–168:

```text
Mode C transparent
   ↓ no TUN permission / VpnService denied / iOS background
Mode B proxied (app must honour proxy settings)
   ↓ no persistent connection / no background execution
Mode A delay-tolerant (works everywhere)
   ↓ no gateway reachable at all
Class A content only — cached objects, offline catalog, local apps
   ↓ no peers
Fully offline — local storage only
```

**Normative rule:** every level MUST be reachable and MUST be honestly labelled
in the UI. A user on Mode A MUST know their traffic is delayed and, if
`GATEWAY_PLAINTEXT`, that a named gateway operator can read it. Silent
degradation across the `PAYLOAD_E2E` → `GATEWAY_PLAINTEXT` boundary is a
forbidden architectural change (spec/03-PLATFORM-MATRIX.md:170).

The mobile node lifecycle layer triggers degradation when:
- Links die (Link Layer → Dead) and cannot be re-established within
  `DEGRADED_TIMEOUT`.
- The OS suspends the process (BACKGROUND → SUSPENDED).
- No gateway is reachable (all gateway authorizations expired/revoked or no
  route to any gateway).

## 7. Process Restart

### 7.1 The problem

A mobile process may be killed and restarted by the OS (memory pressure, user
swipe-away, crash, OS update). On restart:
- All Links are gone (N2.4-05 §7.4).
- All circuits are gone (the source's ephemeral X25519 secret is lost).
- TransportSession state: N2.4-04 §7.5 mandates new TSID + new root (the old
  session dies; a new session is created).

### 7.2 Restart procedure (normative)

```text
process restart
    ↓
[node lifecycle layer starts fresh]
    ↓
[persisted state recovered per N2.4-02 invariant #11:
    - previous_session_id (old TSID, bookkeeping only — authorizes NOTHING)
    - destination descriptors
    - recovery_budget (inherited, no reset)
    - node identity (Ed25519 key — persisted via platform key store)]
    ↓
[N2.4-05 §7.4: fresh transport connections; fresh SNP-IK/0.1 handshakes]
    ↓
[N2.4-04 §7.5: new TSID + new SessionBindingRootKey; fresh transport-session
    binding at the gateway (old binding expires normally)]
    ↓
[routing layer discovers routes over the new Links]
    ↓
[new circuits established as needed (R0/R1/R2 per N2.4-04)]
    ↓
node enters ACTIVE
```

### 7.3 What does NOT survive restart

- Links (N2.4-05 §7.4 — no Link persistence).
- Circuits (fresh circuit_id, fresh keys per N2.4-04).
- TransportSession identity (new TSID + new root per N2.4-04 §7.5).
- Pending Mode-A request bodies (N2.4-04 §7.5.1 — ShareNet MUST NOT
  reconstruct application requests from session metadata).

### 7.4 What DOES survive restart

- Node identity (Ed25519 key — persisted via platform key store:
  Android Keystore, iOS Secure Enclave, TPM, etc.).
- `previous_session_id` (old TSID — bookkeeping only, authorizes NOTHING).
- Destination descriptors.
- `recovery_budget` (inherited — no restart-based budget reset).
- Authorization state (N2.4-02 invariant #11 — security-critical state
  persists across restart).

## 8. Link Replacement and TransportSession Survival

### 8.1 The hierarchy of survival

N2.4-06 coordinates the hierarchy of survival across mobility events. This
hierarchy is derived from N2.4-04 and N2.4-05:

```text
TransportSession (N2.4-04)
    survives: Link replacement, circuit replacement (R0/R1/R2)
    dies on:  source process restart (new TSID + new root)

Circuit (N2.3 frozen)
    survives: Link replacement (via N2.4-04 R1 — new circuit_id + fresh keys
              on a new Link to the same gateway)
    dies on:  circuit expiry, sequence exhaustion, teardown, relay/gateway
              failure, source process restart

Link (N2.4-05)
    survives: nothing below it (it IS the bottom of the ShareNet stack)
    dies on:  transport teardown, liveness timeout, sleep, process restart
```

### 8.2 Link replacement ≠ TransportSession replacement (normative)

This is the key invariant from N2.4-05 §7.4, restated for the mobile context:

- A **Link replacement** (old Link dies, new Link established on the same
  gateway) triggers circuit recovery (N2.4-04 R1) but the TransportSession
  survives (same TSID, same root key — the session is continuous within the
  same process runtime). This is the common case for mobile IP changes.
- A **TransportSession replacement** (new TSID + new root) happens only on
  source process restart (N2.4-04 §7.5). This is the case for OS-killed
  processes.

The mobile node lifecycle layer MUST NOT confuse these two. An IP change is a
Link replacement (session survives). A process kill is a TransportSession
replacement (session dies, new session created).

## 9. Relay / Gateway Availability Changes

### 9.1 Relay disappears

When an intermediate relay on a circuit's route disappears (N2.4-04 F1/F2):
- The Link to that relay goes Dead (N2.4-05 liveness).
- The circuit using that Link fails (in-flight packets lost).
- N2.4-04 R1 recovery: new route to the same gateway (avoiding the failed
  relay) + new circuit + RESUME (TransportSession survives).

This is handled entirely by N2.4-04 + N2.4-05. The mobile node lifecycle layer
observes the recovery event; it does not initiate a separate mechanism.

### 9.2 Gateway becomes unavailable

When the gateway is unreachable (F3: gateway offline; F4: authorization
expired; F5: authorization revoked; F6: scope change):
- All Links to that gateway go Dead.
- All circuits to that gateway fail.
- N2.4-04 R2 recovery: select a different gateway (full N2.4-03 §8.2
  selection ordering) + new route + new circuit + new transport-session
  binding at the new gateway.
- For Mode B: the outbound TCP is RST (the origin-side socket lived on the
  old gateway — honest reset, §8.2 N2.4-04).
- For Mode A: the pending request is re-issued subject to idempotence
  (§10.4 N2.4-04).

### 9.3 Node role changes during mobility

A mobile node may change role as it moves:
- A node that was a `RELAY` may lose background execution capability (OS
  background suspension) and must degrade (§6.5).
- A node that was an `INTERNET_GATEWAY` may lose its Internet connection
  (Wi-Fi → cellular with no data plan) and must cease gateway operation.
- A node that was a `MESH_CLIENT` may gain a stable Wi-Fi connection and
  upgrade to `RELAY`.

Role changes are governed by N2.4-02 (capability authorization). The mobile
node lifecycle layer triggers a role re-evaluation when:
- The node's network capability changes (Links die/are established).
- The OS suspends/restores the process.
- The node's authorization expires or is revoked.

**Normative rule:** a node MUST NOT advertise a capability it cannot sustain
(invariant I12, spec/06-CONFORMANCE-AND-AI-MODEL.md:171). If the OS
suspends the process, the node MUST withdraw its relay/gateway advertisement
before or upon entering SUSPENDED.

## 10. Temporary Disconnects

### 10.1 The problem

A mobile device may lose connectivity temporarily (entering an elevator,
driving through a tunnel, brief Wi-Fi dropout). The disconnect is short enough
that the process is not killed, but long enough that Links time out.

### 10.2 Architecture (normative)

```text
temporary disconnect (all Links Dead)
    ↓
[node lifecycle layer enters DISCONNECTED]
    ↓
[TransportSession survives (process is alive — same TSID, same root)]
[Link state is gone (N2.4-05 §7.4 — no Link persistence)]
[Circuits are gone (relays reject packets — UnknownCircuit)]
    ↓
[network restored]
    ↓
[fresh Links established (fresh SNP-IK/0.1 handshakes)]
    ↓
[N2.4-04: circuits recovered (R1 if same gateway reachable; R2 if
    different gateway needed); TransportSession survives (same TSID,
    new circuit — the session is continuous within the same process runtime)]
    ↓
node returns to ACTIVE
```

**Recovery budget interaction:** each disconnect-recovery cycle MAY consume
recovery budget (N2.4-04 §13). If the budget is exhausted, the
TransportSession transitions to FAILED (Mode A: error returned; Mode B: TCP
RST). The budget resets after a sustained ACTIVE period (default 60s).

### 10.3 Short disconnects (Link liveness tolerance)

If the disconnect is shorter than `DEGRADED_TIMEOUT` (N2.4-05 §7.1, default
3 × `KEEPALIVE_INTERVAL`), some Links MAY still be Degraded (not yet Dead).
The node lifecycle layer enters DEGRADED (not DISCONNECTED), and Links may
recover without full re-establishment. This is transport-dependent:
- TCP: the TCP connection may still be alive (OS TCP keepalive); the Link's
  AEAD keepalive resumes.
- UDP/BLE: the Link is likely Dead (datagram loss for > `DEGRADED_TIMEOUT`).

## 11. Platform Integration Boundary

### 11.1 What N2.4-06 defines (normative)

N2.4-06 defines the **mobile node lifecycle contract** — the states,
transitions, and interactions with N2.4-04/N2.4-05 that every platform must
satisfy. This is platform-neutral (same L8/L9 separation as N2.4-05).

### 11.2 What N2.4-06 does NOT define (deferred to L9)

- Platform-specific wake-up mechanisms (Android `AlarmManager`, iOS
  `BGTaskScheduler`, macOS `NSWorkspaceDidWakeNotification`).
- Platform-specific foreground service implementation (Android
  `FOREGROUND_SERVICE_DATA_SYNC`, notification UI).
- Platform-specific background detection (Android `PROCESS_STATE_IMPORTANT_*`,
  iOS `applicationDidEnterBackground`).
- Platform-specific key storage (Android Keystore, iOS Secure Enclave, TPM).
- Platform-specific network change detection (Android `ConnectivityManager`,
  iOS `NWPathMonitor`, Linux `netlink`).
- Mode C TUN/VPN integration (deferred to N2.7+).

### 11.3 Platform event → lifecycle state mapping (normative)

| Platform event | Lifecycle state transition | ShareNet action |
|----------------|---------------------------|-----------------|
| Screen on / app foreground | → ACTIVE | Re-establish Links; recover circuits |
| Screen off / app background | → BACKGROUND | Reduce activity; let Links degrade |
| Doze / App Nap / suspend | → SUSPENDED | No proactive action (OS suspends process) |
| Network change (IP/Wi-Fi/cell) | Link replacement (N2.4-05) | Fresh Links; circuit recovery (N2.4-04) |
| Network lost | → DISCONNECTED | All Links Dead; TransportSession in RECOVERING_PREPARE |
| Process killed | → (restart) | New TSID + new root (N2.4-04 §7.5) |
| Process restart | → ACTIVE (fresh) | Full re-establishment from persisted state |
| Authorization expired/revoked | Gateway unavailable (N2.4-03 §15) | R2 recovery to different gateway |
| Role capability lost | Role re-evaluation (N2.4-02) | Withdraw advertisement; degrade (§6.5) |

## 12. Security Invariants

1. **N2.3 packet semantics are immutable.** N2.4-06 introduces no new wire
   format, AAD, nonce, or packet field. Mobility is handled above and below
   the circuit layer.
2. **Mobility is Link replacement, not circuit migration.** An IP change
   replaces Links (N2.4-05); circuits are replaced (new circuit_id, fresh
   keys, N2.4-04 R1/R2); the TransportSession survives (if the process
   survived). No `circuit_id` is reused across mobility events.
3. **Process restart creates a new TSID.** Consistent with N2.4-04 §7.5:
   the old session dies; a new TSID + new root are established. The prior
   TSID becomes `previous_session_id` (bookkeeping only, authorizes nothing).
4. **QUIC migration does not substitute peer identity.** Per N2.4-05 §10.2
   invariant: IP endpoint change ≠ NodeId change. A migrated QUIC connection
   remains authenticated to the same ShareNet node.
5. **Background suspension is honestly reported.** Silent degradation across
   `PAYLOAD_E2E` → `GATEWAY_PLAINTEXT` is forbidden (spec/03 §8). The user
   MUST be informed when the node degrades (Mode C → Mode B → Mode A →
   offline).
6. **A node MUST NOT advertise a capability it cannot sustain.** Invariant
   I12. If the OS suspends the process, the node MUST withdraw its
   relay/gateway advertisement before or upon entering SUSPENDED.
7. **No Link persistence across sleep/restart.** Per N2.4-05 §7.4: Link
   state (link_key, sequence, replay window) is transport-scoped and not
   persisted. On wake/restart, fresh SNP-IK/0.1 handshakes establish fresh
   Links.
8. **Recovery budget is inherited across restart.** Per N2.4-04 §7.5: a
   restart does not grant a fresh budget. This prevents restart-based budget
   reset abuse.
9. **TransportSession survives Link replacement.** Per N2.4-04 §7.4 and
   N2.4-05 §7.4: an IP change (Link replacement) does NOT kill the
   TransportSession (if the process survived). Only a process restart kills
   the TransportSession.
10. **The frozen N2.3 circuit layer is unaware of mobility.** The circuit
    layer produces V1/V2 packets as before; mobility events cause circuit
    replacement (new circuit_id, fresh keys) but do not modify the packet
    format or its semantics.
11. **No `PacketProfile::V3`.** N2.4-06 does not introduce in-band mobility
    signaling. Any such mechanism would require a new profile (deferred to
    N2.4-07).
12. **Mode-A reissue after restart requires the complete request.** Per
    N2.4-04 §7.5.1: ShareNet MUST NOT reconstruct application payloads from
    `previous_session_id + destination`. The application or a durable request
    queue must provide the complete request.

## 15. Implementation Boundaries

N2.4-06 defines the **architecture**. Implementation will produce:

- Mobile node lifecycle state machine (platform-neutral, L8 coordination)
- Platform event → lifecycle state mapping (L9 adapters)
- Sleep/wake handling (L9: wake-up registration, Link re-establishment)
- Background suspension handling (L9: foreground service, degradation)
- IP/address change detection (L9: network change callbacks)
- Role re-evaluation on capability change (L6/N2.4-02 coordination)

Implementation is **blocked** until:
- N2.4-06 is approved
- N2.4-07 (PacketProfile V3 Decision) is at least evaluated (to confirm
  no wire-format changes are needed)
- Conformance vectors are defined

**N2.3 frozen implementation MUST NOT be modified.**

Implementation MUST NOT:
- Modify V1/V2 packet format, AAD, nonce, or golden vectors (frozen N2.3).
- Introduce in-band mobility signaling in the circuit packet (requires
  `PacketProfile::V3`, N2.4-07).
- Keep Links alive during sleep (OS power management; §5).
- Silently degrade across `PAYLOAD_E2E` → `GATEWAY_PLAINTEXT` (§6.5).
- Advertise a capability the platform cannot sustain (invariant I12).
- Reuse a TSID across process restart (N2.4-04 §7.5).
- Reconstruct application requests from session metadata (N2.4-04 §7.5.1).
