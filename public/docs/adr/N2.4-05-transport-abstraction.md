## 1. Problem Statement

N2.4-04 established the **Transport Session Layer** — the abstraction that gives
applications continuity across circuit replacement (`TransportSession`, TSID,
`SessionBindingEpoch`, `SessionBindingKey`, RESUME). That layer sits **above**
the circuit layer and treats circuits as replaceable units.

But beneath the circuit layer lies another boundary: the actual one-hop
**transport** that carries bytes between two ShareNet nodes — TCP today, but
intended also to span QUIC, UDP, Bluetooth, Wi-Fi Direct, local mesh links, and
future transports (charter §4.3). The current Rust reference implements only TCP
(`AsyncTcpTransportProvider`); BLE, Wi-Fi Direct, and NearbyConnections are
stub strings; QUIC and UDP are absent entirely. The `TransportProvider` /
`TransportConnection` traits are connection-oriented and awkward for
datagram-oriented transports (BLE GATT, LoRa).

N2.4-05 defines the **L8 Transport Abstraction** — the stable `Link` trait
boundary that all platform transports implement, and that the circuit layer
(L6/N2.3) and session layer (N2.4-04) sit above. This is the layer that makes
ShareNet transport-independent: a circuit operates over a `Link`, and a `Link`
may be backed by TCP, QUIC, BLE, Wi-Fi Direct, or a future transport, without
the circuit or session layer changing.

### The non-negotiable constraint

> **N2.4-05 MUST NOT modify the frozen N2.3 packet semantics.**

N2.4-05 defines the transport boundary **beneath** the circuit layer. It does
not touch V1/V2 packet format, AAD, nonce, replay ordering, or golden vectors.
It introduces no `PacketProfile::V3` (deferred to N2.4-07). The frozen circuit
layer operates over a `Link` exactly as it operated over a TCP socket before;
the `Link` trait is the abstraction that makes this transparent.

## 3. The Link Trait

### 3.1 Core contract

A `Link` is a **single-hop authenticated byte transport** between exactly two
ShareNet nodes. It is the unit over which circuit packets (V1/V2) are sent.

```text
Link {
    // identity (established at handshake, not at Link construction)
    local_endpoint:       TransportEndpoint,
    peer_endpoint:         TransportEndpoint,
    peer_node_id:          NodeId,              // authenticated via SNP-IK/0.1

    // transport classification
    transport_kind:        LinkTransportKind,   // "tcp" | "quic" | "udp" | "ble" | "wifi-direct" | "nearby" | "lora" | ...
    link_mode:             LinkMode,            // Stream | Datagram (§4)

    // properties
    mtu:                   u32,                  // max frame payload (§6)
    supports_ordering:     bool,                 // Stream = true; Datagram = false (unless underlying transport orders)
    is_reliable:           bool,                 // Stream = true; Datagram = false
    is_full_duplex:        bool,                 // can send + receive concurrently

    // liveness
    last_seen:             u64,                  // unix seconds, updated on any frame
    liveness_state:        LivenessState,        // Live | Degraded | Dead (§7)

    // keying (from SNP-IK/0.1 handshake — ADR-0003/0006/0011)
    link_key:              LinkKey,             // per-link AEAD key (ChaCha20-Poly1305)
}
```

A `Link` is **NOT** a route. It is **NOT** aware of circuits, relays, gateways,
or destinations. It carries framed bytes between two authenticated endpoints
and reports liveness. The circuit layer multiplexes circuit packets over
`Link`s; the routing layer (L6) selects which `Link` to use for the next hop.

### 3.2 What a Link is NOT

- **Not a connection in the TCP sense.** A `Link` is the ShareNet abstraction;
  its underlying transport may be connection-oriented (TCP, QUIC stream) or
  connectionless (UDP, BLE GATT). The `Link` unifies them.
- **Not node-addressed.** The `Link` knows its two endpoints
  (`local_endpoint`, `peer_endpoint`) and the authenticated `peer_node_id`, but
  it does NOT know any other node's address, does NOT perform routing, and does
  NOT advertise reachability beyond one hop (spec/01-ARCHITECTURE.md:89).
- **Not route-aware.** A `Link` does not interpret route semantics, destination
  meaning, or circuit membership. It carries frames that may belong to many
  circuits (multiplexed, §8); the `circuit_id` in a frame header is an **opaque
  demultiplexing key** to L8, not a routing identifier. See §8.2 for the
  LinkMultiplexer boundary that consumes `circuit_id` without interpreting its
  meaning. Framing is transport-scoped; circuit packets are opaque payloads to
  the Link.
- **Not platform-specific.** The `Link` trait is platform-neutral
  (`LinkTransportKind` is a string enum, not a platform type — invariant I11).
  Platform-specific code (Android `VpnService`, iOS `NEPacketTunnelProvider`,
  Linux `/dev/net/tun`, BlueZ, CoreBluetooth) lives in L9 adapters
  (spec/06-CONFORMANCE-AND-AI-MODEL.md:170, I11).

### 3.3 Link lifecycle

```
LinkListener::accept()  (inbound)  OR  TransportProvider::connect()  (outbound)
    ↓
[transport connection established — TCP connect / QUIC stream / BLE GATT attach / ...]
    ↓
SNP-IK/0.1 handshake (ADR-0003/0006) — authenticates peer_node_id, derives link_key
    ↓
(no auto-accept — handshake must complete; ADR-0003 I20: stubs throw, never permissive)
    ↓
EstablishedLink  (AEAD frames via ChaCha20-Poly1305, per-link key, §4.4 sequence lifecycle)
    ↓
[Link carries LinkFrames — demultiplexed by LinkMultiplexer to circuits, §8.2]
    ↓
[link liveness monitored — keepalive / probe, §7]
    ↓
LinkClose  (transport teardown, liveness timeout, or peer-disconnect)
    ↓
[LinkKey erased; link state discarded — NOT persisted (N2.1.1 §20.1, §7.4)]
    ↓
[LinkMultiplexer unregisters all circuits that were using this Link;
 affected circuits recover via N2.4-04 R1/R2]
```

## 4. Stream vs Datagram Transport Classification

### 4.1 The two LinkModes

Transports divide into two fundamental classes:

| LinkMode | Underlying transports | Properties |
|----------|----------------------|------------|
| **Stream** | TCP, QUIC (stream), TLS, Unix socket | Ordered, reliable, byte-stream. Framing is the Link's responsibility (length-prefixed frames). `supports_ordering = true`, `is_reliable = true`. |
| **Datagram** | UDP, QUIC (datagram), BLE GATT, LoRa, Wi-Fi Direct (datagram mode) | Unordered (or best-effort ordered), unreliable, message-oriented. Framing is native (one datagram = one frame). `supports_ordering = false` (unless transport guarantees ordering), `is_reliable = false`. |

### 4.2 Framing contract (normative)

- **Stream transports:** the `Link` MUST apply length-prefixed AEAD framing.
  Each frame is `len(u32) || AEAD(link_key, nonce, frame_header || payload)`.
  The frame header carries the transport-scoped sequence number for the AEAD
  nonce (§4.4 sequence lifecycle). This is the existing `snp-link` framing
  strategy; it stays.
- **Datagram transports:** the `Link` MAY use native datagram boundaries (one
  datagram = one AEAD frame). The AEAD nonce is still per-link, transport-scoped
  sequence (§4.4). For UDP/QUIC-datagram, the Link MUST handle reordering and
  loss at the link-AEAD layer (replay window, like the circuit layer's but
  transport-scoped) — this is independent of the circuit-layer replay window
  (which is per-circuit, frozen N2.3). The Link's replay window is specified
  in §4.4.
- **Framing vs circuit packet:** the Link frame `payload` is the frozen N2.3
  V1/V2 circuit packet (opaque bytes to the Link). The Link does NOT inspect
  circuit packet fields; the LinkMultiplexer (§8.2) reads only the
  Link-frame-header `circuit_id` for demux. Circuit packet size, transport
  frame size, and transport fragment size (§4.5) are distinct.

### 4.3 MTU exposure and Link-layer fragmentation (normative)

Each `Link` exposes its `mtu` (max transport fragment payload in bytes) to
inform Link-layer fragmentation (§4.5). **The frozen N2.3 circuit layer is
unaware of individual transport MTUs** — N2.4-05 resolves the MTU question via
**Architecture B (Link fragmentation/reassembly)**:

```text
frozen N2.3 CircuitPacket (up to N2.3 max payload)
    ↓
authenticated LinkFrame (Link AEAD, §4.4)
    ↓
Link fragmentation/reassembly (§4.5) — L8-only
    ↓
transport fragments (≤ transport MTU)
```

**Normative rules:**
- The frozen N2.3 circuit layer MUST remain unaware of individual transport
  MTUs. N2.4-05 MUST NOT modify N2.3 `PayloadTooLarge` / path-MTU semantics.
- L8 MAY fragment a complete authenticated `LinkFrame` into transport fragments
  for transports whose MTU is smaller than the LinkFrame (BLE, LoRa, UDP with
  small path MTU).
- Reassembly MUST happen **before** delivery of the complete `LinkFrame` to the
  `LinkMultiplexer` (§8.2) and ultimately to the circuit layer. The circuit
  layer receives only complete, authenticated circuit packets.
- **Distinct sizes (normative):**
  - `circuit packet size` = the frozen N2.3 V1/V2 circuit packet size (up to
    N2.3 max payload, unchanged by N2.4-05).
  - `transport frame size` = the authenticated `LinkFrame` size (circuit packet
    + Link frame header + AEAD overhead).
  - `transport fragment size` = the size of each fragment's **wire encoding**
    after Link-layer fragmentation.
  - These are distinct; confusing them would silently modify N2.3.

**Fragment wire-size accounting (normative):** the fragment sent over the
transport contains more than its plaintext payload — it also contains a
fragment header and the AEAD authentication tag. A plaintext payload equal to
the MTU would necessarily produce a wire fragment **larger than the MTU**,
violating the transport contract. The fragmenter MUST account for the full
wire size:

```text
fragment_wire_size =
    fragment_header_bytes           // fixed per LinkFragmentProfile (§4.5.5)
    + ciphertext_payload_length     // == plaintext_payload_length (AEAD is
                                    //    non-expanding for ChaCha20-Poly1305)
    + AEAD_TAG_BYTES                // 16 bytes (ChaCha20-Poly1305 tag)

require:  fragment_wire_size <= actual_transport_mtu

therefore the maximum plaintext fragment payload is:

    max_fragment_payload =
        actual_transport_mtu
        - fragment_header_bytes
        - AEAD_TAG_BYTES
```

The fragmenter MUST use `max_fragment_payload` (not the raw transport MTU) as
the maximum plaintext payload per fragment. A fragment that would produce a
wire size exceeding the actual transport MTU MUST be rejected before
transmission. This is normative because BLE/LoRa/etc. depend on it — a
fragment that exceeds the transport MTU is silently lost or truncated.

- If a future optimization wants path-MTU-aware circuit packet sizing, that is
  a **new circuit/profile decision** (e.g., `PacketProfile::V3`, N2.4-07), NOT
  a silent modification of N2.3 packet generation based on transport MTU.

**Per-transport Link MTU defaults (normative for the Link contract):**

`LinkMtu` is defined as **the maximum wire-fragment size that the Link
guarantees can be delivered as one transport unit** — not necessarily the
network interface/path MTU. The Link uses `LinkMtu` to determine fragmentation
feasibility (§4.5.3). This is distinct from:
- **Network/path MTU** — the maximum IP packet size on the network path (a
  network-layer concept, not directly used by L8).
- **Transport unit limit** — the maximum message/datagram size the transport
  accepts (e.g., UDP datagram max, BLE ATT_MTU).
- **Link fragmentation MTU** (`LinkMtu`) — the maximum wire-fragment size L8
  uses for fragmenting `LinkFrame`s.

For **datagram transports** (UDP, BLE GATT, LoRa, Wi-Fi Direct, QUIC datagram):
`LinkMtu` = the maximum datagram wire size (the transport unit limit).

For **stream transports** (TCP, QUIC stream): the underlying stream has **no
equivalent per-message datagram MTU** — the stream carries arbitrarily sized
framed data. L8 framing can carry arbitrarily sized `LinkFrame`s subject to
`MAX_LINK_FRAME_BYTES` (§4.5.6), and stream transport segmentation is handled by
the stream itself. The `LinkMtu` for a stream transport is therefore **not a
network path MTU** but a practical framing choice: the Link MAY set `LinkMtu` to
a large value (e.g., 65535) to avoid unnecessary fragmentation, or MAY set it
lower to bound memory per frame. The Link MUST NOT present a stream
`LinkMtu` as a network path MTU — TCP's 65535 is a framing choice, not the
network path MTU.

**Per-transport LinkMtu defaults:**
- TCP / QUIC stream: 65535 (practical framing choice; the Link MAY negotiate
  lower. This is NOT the network path MTU — the stream carries arbitrarily
  sized framed data; L8 fragmentation is unnecessary unless the LinkFrame
  exceeds this practical framing bound or `MAX_LINK_FRAME_BYTES`)
- UDP: 1400 (conservative; avoids common path MTU issues. This IS the
  transport datagram unit limit)
- BLE GATT: 244 (ATT_MTU 247 minus 3 header; conservative. This IS the BLE
  transport unit limit)
- Wi-Fi Direct: 1400 (treat like UDP until measured)
- LoRa: 51–242 (region/bandwidth-dependent; the Link MUST expose the actual
  value, not a default. This IS the LoRa transport unit limit)

The Link MUST expose the **actual** `LinkMtu` (measured or negotiated with the
transport, or the practical framing choice for streams), not a hardcoded
default. A Link that lies about its `LinkMtu` causes silent packet loss
downstream.

### 4.4 Link sequence / nonce lifecycle (normative)

The Link AEAD introduces a transport-scoped sequence number and replay window.
This is a new security-sensitive protocol; its lifecycle MUST be specified
with the same fail-closed discipline as frozen N2.3 (per N2.3-V1-CONFORMANCE
replay-window invariants), explicitly separate from the N2.3 circuit sequence.

**LinkTxSequence (per direction, per Link):**

- **First sequence = 1.** (Matches N2.3 `FIRST_PACKET_SEQ`.)
- **Monotonically increases** per direction per Link. Never decreases.
- **u32::MAX is the last usable sequence number.**
- **Next send after u32::MAX = `LinkSequenceExhausted`.** The Link MUST be torn
  down and re-established (fresh SNP-IK/0.1 handshake, fresh `link_key`, fresh
  sequence space starting at 1) before further traffic.
- **NEVER wraps to 0.** Wrapping would reuse an AEAD nonce under the same
  `link_key` — catastrophic for ChaCha20-Poly1305. This mirrors the frozen
  N2.3 no-wraparound invariant (N2.3-V1-CONFORMANCE:76–78).
- **Pre-flight failure vs post-reservation failure (normative):** the rule
  for sequence consumption distinguishes pre-flight validation from
  post-reservation cryptographic construction:
  - **Pre-flight failure** (e.g., frame exceeds `effective_max_frame_for_link`
    (§4.5.3), oversize payload rejected, insufficient sequence space before
    reservation (§4.5.8)): the frame is rejected **before** any sequence is
    reserved. No sequence is consumed. This matches the N2.3 principle: a
    failed packet construction MUST NOT consume a sequence number.
  - **Successful reservation** (§4.5.8 step 4): the complete sequence range
    `[s, s + fragment_count - 1]` is **permanently consumed** for the logical
    frame. Once reserved, these sequences are consumed regardless of what
    happens next.
  - **Post-reservation failure** (AEAD/construction error after the range is
    reserved): zero fragments of that logical frame are transmitted, but the
    **reserved sequences remain consumed** — they MUST NOT roll back. The
    frame is discarded; the caller handles the failure. This is consistent
    with the replay-no-rollback rule (§4.5.7): sequences committed to a
    logical frame are irrevocably consumed.
  - **Transport loss after construction** (datagram fragment lost in transit):
    sequences remain consumed (§4.5.7).
  - **Never permit partial logical-frame transmission** due to sequence
    exhaustion or post-reservation construction failure.

  For fragmented frames (§4.5), each fragment consumes exactly one Link
  transmit sequence number (the fragment's AEAD uses that sequence as its
  nonce input); a logical LinkFrame spanning N fragments consumes N
  consecutive sequence numbers. See §4.5.1 and §4.5.8 for the
  fragment-AEAD nonce model and the full reservation lifecycle.

**Directional sequence spaces (normative):**
- Each direction (send → receive on the peer) has an **independent** sequence
  space and replay window.
- A forward-direction sequence MUST NOT mutate the reverse-direction replay
  window, and vice versa.
- This mirrors the frozen N2.3 V2 direction-aware replay-window independence
  (ADR-0014 §4).

**Replay window (per direction, per Link):**
- **`check()` is read-only, BEFORE AEAD** (matches N2.3: check-before-AEAD).
- **`commit()` runs ONLY after successful AEAD authentication** (matches N2.3:
  commit-after-AEAD). A frame that fails AEAD MUST NOT mutate replay state.
- **Bounded O(WINDOW) update:** `LINK_REPLAY_WINDOW_SIZE` = 1024 (matches
  N2.3 `REPLAY_WINDOW_SIZE`). The commit algorithm is O(delta) ≤ O(WINDOW);
  it MUST NOT iterate the full range `max_seen..seq` (that was a CPU DoS, fixed
  in N2.3 P0 #2). The same algorithm applies here.
- **`seq == 0` → `LinkSequenceZero` (invalid).**
- **`seq == u32::MAX` → valid; the next send is `LinkSequenceExhausted`.**
- **`initialized` flag** (not a `max_seen == 0` sentinel) — matches N2.3.

**Restart / key-establishment semantics (normative):**
- A fresh `link_key` (from a fresh SNP-IK/0.1 handshake) establishes a fresh
  sequence space starting at 1. The old sequence space is discarded with the
  old `link_key`.
- After process restart (§7.4), all Links are gone; fresh handshakes establish
  fresh `link_key`s and fresh sequence spaces. Old sequence state is not
  persisted (N2.1.1 §20.1) and cannot be reused.
- **Key rotation:** N2.4-05 does NOT define in-place key rotation for a live
  Link. If the Link sequence approaches exhaustion (u32::MAX), the Link MUST be
  torn down and re-established with a fresh handshake (teardown +
  re-establishment, mirroring the N2.3 circuit recovery model). In-place key
  rotation is a future concern (N2.4-07+, if a `PacketProfile::V3` is
  introduced) and MUST NOT be implied by implementation.

**Separation from N2.3 circuit sequence (normative):**
- The Link sequence is **transport-scoped** (per-Link, per-direction). The
  N2.3 circuit sequence is **circuit-scoped** (per-circuit, frozen).
- They are independent: a Link sequence number N on Link L does not relate to
  a circuit sequence number M on circuit C that rides Link L.
- Replay-window contamination between the two is forbidden. A Link frame that
  passes Link AEAD is then subject to the circuit's own frozen replay window.

### 4.5 Secure Link fragmentation (normative)

For transports whose MTU is smaller than the `LinkFrame` (BLE, LoRa, UDP with
small path MTU), the Link fragments the `LinkFrame` into transport fragments
and reassembles them before delivering the complete `LinkFrame` to the
`LinkMultiplexer` (§8.2). This is **Architecture B** from §4.3 — the frozen
N2.3 circuit layer is unaware of fragmentation.

**Fragmentation is security-critical.** The fragment-AEAD model, the
reassembly identity, the size consistency, and the format versioning are all
normative below. An attacker who can send arbitrary fragments must not be able
to (a) cause nonce reuse, (b) splice fragments across logical frames,
(c) cause unbounded memory, or (d) silently reinterpret the fragment format.

#### 4.5.1 Fragment-before-AEAD model (normative)

N2.4-05 uses a **fragment-before-AEAD** model. The LinkFrame plaintext is
fragmented **before** per-fragment Link AEAD — there is no "encrypt the whole
LinkFrame, then re-encrypt the fragments" double-AEAD. Each fragment is
authenticated independently under the `link_key`, and each fragment consumes
exactly one Link transmit sequence number.

```text
N2.3 CircuitPacket (frozen, opaque to L8)
    ↓
LinkFrame plaintext (circuit_id + frame metadata + circuit packet payload)
    ↓
fragment into N transport fragments (§4.5.3 size rules)
    ↓
per-fragment Link AEAD (each fragment gets its own AEAD tag under link_key)
    ↓
transport fragments (≤ transport MTU each)
    ↓ [transport]
    ↓ [reassembly — §4.5.2]
complete authenticated LinkFrame
    ↓
LinkMultiplexer (§8.2) → Circuit layer
```

**One coherent nonce lifecycle.** There is ONE sequence space per direction
per Link (§4.4). Fragments do NOT have a separate `FragmentSequence`; each
fragment consumes one Link transmit sequence. A logical LinkFrame spanning N
fragments consumes N consecutive Link sequence numbers.

**Complete sequence range reserved before transmission (normative):** because
sequence exhaustion is fail-closed at `u32::MAX` (§4.4), the sender MUST verify
that the complete fragment sequence range fits in the remaining sequence space
**before** transmitting any fragment. Partial logical-frame transmission due to
sequence exhaustion is forbidden (§4.5.8). The sender's procedure distinguishes
**pre-flight validation** (no sequence consumed on failure) from
**post-reservation construction** (sequences permanently consumed):

```text
1. pre-flight: calculate fragment_count (from LinkFrame size + max_fragment_payload, §4.3)
2. pre-flight: verify MTU/resource/size conditions (effective_max_frame_for_link, §4.5.3)
3. pre-flight: verify (current_sequence + fragment_count - 1) <= u32::MAX
   → if NOT: LinkSequenceExhausted — transmit ZERO fragments, NO sequence consumed
4. reservation: reserve/allocate the entire sequence range [s, s + fragment_count - 1]
   → sequences are now PERMANENTLY CONSUMED (irrevocable)
5. construction: construct/encrypt all N fragments (each gets its reserved sequence)
   → if construction/AEAD fails: discard the whole frame, ZERO fragments transmitted,
     reserved sequences REMAIN CONSUMED (no rollback — §4.5.7)
6. transmission: transmit fragments (order within the reserved range is
   implementation-defined; the receiver reassembles regardless of arrival order
   via ReassemblyKey, §4.5.4)
   → transport loss: sequences remain consumed (§4.5.7)
```

**Key rule (normative):** pre-flight failures (steps 1-3) consume NO sequence.
Successful reservation (step 4) permanently consumes the range. Post-reservation
failures (step 5: AEAD/construction error) and transport losses (step 6) do
NOT roll back the reservation — the sequences remain consumed. This is
consistent with the replay-no-rollback discipline (§4.5.7) and the N2.3
principle that a failed *pre-flight* construction MUST NOT consume a sequence
number. See §4.5.8 for the full lifecycle.

This prevents the failure mode where the sender transmits fragments 0 and 1,
then hits `u32::MAX` on fragment 2 and cannot complete the logical frame —
which would leave a partially-transmitted frame consuming consumed sequence
numbers with no way to complete reassembly. See §4.5.8 for the full
sequence-reservation invariant.

```text
example: a LinkFrame fragmented into 3 fragments

Link sequence 100 → fragment 0   (AEAD nonce derived from seq 100)
Link sequence 101 → fragment 1   (AEAD nonce derived from seq 101)
Link sequence 102 → fragment 2   (AEAD nonce derived from seq 102)
```

For an **unfragmented** LinkFrame (MTU is large enough), the LinkFrame is a
single fragment consuming one sequence number (fragment_index = 0,
fragment_count = 1). The fragment-AEAD model is uniform: every Link frame,
fragmented or not, is a sequence of one-or-more authenticated fragments.

#### 4.5.2 Fragment AEAD nonce and AAD (normative)

**Nonce derivation (normative — frozen, not deferred):**

The fragment AEAD nonce is derived via a **single exact HKDF-SHA256
construction**. This is normative and frozen in N2.4-05 — it is NOT deferred
to N2.5 or left as an implementation choice. Two conformant implementations
MUST derive byte-identical nonces for the same `(link_key, direction,
link_sequence)` triple.

```text
// Inputs (all normatively encoded):
//   link_key      : 32 bytes (ChaCha20-Poly1305 key from SNP-IK/0.1, §4.4)
//   direction     : 1 byte  (0x00 = Forward, 0x01 = Reverse)
//   link_sequence : 4 bytes (big-endian u32, the per-fragment Link transmit
//                            sequence number, §4.4)

nonce_material =
    "SNP/0.1/link/fragment/nonce/v1"   // 31-byte ASCII domain separator
    || direction                        // 1 byte
    || link_sequence                    // 4 bytes, big-endian u32

// HKDF-SHA256 (RFC 5869):
//   salt  = link_key (32 bytes)
//   IKM   = nonce_material (35 bytes)
//   info  = "SNP/0.1/link/fragment/nonce/v1" (31 bytes)
//   L     = 12 (ChaCha20-Poly1305 nonce length)

fragment_nonce = HKDF-SHA256(
    salt = link_key,
    IKM  = nonce_material,
    info = "SNP/0.1/link/fragment/nonce/v1",
    L    = 12
)[0..12]                              // 12-byte ChaCha20-Poly1305 nonce
```

**Normative encoding rules:**
- The domain separator `"SNP/0.1/link/fragment/nonce/v1"` is ASCII-encoded
  (31 bytes, no NUL terminator).
- `direction` is a single byte: `0x00` for Forward, `0x01` for Reverse.
- `link_sequence` is a 4-byte **big-endian** u32 (network byte order), matching
  the N2.3 sequence encoding (N2.3-V1-CONFORMANCE:55–63, `seq(BE)`).
- `link_key` is the 32-byte ChaCha20-Poly1305 key derived from the SNP-IK/0.1
  handshake (ADR-0003/0006/0011).
- HKDF-SHA256 follows RFC 5869: Extract-then-Expand. The output is 12 bytes
  (truncated from the Expand output to the ChaCha20-Poly1305 nonce length).
- The construction is **deterministic**: given the same `(link_key, direction,
  link_sequence)`, every implementation produces the same 12-byte nonce.

**Nonce uniqueness invariant (normative):** because `link_sequence` is
monotonic and never wraps (§4.4), `direction` is bound into the nonce input,
and `link_key` is unique per Link (SNP-IK/0.1), the nonce is unique per
`(link_key, direction, link_sequence)` triple. There is no nonce reuse under
the same `link_key`. This is the same fail-closed discipline N2.3 applies to
the circuit-layer nonce (N2.3-V1-CONFORMANCE:55–78); N2.4-05 applies it at
the transport layer with an exact construction.

**Fragment AEAD AAD (normative):** every fragment's AEAD additional
authenticated data MUST bind ALL of the following, so that the fragment is
cryptographically tied to exactly one logical frame and one position within it:

```text
fragment_AAD =
    protocol_domain              // e.g. "SNP/0.1/link/fragment/v1"
    || link_fragment_profile     // LinkFragmentProfile version (§4.5.5)
    || direction                 // Forward | Reverse
    || frame_sequence            // the FIRST sequence number of this logical frame
    || fragment_id              // reassembly-group identifier (see §4.5.4)
    || fragment_index           // 0-based index of this fragment
    || fragment_count           // total fragments in the group
    || original_frame_length    // declared size of the reassembled LinkFrame
    || fragment_payload_length  // byte length of this fragment's payload
```

The `frame_sequence` field is the **first** Link sequence number consumed by
this logical frame (e.g., 100 in the example above). All fragments of the same
logical frame share the same `frame_sequence`, `fragment_id`,
`fragment_count`, and `original_frame_length`; they differ only in
`fragment_index` and `fragment_payload_length` (and the per-fragment
`link_sequence` used for the nonce).

#### 4.5.3 Fragment size consistency rules (normative)

**Per-fragment wire-size bounds (normative):** the fragment's **wire size**
(header + ciphertext + AEAD tag) MUST be ≤ the actual transport MTU. The
fragmenter derives the maximum plaintext payload from the actual MTU (§4.3):

```text
max_fragment_payload =
    actual_transport_mtu
    - fragment_header_bytes     // fixed per LinkFragmentProfile
    - AEAD_TAG_BYTES            // 16 bytes (ChaCha20-Poly1305)

fragment_wire_size =
    fragment_header_bytes + ciphertext_payload_length + AEAD_TAG_BYTES

require:  fragment_wire_size <= actual_transport_mtu
          (equivalently: ciphertext_payload_length <= max_fragment_payload)
```

- A fragment whose plaintext payload exceeds `max_fragment_payload` is rejected
  before transmission (it would produce a wire fragment larger than the MTU).
- The **final fragment** MAY be smaller than `max_fragment_payload` (the last
  fragment of a frame need not be full-size).

**Effective maximum frame per Link (normative):** the absolute constants
`MAX_LINK_FRAME_BYTES` and `MAX_LINK_FRAGMENTS` are upper bounds, but a
low-MTU transport may not be able to represent a frame up to those bounds.
The **effective maximum frame for a specific Link** is:

```text
effective_max_frame_for_link =
    min(
        MAX_LINK_FRAME_BYTES,
        max_fragment_payload(mtu) * MAX_LINK_FRAGMENTS
    )
```

A logical `LinkFrame` whose size exceeds `effective_max_frame_for_link` MUST be
rejected **before transmission begins** — it cannot be represented within both
the MTU-derived fragment-payload bound and the fragment-count bound. The
sender MUST NOT begin fragmenting a frame that cannot fit. The receiver MUST
enforce the same bound (rejecting fragments declaring a larger
`original_frame_length` than the receiver's `effective_max_frame_for_link`).

**Group consistency (normative):**

```text
fragment_count           ≤ MAX_LINK_FRAGMENTS        (4096)
original_frame_length    ≤ effective_max_frame_for_link
                              (min(MAX_LINK_FRAME_BYTES,
                               max_fragment_payload(mtu) * MAX_LINK_FRAGMENTS))

on every received fragment:
    sum(received_fragment_payload_lengths)  ≤  original_frame_length

on successful completion (all fragment_count fragments received):
    sum(fragment_payload_lengths)  ==  original_frame_length
```

**Receiver-side consistency checks (normative):**
- If a fragment declares `original_frame_length > MAX_LINK_FRAME_BYTES`, the
  fragment is rejected and the reassembly group is discarded.
- If a fragment declares `original_frame_length > effective_max_frame_for_link`
  (MTU-derived, §4.5.3), the fragment is rejected and the group is discarded.
- If a fragment declares `fragment_count > MAX_LINK_FRAGMENTS`, the fragment
  is rejected and the group is discarded.
- If accumulating received fragment payload lengths would exceed the declared
  `original_frame_length`, the new fragment is rejected (overlength — the
  sender is lying or corrupt) and the group is discarded.
- On completion (all `fragment_count` fragments received), if
  `sum(fragment_payload_lengths) != original_frame_length`, the group is
  discarded (the fragments do not constitute a legal partition of the declared
  frame — defensive against an attacker who sends individually-valid fragments
  that do not sum correctly).
- No incomplete, overlapping, or overlength reassembly may reach the
  `LinkMultiplexer`. Only a fully-validated, complete, authenticated
  `LinkFrame` is delivered.

#### 4.5.4 Reassembly identity and cross-frame binding (normative)

**ReassemblyKey (normative):** the receiver groups fragments by a canonical
reassembly identity:

```text
ReassemblyKey =
    direction           // Forward | Reverse (per-direction reassembly)
    || frame_sequence   // the first sequence number of the logical frame
    || fragment_id     // reassembly-group identifier within the frame
```

The `fragment_id` disambiguates multiple logical frames that may be in flight
concurrently on the same Link (e.g., a sender transmitting frame A's fragments
interleaved with frame B's fragments). `frame_sequence` is the authoritative
identifier of the logical frame; `fragment_id` is the sub-group within it. A
sender MUST use distinct `(frame_sequence, fragment_id)` pairs for distinct
logical frames.

**Cross-frame binding (normative):** every fragment's AEAD AAD (§4.5.2)
includes `frame_sequence`, `fragment_id`, `fragment_index`, `fragment_count`,
and `original_frame_length`. This means:
- A fragment from frame X (sequence 100) CANNOT be spliced into a reassembly
  group for frame Y (sequence 200) — the `frame_sequence` in the AAD differs,
  and the AEAD tag would not verify under the wrong `frame_sequence`.
- A fragment with `fragment_index = 0` from one group CANNOT be replayed as
  `fragment_index = 0` of a different group — the `fragment_id` (and
  `frame_sequence`) in the AAD differs.

**Conflicting-metadata rejection (normative):** the receiver MUST reject a
reassembly group if any fragment's AAD-decoded metadata conflicts with
previously-received fragments of the same `ReassemblyKey`:
- conflicting `fragment_count`
- conflicting `original_frame_length`
- conflicting `direction`
- conflicting `frame_sequence`

A conflict causes the **entire group** to be discarded (defensive — the sender
is malformed or malicious).

#### 4.5.5 LinkFragmentProfile (normative)

The fragment envelope carries an explicit version/profile discriminator so
that future changes to fragment header, fragment AEAD, reassembly rules, or
size limits cannot silently reinterpret the existing format.

```text
LinkFragmentProfile::V1 = 1   // the version defined in this ADR
```

- The profile field is carried in the fragment envelope (in the fragment
  header, BEFORE the AEAD tag, so the receiver can dispatch on it before
  attempting AEAD).
- An unknown `LinkFragmentProfile` value MUST **fail closed**: the fragment is
  rejected and the reassembly group is discarded. The receiver MUST NOT
  silently reinterpret the fragment under a different profile.
- `LinkFragmentProfile` belongs to **N2.4-05 Link framing**. It does NOT modify
  the frozen N2.3 `CircuitPacket` V1/V2 or `PacketProfile` (which is a
  circuit-layer concept). The two profiles are independent: a V1 circuit
  packet may ride a V1 fragment profile; a V2 circuit packet may ride a V1
  fragment profile; future combinations are allowed as long as both profiles
  are known to the receiver.
- Future profiles (V2, V3, ...) are additive: a receiver MAY support multiple
  profiles and dispatch on the field. Adding a new profile does NOT modify V1.

#### 4.5.6 Bounded reassembly resources (normative)

An attacker who can send arbitrary fragments must not cause unbounded memory.
The following bounds are normative:

```text
MAX_LINK_FRAME_BYTES        = 1 MiB     // upper bound on reassembled frame
MAX_LINK_FRAGMENTS          = 4096      // upper bound on fragment count
REASSEMBLY_TIMEOUT          = 30 s      // incomplete reassembly discarded
MAX_CONCURRENT_REASSEMBRIES = 256       // per Link, per direction
MAX_REASSEMBLY_MEMORY       = 16 MiB     // per Link total reassembly bytes
```

**Security rules (normative):**
- **Declared frame length** ≤ `MAX_LINK_FRAME_BYTES` (§4.5.3).
- **Fragment count** ≤ `MAX_LINK_FRAGMENTS` (§4.5.3).
- **Reassembly timeout:** an incomplete reassembly group is discarded after
  `REASSEMBLY_TIMEOUT` (default 30s) without a new fragment for that group.
- **Maximum concurrent reassemblies** ≤ `MAX_CONCURRENT_REASSEMBRIES` per Link
  per direction. A new fragment group that would exceed this bound causes the
  oldest incomplete group to be discarded (bounded memory).
- **Maximum reassembly memory** ≤ `MAX_REASSEMBLY_MEMORY` per Link. If
  accumulating reassembly buffers would exceed this, incomplete groups are
  discarded oldest-first.
- **Duplicate fragment handling:** a fragment with a `ReassemblyKey +
  fragment_index` already received for the same group is a duplicate and is
  silently dropped (idempotent reassembly). The AEAD tag verifies (it is a
  replay of a valid fragment); the replay window (§4.4) also catches the
  duplicate `link_sequence`.
- **Overlap handling:** fragments MUST NOT overlap. Because each fragment
  consumes a distinct `link_sequence` and `fragment_index`, and the
  `sum(fragment_payload_lengths) == original_frame_length` check (§4.5.3)
  enforces a partition, overlap is structurally impossible in a well-formed
  group. A group that would overlap is discarded.
- **No attacker-controlled unbounded allocation.** The bounds above ensure
  that an attacker sending `fragment 0`, `fragment 65535`, `fragment 9999`, ...
  cannot cause unbounded memory — each group is bounded by
  `MAX_LINK_FRAME_BYTES` and `MAX_LINK_FRAGMENTS`, concurrent groups are
  bounded by `MAX_CONCURRENT_REASSEMBRIES`, and total reassembly is bounded by
  `MAX_REASSEMBLY_MEMORY`.

Fragmentation is transparent to the circuit layer: the circuit layer receives
only complete, authenticated circuit packets (reassembled from `LinkFrame`s).
The circuit layer does not know whether fragmentation occurred.

#### 4.5.7 Fragment loss and retransmission semantics (normative)

Every fragment consumes a Link transmit sequence number and commits replay
state after successful AEAD (§4.4). On datagram transports (UDP, BLE GATT,
LoRa, Wi-Fi Direct), fragments may be lost. N2.4-05 defines the loss/retransmission
behavior explicitly to avoid accidentally creating a second retransmission
protocol inside L8.

**Normative rule — no Link-layer fragment retransmission:**

> **N2.4-05 provides NO Link-layer fragment retransmission.** A missing
> fragment causes the reassembly group to time out and the entire incomplete
> logical `LinkFrame` to be discarded. The Link does not attempt partial
> fragment recovery. Higher layers (session/application) may recover the lost
> logical data according to their own semantics (N2.4-04 §10.3; §10.4 of
> this ADR).

```text
fragment loss (datagram transport)
    ↓
one or more fragments of a logical LinkFrame never arrive
    ↓
reassembly group remains incomplete
    ↓
REASSEMBLY_TIMEOUT (30s) elapses without a new fragment for that group
    ↓
entire incomplete LinkFrame discarded
    ↓
circuit layer never receives the frame
    ↓
higher-layer recovery (N2.4-04 session layer or application)
```

**Per-transport behavior (normative):**
- **Stream transports (TCP, QUIC stream):** the underlying transport provides
  reliability. Fragment loss at the transport level is handled by TCP
  retransmission / QUIC stream retransmission; the Link never sees a missing
  fragment. `REASSEMBLY_TIMEOUT` is a backstop for stream-transport
  disconnection, not for fragment loss.
- **Datagram transports (UDP, BLE GATT, LoRa, Wi-Fi Direct, QUIC datagram):**
  the transport does NOT guarantee delivery. Loss of **any required fragment**
  means loss of the **logical LinkFrame**. The group times out and is
  discarded. The Link does not retransmit the missing fragment; the sender's
  consumed Link sequence numbers for those fragments are spent (see §4.5.7
  replay rule below). Higher-layer recovery (N2.4-04 or application) handles
  the lost logical data.

**Why no Link-layer retransmission (architectural rationale):**
- **Link sequence = transmission authenticity/replay only.** The Link sequence
  authenticates and replay-protects each fragment; it is NOT a retransmission
  sequence. Mixing the two would create a second reliability protocol inside
  L8, conflicting with the circuit/session-layer recovery model (N2.4-04).
- **Circuit/session recovery = recovery of lost logical data.** N2.4-04 already
  defines circuit replacement (R1/R2) and the session layer defines
  application-visible recovery. Adding L8 retransmission would duplicate this
  and complicate the layering.
- **Stream transports already handle loss.** For TCP/QUIC-stream, fragment
  loss is transparent to the Link. For datagram transports, losing any
  fragment loses the frame — this is the natural semantics of an unreliable
  transport, and the Link does not paper over it.

**Replay state is never rolled back (normative — P1 security invariant):**

This is a critical security rule. When a reassembly group times out, the
Link's replay-window state for the fragments that were authenticated and
committed MUST NOT be rolled back. The consumed sequence numbers remain
consumed.

```text
fragment authenticated + AEAD passes
    ↓
replay window commit() (§4.4 — commit-after-AEAD)
    ↓
reassembly later times out (REASSEMBLY_TIMEOUT)
    ↓
incomplete LinkFrame discarded
    ↓
fragment sequence numbers REMAIN CONSUMED in the replay window
```

**Normative rules:**
- **Reassembly timeout MUST NOT roll back replay-window state.** A fragment
  that was authenticated and committed remains committed even if its
  reassembly group is discarded. Rolling back replay state would allow an
  attacker to replay the same fragment sequence under a new reassembly
  attempt — a serious replay vulnerability.
- **Reassembly timeout MUST NOT make any previous sequence reusable.** The
  Link sequence numbers consumed by the timed-out group are spent; the
  sender's next fragment uses a fresh sequence (the monotonic counter has
  advanced).
- **No "undo" of commit().** The `commit()` operation (§4.4) is irreversible
  for the life of the `link_key`. Only a fresh SNP-IK/0.1 handshake (fresh
  `link_key`, fresh sequence space starting at 1) resets the replay window —
  and that requires Link teardown + re-establishment (§7.4).

This rule prevents the subtle attack where an attacker sends valid fragments,
waits for the group to time out, then replays those fragments hoping the
receiver "forgot" the sequences. The receiver does not forget — the sequences
remain in the replay window, and the replayed fragments are rejected as
duplicates (or rejected by the replay window outright, depending on whether
the sequence is within the window).

#### 4.5.8 Sequence reservation before transmission (normative)

A fragmented logical frame consumes N consecutive Link sequence numbers (§4.5.1).
Because sequence exhaustion is fail-closed at `u32::MAX` (§4.4), the sender
MUST verify that the complete fragment sequence range fits in the remaining
sequence space **before** transmitting any fragment. Partial logical-frame
transmission due to sequence exhaustion is forbidden.

**The lifecycle distinguishes pre-flight validation from post-reservation
cryptographic construction (normative):**

```text
PRE-FLIGHT VALIDATION (no sequence consumed on failure):
  1. determine fragment_count
       (from LinkFrame size + max_fragment_payload, §4.3, §4.5.3)
  2. validate MTU/resource/size conditions
       (effective_max_frame_for_link, §4.5.3; MAX_LINK_FRAGMENTS, §4.5.6)
  3. verify sequence space: (current_sequence + fragment_count - 1) <= u32::MAX
       → if NOT: LinkSequenceExhausted
         → transmit ZERO fragments of this logical frame
         → NO sequence consumed (pre-flight failure)
         → the logical frame is rejected; the caller handles the failure

RESERVATION (sequences permanently consumed):
  4. reserve/allocate the entire sequence range atomically
       [current_sequence, current_sequence + fragment_count - 1]
     → the complete sequence range is now PERMANENTLY CONSUMED
       (irrevocable — MUST NOT roll back, consistent with §4.5.7 replay-no-rollback)

CRYPTOGRAPHIC CONSTRUCTION (zero fragments if fails; sequences remain consumed):
  5. construct/encrypt all N fragments (each gets its reserved sequence)
     → if construction/AEAD fails for any fragment:
       → discard the whole frame
       → ZERO fragments of that logical frame are transmitted
       → reserved sequences REMAIN CONSUMED (no rollback)
       → the caller handles the failure (the Link is NOT necessarily torn down;
         only sequence exhaustion or explicit teardown closes the Link)

TRANSMISSION (sequences remain consumed regardless of transport outcome):
  6. transmit fragments (order within the reserved range is
     implementation-defined; the receiver reassembles regardless of arrival
     order via ReassemblyKey, §4.5.4)
     → datagram transport loss: sequences remain consumed (§4.5.7);
       reassembly times out → frame discarded; sequences NOT rolled back
     → stream transport: underlying stream reliability handles delivery;
       sequences remain consumed
```

**Five-rule lifecycle summary (normative):**

| # | Phase | Failure outcome | Sequences consumed? |
|---|-------|-----------------|---------------------|
| 1 | Pre-flight (steps 1-3): fragment_count, MTU/resource validation, sequence-space check | `LinkSequenceExhausted` or validation error; ZERO fragments transmitted | **NO** — pre-flight failure consumes no sequence |
| 2 | Successful reservation (step 4): range `[s, s+N-1]` allocated | N/A — reservation succeeded | **YES — permanently** (irrevocable) |
| 3 | Post-reservation AEAD/construction failure (step 5) | Frame discarded; ZERO fragments transmitted | **YES — remain consumed** (no rollback) |
| 4 | Transport loss after construction (step 6, datagram) | Reassembly timeout → frame discarded | **YES — remain consumed** (§4.5.7) |
| 5 | Successful transmission + reassembly | Complete `LinkFrame` delivered to `LinkMultiplexer` | **YES — remain consumed** |

**Never permit partial logical-frame transmission** due to sequence exhaustion
or post-reservation construction failure. The pre-flight check (step 3) prevents
the case where the sender begins transmitting and then discovers it cannot
complete the range. The post-reservation rule (step 5) ensures that even if
construction fails after reservation, no partial frame is transmitted.

**Forbidden behavior (normative):**

```text
seq = u32::MAX - 1
frame requires 3 fragments

[pre-flight check detects insufficient space → LinkSequenceExhausted → ZERO fragments]
```

The pre-flight check catches this **before** any fragment is transmitted or any
sequence is reserved. The sender does NOT send fragment 0 and 1 and then fail
on fragment 2 — the complete range is verified to fit before reservation.

**Interaction with effective_max_frame (§4.5.3):** a frame that exceeds
`effective_max_frame_for_link` is rejected at pre-flight step 2 (before
sequence reservation) — it cannot be fragmented at all. The sequence-space
check at step 3 applies only to frames that CAN be fragmented but may not fit
in the remaining sequence space.

**This is the same fail-closed principle already established for N2.3**
(N2.3-V1-CONFORMANCE: a failed packet construction MUST NOT consume a sequence
number). N2.4-05 extends this precisely: a **pre-flight** failure MUST NOT
consume a sequence; a **post-reservation** failure (after the range is
irrevocably allocated) MUST NOT roll back the reservation. The distinction is
between *attempting to construct* (pre-flight, no consumption) and *having
reserved and then failing during construction* (post-reservation, consumption
is irrevocable).

## 5. TransportEndpoint and LinkTransportKind

### 5.1 TransportEndpoint (normative)

A `TransportEndpoint` identifies how to reach a node over a specific transport.
It is the address the `TransportProvider` uses to `connect()` and the
`LinkListener` binds to. It is **transport-specific**:

```text
TransportEndpoint =
    Tcp(host:port)                      // "192.0.2.10:47000"
  | Quic(host:port)                     // "192.0.2.10:47001"
  | Udp(host:port)                      // "192.0.2.10:47002"
  | Ble(peer_mac_or_uuid)              // "AA:BB:CC:DD:EE:FF" or service UUID
  | WifiDirect(peer_mac)               // "AA:BB:CC:DD:EE:FF"
  | Nearby(connection_endpoint_token)  // platform-specific token
  | Lora(dev_addr, session_key_id)     // LoRaWAN-style identifier
  | Future(string)                      // extensible for future transports
```

`TransportEndpoint` is NOT a NodeId. It is the transport-layer address; the
NodeId is authenticated separately via the SNP-IK/0.1 handshake after the
transport connection is established. A single NodeId MAY be reachable over
multiple `TransportEndpoint`s (multi-transport node).

### 5.2 LinkTransportKind (normative)

```text
LinkTransportKind = "tcp" | "quic" | "udp" | "ble" | "wifi-direct" | "nearby" | "lora" | <future-kind>
```

`LinkTransportKind` is a **string enum**, not a platform type (invariant I11,
ADR-0003). This allows future transports to be added without modifying the
frozen L8 trait. The string is carried in:
- `TransportEndpoint` canonical CBOR (a `type` field + an `addr` field —
  existing `descriptor.rs:366-432` pattern).
- Link advertisement (the `Link` reports its kind for peer-awareness).

A receiver that encounters an unknown `LinkTransportKind` MUST reject the
endpoint (fail-closed, I20) — it MUST NOT silently fall back to a default
transport.

### 5.3 Canonical CBOR

`TransportEndpoint` has canonical-CBOR encoding for persistence and signature
binding (it appears in `CommittedRoute.validated_hops.link_evidence`). The
existing encoding (`descriptor.rs:366-432`) is:
```text
{ "type": <kind-string>, "addr": <transport-specific-string> }
```
N2.4-05 extends the `type` set to include `"quic"`, `"udp"`, `"lora"` (currently
absent). This is a **non-breaking extension** — existing `"tcp"` / `"ble"` /
`"wifi-direct"` / `"nearby"` encodings are unchanged. Frozen N2.3 routes that
use only TCP remain valid.

### 5.4 TransportEndpoint (locator) vs TransportCredential (normative)

`TransportEndpoint` is a **locator** — it identifies how to reach a peer over
a transport. It is NOT an authenticator and does NOT carry security material.
Some transports (Nearby Connections, LoRa, BLE Secure Connections) require
transport-specific authentication material or capability tokens that are NOT
locator semantics. N2.4-05 separates these explicitly:

```text
TransportEndpoint = locator
    (e.g., Tcp(host:port), Ble(mac_or_uuid), Nearby(token), Lora(dev_addr, session_key_id))

TransportCredential / TransportContext = transport-specific authentication material
    (e.g., Nearby connection capability token, LoRa session keys,
     BLE Secure Connections pairing material, QUIC TLS identity)

NodeId = cryptographic ShareNet identity
    (authenticated via SNP-IK/0.1 handshake AFTER transport connection is established)
```

**Normative rules:**
- `TransportEndpoint` values are **locators**, not credentials. A locator
  string that happens to embed a token (e.g., `Nearby(token)`) is treated as
  an opaque locator; the token's security semantics are transport-specific and
  live in `TransportContext`, not in the generic `TransportEndpoint` model.
- `TransportCredential` / `TransportContext` is **transport-specific security
  context**. It is NOT part of the generic `TransportEndpoint` identity model
  and MUST NOT be conflated with `NodeId`. The ShareNet `NodeId` is
  authenticated cryptographically via the SNP-IK/0.1 handshake, independent of
  any transport-specific credential.
- A transport adapter MAY consume `TransportContext` to establish the transport
  connection (e.g., a Nearby Connections adapter uses the platform token to
  authenticate the connection establishment), but the resulting ShareNet `Link`
  is authenticated by the SNP-IK/0.1 handshake, not by the transport credential.
- If a transport credential is compromised (e.g., a Nearby token is leaked),
  the ShareNet `NodeId` is NOT compromised — the attacker would still need to
  complete the SNP-IK/0.1 handshake (which requires the peer's Ed25519
  private key). The transport credential is a **per-transport access control**,
  not a ShareNet identity credential.

This separation prevents transport-specific authentication material from
accidentally becoming part of the generic endpoint identity model.

## 6. TransportProvider and LinkListener

### 6.1 TransportProvider (outbound)

```text
trait TransportProvider {
    fn kind() -> LinkTransportKind;
    fn connect(endpoint: TransportEndpoint, timeout: Duration)
        -> Result<LinkHandshake, TransportError>;
    fn supports_mode() -> LinkMode;  // Stream | Datagram
}
```

`connect()` establishes the underlying transport connection (TCP connect, QUIC
stream, BLE GATT attach, etc.) and returns a `LinkHandshake` — the transport
connection ready for the SNP-IK/0.1 handshake. The `TransportProvider` does
NOT perform the handshake; that is the `Link` layer's job (ADR-0003/0006).

### 6.2 LinkListener (inbound)

```text
trait LinkListener {
    fn kind() -> LinkTransportKind;
    fn bind(endpoint: TransportEndpoint) -> Result<(), TransportError>;
    fn accept() -> Result<LinkHandshake, TransportError>;  // blocking or async
}
```

`accept()` returns a `LinkHandshake` for an incoming transport connection. The
listener does NOT auto-accept (ADR-0003: no auto-accept; the handshake must
complete before the `Link` is established).

### 6.3 Platform code lives in L9 (invariant I11)

`TransportProvider` and `LinkListener` **implementations** are
platform-specific and live in `platform/linux`, `platform/android`, etc. (L9).
The **trait definitions** live in L8 (core ShareNet). This is invariant I11
(spec/06-CONFORMANCE-AND-AI-MODEL.md:170): "Platform-specific code exists only
in L9 adapters and link implementations." CI gate 6
(spec/06-CONFORMANCE-AND-AI-MODEL.md:258) fails the build if L8 imports L6 or
if L6 imports a platform SDK.

## 7. Link Liveness

### 7.1 LivenessState (normative)

```text
LivenessState = Live | Degraded | Dead
```

- **Live**: the Link has carried a frame (data or keepalive) within
  `KEEPALIVE_INTERVAL` (default 5s for TCP/QUIC; 30s for BLE; 60s for LoRa).
- **Degraded**: no frame within `KEEPALIVE_INTERVAL` but within
  `DEGRADED_TIMEOUT` (default 3 × `KEEPALIVE_INTERVAL`). The Link is still
  usable but the routing layer (L6) MAY prefer alternative links.
- **Dead**: no frame within `DEGRADED_TIMEOUT`. The Link is torn down; its
  `LinkKey` is erased; its entry is removed from the `LinkTable`. Circuits
  using this link must recover (N2.4-04 R1/R2).

### 7.2 Keepalive contract (normative)

- The `Link` MUST support keepalive frames (zero-length AEAD frames that update
  `last_seen` but carry no payload).
- The `Link` MUST send a keepalive if no data frame has been sent within
  `KEEPALIVE_INTERVAL / 2`.
- The `Link` MUST NOT require the circuit layer to send keepalives — liveness is
  a transport concern (L8 owns "link liveness", spec/01-ARCHITECTURE.md:89).
- For datagram transports (UDP, BLE GATT), keepalives double as reachability
  probes. For stream transports (TCP, QUIC), keepalives are still useful for
  detecting half-open connections (e.g., a peer that crashed without sending
  FIN).

### 7.3 Probe semantics per transport (normative)

| Transport | Probe mechanism | Liveness signal |
|-----------|-----------------|-----------------|
| TCP | keepalive frame (AEAD zero-payload) | frame received |
| QUIC (stream/datagram) | keepalive frame | frame received |
| UDP | keepalive datagram | datagram received |
| BLE GATT | BLE connection-event / notification | GATT indication received |
| Wi-Fi Direct | keepalive frame (over the Wi-Fi Direct link) | frame received |
| Nearby | keepalive frame | frame received |
| LoRa | downlink confirmation (Class C) or scheduled check-in (Class A/B) | confirmed receive |

For BLE and LoRa, the underlying transport's own liveness signal MAY be used
where available (BLE connection events, LoRa confirmed receipts). The `Link`
MUST NOT rely on transport-level liveness alone for security decisions — a
keepalive frame proves the peer's `link_key` is still valid, which
transport-level liveness does not.

### 7.4 Link restart semantics (normative)

A source/relay process restart (F11 in N2.4-04) destroys all Links. The
following rules are normative and define the interaction with N2.4-04:

```text
process restart
    ↓
all Links lost (transport connections dropped; process memory gone)
    ↓
old LinkKeys invalid
    (the SNP-IK/0.1 transcript and derived link_key lived in process memory;
    a restart cannot prove the keys were not exfiltrated before the process died.
    Treating them as valid would make a restarted process a long-lived bearer
    credential — explicitly forbidden, same discipline as N2.4-04 §7.5
    SessionBindingRootKey)
    ↓
Link state is NOT persisted (N2.1.1 §20.1 — link state is transport-specific
    and may not survive restart)
    ↓
fresh transport connections established (per L9 adapter)
    ↓
fresh SNP-IK/0.1 handshakes (fresh link_key, fresh sequence space starting at 1, §4.4)
    ↓
affected circuits recover via N2.4-04
    (a Link failure is a relay/gateway failure from the circuit's perspective;
    N2.4-04 R1/R2 recovery applies. The TransportSession (N2.4-04) survives
    across Link replacement — only the circuit and the Link are replaced)
```

**Link replacement ≠ TransportSession replacement.** A Link can change while
the higher-level `TransportSession` (N2.4-04) survives, exactly as N2.4-04
established for circuit replacement. The hierarchy of survival across restart:

```text
TransportSession (N2.4-04)   — survives circuit replacement; dies on source process restart
    (new TSID + new root required on restart, N2.4-04 §7.5)
Circuit (N2.3 frozen)         — survives Link replacement; dies on circuit expiry/teardown/restart
    (new circuit_id + fresh keys on each replacement, N2.4-04)
Link (N2.4-05, this ADR)      — dies on transport teardown, liveness timeout, or process restart
    (fresh SNP-IK/0.1 handshake on each re-establishment; link state NOT persisted)
```

**No Link persistence across restart (normative):** Link state (transport
connection, `link_key`, link sequence, replay window, liveness state) is
**transport-scoped** and is NOT persisted (N2.1.1 §20.1). On restart, all
Links are re-established via fresh transport connections + fresh SNP-IK/0.1
handshakes. The Link layer provides no persistence — this is the security
boundary that prevents a restarted process from inheriting stale transport
keys. If persistent Link-key recovery is ever desired (so that a restart could
resume a prior transport connection), that requires a **future secure-storage /
key-management ADR** to define how the `link_key` is protected at rest; N2.4-05
does NOT define this.

## 8. Transport Multiplexing

### 8.1 The problem

N2.4-01 residual risk #5 (threat-model.md:469-472): "if the transport (TCP) is
fingerprintable, an observer can correlate circuits across transport sessions.
Mitigation: transport multiplexing (N2.4)."

Without multiplexing, each circuit uses its own TCP connection. An observer
who sees N TCP connections from the same source can correlate them by timing,
volume, and connection patterns. Multiplexing multiple circuits over one TCP
connection makes per-circuit correlation harder.

### 8.2 Multiplexing decision and the LinkMultiplexer boundary (normative)

N2.4-05 establishes that **multiple circuits MAY be multiplexed over a single
Link**. This is an L8 property. To resolve the boundary contradiction (the
Link cannot both "not inspect circuit_id" and "demultiplex to circuits"),
N2.4-05 introduces an **explicit L8 component: the LinkMultiplexer (Demux)**.

**The L8 demultiplexing boundary:**

```text
L6 / N2.3 Circuit layer
    ↑ delivers opaque circuit packets to the correct circuit's RelayForwardingTable
LinkMultiplexer / Demux   (L8 component)
    ↑ reads circuit_id from the LinkFrame header (opaque demux key)
    ↑ circuit registration / lookup / demux / unknown-circuit / teardown
LinkFrame   (authenticated AEAD frame, §4.4 sequence)
    ↑ carries: circuit_id (demux key) || seq || direction(V2) || payload
Link   (L8 component)
    ↑ owns: transport, Link AEAD, link sequence, framing, MTU, liveness
    ↑ does NOT interpret circuit_id meaning or route semantics
L9 platform adapter  (TCP / QUIC / BLE / ...)
```

**Ownership (normative):**

| Component | Owns | Does NOT own |
|-----------|------|---------------|
| **Link** | transport connection, `link_key`, Link AEAD, link sequence (§4.4), framing, MTU, liveness | circuit_id meaning, circuit membership, route semantics, destinations |
| **LinkMultiplexer / Demux** | `circuit_id` demultiplexing (opaque key), circuit registration/unregistration, frame delivery to the correct circuit's `RelayForwardingTable` entry, unknown-circuit handling | circuit_id meaning, route selection, destinations, what the circuit does with the frame |
| **Circuit layer (L6/N2.3 frozen)** | per-circuit replay window, per-circuit AEAD (forwarding keys), circuit packet interpretation | transport framing, link sequence, link liveness |

**The Link treats `circuit_id` as opaque.** It does not interpret the `circuit_id`
value. The LinkMultiplexer consumes `circuit_id` as a **demultiplexing key**
(an opaque routing key to the correct circuit table entry) but does NOT
interpret the circuit's route semantics, destination meaning, or circuit
membership beyond lookup. Invariant I9 (L8 never imports L6) is preserved:
neither the Link nor the LinkMultiplexer routes, and neither knows what the
circuit_id *means* — they only use it to find the correct circuit table entry.

**LinkMultiplexer operations (normative):**
- **Circuit registration:** when a circuit is established (N2.2), the circuit's
  `circuit_id` is registered with the `LinkMultiplexer` for each Link the
  circuit uses. The registration maps `circuit_id → RelayForwardingTable entry`.
- **Frame demultiplexing:** on receiving an authenticated `LinkFrame` from the
  Link, the LinkMultiplexer reads the `circuit_id` from the frame header, looks
  up the registered circuit, and delivers the opaque circuit packet to that
  circuit's `RelayForwardingTable` entry for circuit-layer processing (frozen
  N2.3 replay window + AEAD).
- **Unknown-circuit handling:** a frame whose `circuit_id` is not registered
  is **rejected as unknown** (`UnknownCircuit`, matching frozen N2.3
  `forward_packet` behavior). The LinkMultiplexer MUST NOT create a circuit
  entry on demand — circuit creation is an L6/N2.2 concern.
- **Circuit teardown/unregistration:** when a circuit is torn down (N2.3
  `CircuitTeardown`), the circuit is unregistered from the `LinkMultiplexer`.
  Subsequent frames for that `circuit_id` are rejected as `UnknownCircuit`.
- **Link close → unregister all:** when a Link closes (§3.3), the
  `LinkMultiplexer` unregisters all circuits that were using that Link.
  Affected circuits recover via N2.4-04 R1/R2 (a Link failure is a relay/gateway
  failure from the circuit's perspective).

**Multiplexing is OPTIONAL per Link.** A Link MAY carry one circuit (simple,
no demux overhead) or many (multiplexed). The choice is a transport-layer
decision; the circuit layer does not require multiplexing.

### 8.3 Multiplexing security considerations

- **Timing correlation within a multiplexed Link:** an observer who sees the
  Link's aggregate traffic cannot trivially separate circuits, but traffic
  analysis within the Link is still possible (packet sizes, timing gaps). Full
  per-circuit traffic-analysis resistance is a padding concern (N2.4-08, if
  required), not a transport concern.
- **Replay window independence:** the Link's transport-scoped AEAD replay
  window is separate from each circuit's frozen N2.3 replay window. A frame
  replayed on the Link is rejected by the Link's replay window; a circuit
  packet that passes Link AEAD is then subject to the circuit's own replay
  window (frozen, per-circuit). These windows are independent and MUST NOT
  contaminate each other.
- **Key separation:** the `LinkKey` (per-link, SNP-IK/0.1) is distinct from
  the circuit's per-hop forwarding keys (X25519 + HKDF, ADR-0011). A Link that
  carries N circuits uses ONE `LinkKey` for framing AEAD and N separate
  per-hop keys for circuit-packet AEAD. These are never mixed (ADR-0011 key
  independence).

### 8.4 Flow_id relationship (V2)

The V2 packet's `flow_id` field (8 bytes, bound in AAD — frozen N2.3) is a
**circuit-scoped** flow identifier, NOT a transport multiplexing identifier.
It distinguishes flows within a single circuit (e.g., multiple TCP streams
over one Mode B circuit). It is unrelated to Link multiplexing (§8.2), which
distinguishes circuits within a single Link. The two are orthogonal:

```
Link (L8)  ──multiplexes──>  Circuits (L6/N2.3)  ──multiplexes──>  Flows (V2 flow_id)
```

N2.4-05 does not modify `flow_id` semantics (frozen). TCP stream multiplexing
over a circuit (ADR-0014 deferred list) is a future concern, not N2.4-05.

## 9. Relationship to N2.4-04 Transport Session Layer

### 9.1 The boundary

N2.4-04's `TransportSession` (TSID, RESUME, epoch) sits at L7 (gateway
application protocol) and above. The TSID is carried in:
- **Mode A**: an application-layer header on the Mode A request (gateway app
  protocol).
- **Mode B**: the CONNECT request metadata at tunnel establishment.

In both cases, the TSID-carrying gateway application protocol rides over a
circuit, which rides over a `Link`. N2.4-05 defines the `Link` boundary that
N2.4-04's session layer transitively depends on.

```
Application (Mode A request / Mode B byte stream)
    ↓ carries TSID in gateway app protocol (N2.4-04)
TransportSession layer (N2.4-04 — TSID, epoch, RESUME)
    ↓ maps to a circuit
Circuit layer (N2.3 frozen — V1/V2 packet, ActiveCircuit)
    ↓ multiplexes over Links (N2.4-05 §8)
Link layer (N2.4-05 — L8, this ADR)
    ↓ implemented by platform adapters
L9 platform adapters (TCP / QUIC / BLE / Wi-Fi Direct / … — implementation deferred)
```

### 9.2 What N2.4-04 depends on from N2.4-05

N2.4-04 §21 (implementation-blocked-until) requires "N2.4-05 (Transport
Abstraction) is at least proposed (the session layer depends on the transport
abstraction boundary)." Specifically:

- A stable `Link` trait that the circuit layer can rely on for framed transport.
- A `TransportEndpoint` + `LinkTransportKind` that the route layer (L6/N2.1.2)
  can record in `CommittedRoute.validated_hops.link_evidence`.
- Per-Link `LinkMtu` exposure so L8 can determine fragmentation feasibility
  (§4.3, §4.5.3). The circuit layer remains **unaware** of individual
  transport MTUs — Architecture B (§4.3) means L8 handles fragmentation; the
  frozen N2.3 circuit layer does NOT enforce `PayloadTooLarge` based on
  transport MTU and does NOT need to fit the path MTU.
- Link liveness so the circuit layer (and N2.4-04 recovery) can detect relay
  disappearance (F1/F2) via `LivenessState == Dead`.

### 9.3 What N2.4-04 does NOT depend on

N2.4-04 does NOT depend on:
- Specific transport implementations (TCP, BLE, etc.) — only the trait.
- Multiplexing (§8) — the session layer works with or without it.
- QUIC or UDP availability — TCP-only is sufficient for N2.4-04 operation;
  additional transports expand deployment, not correctness.

## 10. Per-Transport Contracts (Normative Boundary)

For each transport, N2.4-05 defines the **contract** the platform adapter
must satisfy. Implementation is deferred (L9, platform-specific). The contract
is normative: an adapter that violates it breaks ShareNet.

### 10.1 TCP

- `LinkMode = Stream`, `supports_ordering = true`, `is_reliable = true`,
  `is_full_duplex = true`.
- `TransportEndpoint::Tcp(host:port)`.
- Framing: length-prefixed AEAD (existing `snp-link` framing).
- MTU: 65535 (or negotiated lower via TCP MSS clamping; the Link exposes the
  actual negotiated value).
- Handshake: TCP connect → SNP-IK/0.1 over the TCP stream → `EstablishedLink`.
- Liveness: keepalive frames every 5s; TCP keepalive (SO_KEEPALIVE) MAY be
  enabled as a backstop but the Link MUST send its own keepalives (TCP
  keepalive alone does not prove `link_key` validity).
- **Android note:** TCP sockets used for ShareNet Links SHOULD be
  `protect()`ed from the `VpnService` loop (spec/03-PLATFORM-MATRIX.md:51-78)
  to avoid the ShareNet traffic being re-tunneled. This is a platform concern,
  not a Link contract concern — the Link trait does not expose `protect()`.

### 10.2 QUIC

- `LinkMode = Stream` (for QUIC stream mode) or `Datagram` (for QUIC datagram
  extension, RFC 9221). The Link reports the mode it is using.
- `TransportEndpoint::Quic(host:port)`.
- Framing: for stream mode, length-prefixed AEAD (same as TCP); for datagram
  mode, native QUIC datagram boundaries (one datagram = one AEAD frame).
- MTU: 65535 (stream); the QUIC datagram MTU is negotiated via
  `max_datagram_frame_size` transport parameter — the Link exposes the
  negotiated value.
- Handshake: QUIC handshake → SNP-IK/0.1 over a QUIC stream → `EstablishedLink`.
  The QUIC handshake authenticates the server's TLS identity; the ShareNet
  SNP-IK/0.1 handshake authenticates the NodeId. These are separate.
- Liveness: keepalive frames; QUIC's own keepalive (`max_idle_timeout`) MAY be
  used as a backstop.
- **Migration (normative invariant):** QUIC connection migration (RFC 9000 §9)
  is a transport-layer feature that MAY allow a peer's IP to change without
  tearing down the QUIC connection. N2.4-05 does NOT require or forbid QUIC
  migration; it is a platform/adapter decision. **Normative invariant:** QUIC
  path/address migration MUST NOT change the authenticated ShareNet `NodeId` or
  silently substitute peer identity. IP endpoint change ≠ NodeId change. A
  migrated QUIC connection MUST remain authenticated to the same ShareNet node
  cryptographically (the `link_key` derived from the SNP-IK/0.1 handshake is
  unchanged by QUIC migration; only the underlying transport path changes).
  N2.4-06 (Mobile Node Lifecycle) may define the concrete mobile-IP-change
  behavior using QUIC migration as one mechanism, but MUST NOT use transport
  migration to silently substitute the authenticated peer.

### 10.3 UDP

- `LinkMode = Datagram`, `supports_ordering = false`, `is_reliable = false`,
  `is_full_duplex = true`.
- `TransportEndpoint::Udp(host:port)`.
- Framing: native datagram boundaries; AEAD per datagram. The Link MUST
  implement a transport-scoped replay window (the frozen N2.3 circuit replay
  window is separate and per-circuit).
- MTU: 1400 (conservative; the Link MAY negotiate higher via path MTU
  discovery but MUST NOT exceed the discovered path MTU).
- Handshake: UDP has no handshake; the SNP-IK/0.1 handshake runs over UDP
  datagrams (with retransmission, since UDP is unreliable). The Link is
  `EstablishedLink` only after the handshake completes.
- Liveness: keepalive datagrams every 5s; a missed keepalive within
  `DEGRADED_TIMEOUT` → Degraded; beyond → Dead.
- **Reliability (normative):** the Link does NOT provide reliability for data
  frames. A Datagram Link provides **authenticated datagram delivery** with
  loss and reordering permitted. Any retransmission/recovery is performed by
  the appropriate higher layer:
  - **Application transport** (e.g., TCP/HTTP over Mode B) provides its own
    retransmission.
  - **Circuit delivery recovery** (whether a lost circuit packet is recovered)
    is handled at the session layer (N2.4-04) or application layer — NOT by
    the frozen N2.3 circuit packet itself.
  - N2.4-05 MUST NOT imply that frozen N2.3 circuit packets implement a generic
    reliable transport. The N2.3 circuit layer provides authenticated,
  replay-protected, ordered (per-direction) delivery *of packets that arrive*;
    it does NOT retransmit lost packets. Loss recovery is a session/application
    concern. The Link provides only AEAD framing and replay protection for the
    transport.

### 10.4 Bluetooth (BLE GATT)

- `LinkMode = Datagram`, `supports_ordering = false` (BLE GATT notifications
  are unordered), `is_reliable = false`, `is_full_duplex = true` (notifications
  + writes).
- `TransportEndpoint::Ble(peer_mac_or_service_uuid)`.
- Framing: BLE GATT notifications (peer → local) and writes (local → peer).
  Each notification/write carries one AEAD frame (MTU 244, conservative ATT_MTU
  247 − 3 header). Frames larger than the BLE MTU MUST be fragmented at the
  Link layer (transport-scoped, not circuit-scoped).
- MTU: 244 (or the negotiated ATT_MTU − 3; the Link exposes the actual value).
- Handshake: BLE GATT connection → service discovery → SNP-IK/0.1 over GATT
  characteristics → `EstablishedLink`.
- Liveness: BLE connection events (the BLE stack's own liveness) PLUS
  keepalive frames every 30s (BLE connections are low-duty-cycle; 5s keepalives
  would drain battery). A BLE disconnect → Dead immediately.
- **Android note:** BLE background restrictions (Android 12+ scan/advertise
  throttling, `BLUETOOTH_SCAN/ADVERTISE/CONNECT` permissions) affect when a
  BLE Link can be established — this is a platform concern, not a Link contract.

### 10.5 Wi-Fi Direct

- `LinkMode = Datagram` (Wi-Fi Direct group owner / client uses UDP-like
  framing over the Wi-Fi Direct link) or `Stream` (if TCP over Wi-Fi Direct).
  The Link reports the mode.
- `TransportEndpoint::WifiDirect(peer_mac)`.
- Framing: per the underlying mode (Stream = length-prefixed AEAD; Datagram =
  native datagram AEAD).
- MTU: 1400 (treat like UDP until measured).
- Handshake: Wi-Fi Direct group negotiation → TCP/UDP over the link →
  SNP-IK/0.1 → `EstablishedLink`.
- Liveness: keepalive frames every 5s; Wi-Fi Direct link-down event → Dead.
- **Platform note:** Wi-Fi Direct is unavailable on iOS (MultipeerConnectivity
  only) and macOS (AWDL via MultipeerConnectivity); available on Android
  (`WifiP2pManager`), Windows (Wi-Fi Direct API), Linux (`wpa_supplicant`).
  Platform availability is a concern of L9 adapters, not the Link contract.

### 10.6 Nearby Connections (Android Play Services)

- `LinkMode = Stream` (Nearby Connections provides a reliable byte stream).
- `TransportEndpoint::Nearby(connection_endpoint_token)`.
- Framing: length-prefixed AEAD over the Nearby Connections stream.
- MTU: 65535 (Nearby Connections abstracts the underlying transport).
- Handshake: Nearby Connections advertising/discovery → connection →
  SNP-IK/0.1 → `EstablishedLink`.
- Liveness: keepalive frames every 5s; Nearby disconnection callback → Dead.
- **AOSP/GrapheneOS/Huawei exclusion:** Nearby Connections requires Play
  Services; AOSP-only devices cannot use it. A Play-free link (Wi-Fi Direct
  + BLE + TCP over local Wi-Fi) is REQUIRED for these devices
  (spec/03-PLATFORM-MATRIX.md:51-78). This is a platform concern.

### 10.7 LoRa

- `LinkMode = Datagram`, `supports_ordering = false`, `is_reliable = false`,
  `is_full_duplex = false` (LoRa is half-duplex per device; Class C devices
  can receive continuously but transmit on schedule).
- `TransportEndpoint::Lora(dev_addr, session_key_id)`.
- Framing: native LoRa datagram boundaries; AEAD per datagram. Fragmentation
  at the Link layer for payloads > MTU (51–242 bytes region/bandwidth-dependent).
- MTU: the actual LoRa payload size (region/bandwidth/Spreading Factor
  dependent, 51–242 bytes). The Link exposes the actual value.
- Handshake: LoRa join (OTAA) → SNP-IK/0.1 over confirmed downlinks →
  `EstablishedLink`. The handshake is slow (seconds to minutes depending on
  Spreading Factor and duty cycle).
- Liveness: confirmed downlink every 60s (Class C) or scheduled check-in
  (Class A/B). LoRa duty-cycle limits (1% in EU868) bound the keepalive rate.
- **Store-carry-forward:** LoRa is delay-tolerant by nature. A LoRa Link MAY
  carry N2.4-04 Mode A bundles (delay-tolerant request/response) but is
  unsuitable for Mode B (byte-stream proxy) due to high latency and low
  throughput. The Link reports `link_mode = Datagram` and the session layer
  chooses modes accordingly.

### 10.8 Future transports

N2.4-05 is extensible: a future transport adds a new `LinkTransportKind`
string, a new `TransportEndpoint` variant (or `Future(string)`), and a new
`TransportProvider`/`LinkListener` implementation in L9. The Link trait, the
circuit layer, and the session layer do NOT change. This is the point of the
abstraction.

## 11. IP-Pinned Connections (Gateway Egress Interaction)

### 11.1 The constraint from N2.4-03 / ADR-0008

N2.4-03 §5.3 (destination validation) and ADR-0008 (gateway DNS-rebinding
defence) require the gateway to `connect()` to a **pinned validated IP
address** — no DNS re-resolution between validation and connect
(`pin-and-connect`, §5.3.2). This "breaks some platform HTTP client
assumptions" (ADR-0008).

### 11.2 What the Link trait must support

For **gateway egress** (Mode A outbound HTTP request, Mode B outbound TCP), the
gateway's transport adapter MUST support connecting to an IP literal directly:

- `TransportEndpoint::Tcp(ip_literal:port)` — the gateway passes the
  validated IP (not the hostname) to `connect()`.
- The Link's underlying HTTP client (Mode A) or TCP connect (Mode B) MUST use
  this IP literal for `connect()` and MUST NOT re-resolve the hostname.

This is a Link contract requirement: a transport adapter that cannot connect
to an IP literal (e.g., a high-level HTTP client that always re-resolves)
cannot be used for gateway egress. N2.4-05 does not modify the gateway's
HTTP client; it requires that the transport adapter support IP-pinned
connections so the gateway can enforce §5.3.2.

## 12. Transport Negotiation and Fallback

### 12.1 Multi-transport nodes

A node MAY advertise multiple `TransportEndpoint`s (e.g., `Tcp(...)` +
`Ble(...)` + `Quic(...)`). The routing layer (L6/N2.1.2) selects which Link to
use for a route based on:
- Availability (the endpoint is reachable).
- Link `LinkMtu` (the selected route must provide Links whose `LinkMtu`s permit
  L8 fragmentation of the circuit's expected packet size under §4.5 bounds.
  The frozen N2.3 `CircuitPacket` itself does NOT need to fit a path MTU —
  Architecture B (§4.3) means L8 fragments as needed; route selection
  considers transport feasibility, not a new path-MTU constraint on N2.3).
- Preference (the source's transport preferences — e.g., prefer BLE for
  low-power, TCP for throughput).
- Authorization (N2.4-02: a node's capability may constrain which transports
  it is authorized to use — e.g., a Tier-0 open node may be restricted to
  TCP only).

### 12.2 No silent fallback (normative)

A transport failure (e.g., BLE Link dies) MUST NOT silently fall back to a
different transport (e.g., TCP) without the routing layer's explicit decision.
Silent fallback would:
- Violate the user's transport preferences (e.g., the user chose BLE for
  privacy; silent fallback to TCP exposes metadata).
- Create observability gaps (the user sees traffic they did not expect).
- Potentially bypass authorization (a node authorized for BLE-only must not
  silently use TCP).

**Normative rule:** transport selection is an L6 (routing) decision, not an
L8 (transport) decision. The Link layer reports `LivenessState`; the routing
layer decides whether to re-route over a different Link. The Link layer MUST
NOT switch transports on its own.

### 12.3 Visible transport selection (invariant)

Per spec/01-ARCHITECTURE.md §4.5 and spec/03-PLATFORM-MATRIX.md §8: "Silent
degradation from `PAYLOAD_E2E` to `GATEWAY_PLAINTEXT` is a forbidden
architectural change." The same principle applies to transport selection: a
change in the active transport (e.g., BLE → TCP) MUST be visible to the user
and recorded in session metadata. The `TransportSession` (N2.4-04) records
the current circuit's `Link` kind; a transport change is a circuit
replacement (new circuit_id, new route, new Link) and is visible as a recovery
event.

## 13. Security Invariants

1. **L8 never imports L6.** The Link trait does not route, does not know about
   routes, does not inspect circuit membership. (Invariant I9,
   spec/06-CONFORMANCE-AND-AI-MODEL.md:168; spec/01-ARCHITECTURE.md:95.)
2. **L6 never imports a platform SDK.** The routing layer does not import
   Android, iOS, Linux, or any platform-specific crate. Platform code lives
   only in L9 adapters. (Invariant I10, I11.)
3. **`LinkTransportKind` is a string enum, not a platform type.** (ADR-0003 I11.)
   Future transports add new strings without modifying the frozen trait.
4. **Stubs throw, never return permissive defaults.** An unimplemented transport
   or a stub in a security-critical path MUST return an error, never a
   permissive ok. (ADR-0003 I20.)
5. **No Link without a handshake.** A `Link` is `EstablishedLink` only after
   SNP-IK/0.1 completes (ADR-0003/0006). No auto-accept. The `link_key` is
   derived from the handshake transcript; no unauthenticated Links.
6. **Link keys are distinct from circuit keys.** The `LinkKey` (per-link,
   SNP-IK/0.1) and the circuit's per-hop forwarding keys (X25519 + HKDF,
   ADR-0011) are cryptographically independent. A relay that possesses the
   LinkKey CANNOT derive the circuit key, and vice versa. (ADR-0011 key
   independence.)
7. **MTU is exposed; N2.3 is unaware (Architecture B).** Each Link exposes its
   actual MTU for Link-layer fragmentation (§4.3, §4.5). The frozen N2.3
   circuit layer is unaware of individual transport MTUs; L8 MAY fragment an
   authenticated `LinkFrame` and reassembles before circuit delivery.
   `circuit packet size ≠ transport frame size ≠ transport fragment size`.
   N2.4-05 MUST NOT modify N2.3 `PayloadTooLarge` / path-MTU semantics. A Link
   that lies about its MTU causes silent loss.
8. **Liveness is transport-owned.** The Link owns keepalive and liveness
   detection (spec/01-ARCHITECTURE.md:89). The circuit layer does not send
   transport keepalives; it relies on `LivenessState`.
9. **Multiplexing is optional, Link-scoped, and demuxed by an explicit L8
   LinkMultiplexer.** Multiple circuits over one Link is permitted (§8.2); the
   LinkFrame header carries `circuit_id` for demux. The Link treats `circuit_id`
   as opaque; the LinkMultiplexer consumes it as a demultiplexing key to find
   the correct circuit table entry, but does NOT interpret route semantics or
   destination meaning. Link-scoped AEAD and replay are independent of
   circuit-scoped AEAD and replay (frozen N2.3). Unknown `circuit_id` →
   `UnknownCircuit` (fail-closed, matching frozen N2.3).
10. **No silent transport fallback.** Transport selection is an L6 decision.
    A Link failure triggers recovery (N2.4-04); the routing layer decides
    whether to re-route over a different Link. The Link layer MUST NOT switch
    transports on its own.
11. **IP-pinned egress is supported.** The gateway's transport adapter MUST
    support connecting to IP literals (§11) so N2.4-03 §5.3.2
    (pin-and-connect) can be enforced. A transport that cannot connect to IP
    literals cannot be used for gateway egress.
12. **Transport selection is visible.** A change in active transport is a
    circuit replacement (new circuit_id, new route, new Link) and is visible
    as a recovery event. Silent transport degradation is forbidden (like
    `PAYLOAD_E2E` → `GATEWAY_PLAINTEXT`, spec/01-ARCHITECTURE.md §4.5).
13. **N2.3 packet semantics are immutable.** N2.4-05 defines the transport
    boundary beneath the circuit layer; it does not touch V1/V2 packet format,
    AAD, nonce, replay ordering, or golden vectors. No `PacketProfile::V3`
    (deferred to N2.4-07).
14. **Link state is not persisted.** Link state is transport-specific and may
    not survive restart (N2.1.1 §20.1, §7.4). On restart, Links are re-established
    via fresh transport connections + fresh SNP-IK/0.1 handshakes. The circuit
    layer (N2.4-04) handles circuit recovery; the Link layer provides no
    persistence. Link replacement ≠ TransportSession replacement (§7.4).
15. **Link sequence lifecycle is fail-closed.** The Link AEAD sequence starts
    at 1, monotonically increases, never wraps to 0, and u32::MAX is the last
    usable — next send is `LinkSequenceExhausted`, requiring teardown +
    re-establishment (fresh handshake, fresh key). Each direction has
    independent sequence/replay. `check()` before AEAD, `commit()` after AEAD,
    bounded O(WINDOW) update (matches N2.3 discipline, §4.4). Link sequence is
    transport-scoped and independent of the frozen N2.3 circuit sequence.
16. **Link fragmentation is bounded, fragment-before-AEAD, and
    cryptographically bound.** Fragmentation (§4.5) is security-critical:
    (a) **fragment-before-AEAD model** — LinkFrame plaintext is fragmented
    before per-fragment AEAD; each fragment consumes exactly one Link transmit
    sequence (no separate fragment nonce space, no nonce reuse); (b)
    **ReassemblyKey** = direction + frame_sequence + fragment_id — fragments
    are cryptographically bound to exactly one logical frame; cross-frame
    splicing is impossible because the AEAD AAD includes frame_sequence,
    fragment_id, fragment_index, fragment_count, original_frame_length; (c)
    **size consistency** — sum(received) ≤ original, sum(complete) ==
    original, final fragment MAY be smaller than MTU, no
    incomplete/overlapping/overlength reassembly reaches the LinkMultiplexer;
    (d) **bounded resources** — MAX_LINK_FRAME_BYTES, MAX_LINK_FRAGMENTS,
    REASSEMBLY_TIMEOUT, MAX_CONCURRENT_REASSEMBRIES, MAX_REASSEMBLY_MEMORY. No
    attacker-controlled fragment stream may cause unbounded allocation.
    Fragmentation is transparent to the frozen N2.3 circuit layer.
17. **Link restart discards all link keys.** Process restart destroys all
    Links; old `link_key`s are invalid (not trusted); fresh SNP-IK/0.1
    handshakes establish fresh keys and sequence spaces. The Link layer
    provides no persistence — this prevents a restarted process from
    inheriting stale transport keys (same discipline as N2.4-04 §7.5
    SessionBindingRootKey). Affected circuits recover via N2.4-04 R1/R2.
18. **QUIC migration does not substitute peer identity.** QUIC path/address
    migration (RFC 9000 §9) MUST NOT change the authenticated ShareNet
    `NodeId` or silently substitute peer identity (§10.2). IP endpoint change
    ≠ NodeId change. A migrated QUIC connection remains authenticated to the
    same ShareNet node cryptographically (the `link_key` is unchanged by
    transport migration). N2.4-06 may define mobile-IP-change using QUIC
    migration, but MUST NOT use transport migration to silently substitute
    the authenticated peer.
19. **TransportEndpoint is a locator, not a credential.** `TransportEndpoint`
    values are locators (§5.4). Transport-specific authentication material
    (Nearby tokens, LoRa session keys, BLE pairing material, QUIC TLS identity)
    is `TransportCredential` / `TransportContext` — transport-specific security
    context, NOT part of the generic endpoint identity model and NOT conflated
    with `NodeId`. The ShareNet `NodeId` is authenticated via the SNP-IK/0.1
    handshake, independent of any transport credential. A compromised transport
    credential does NOT compromise the `NodeId`.
20. **Fragment AEAD has one coherent nonce lifecycle with a frozen
    construction.** Each fragment consumes exactly one Link transmit
    sequence number (§4.5.1); the fragment AEAD nonce is derived from
    `(link_key, direction, link_sequence)` via an exact HKDF-SHA256
    construction (§4.5.2 — domain separator "SNP/0.1/link/fragment/nonce/v1",
    direction 1 byte, link_sequence big-endian u32, salt=link_key, 12-byte
    output). The construction is frozen and deterministic — byte-identical
    across implementations. There is NO separate fragment-sequence space —
    fragments use the same monotonic, no-wrap Link sequence as unfragmented
    frames (§4.4). A logical LinkFrame spanning N fragments consumes N
    consecutive Link sequence numbers. This avoids the nonce-reuse failure
    class that N2.3 hardened against; N2.4-05 applies the same discipline at
    the transport layer with an exact construction.
21. **Link fragment format is versioned.** The fragment envelope carries an
    explicit `LinkFragmentProfile` (§4.5.5, V1 = 1). Unknown profile values
    fail closed (fragment rejected, group discarded). The profile belongs to
    N2.4-05 Link framing and does NOT modify the frozen N2.3 `CircuitPacket`
    V1/V2 or `PacketProfile` (circuit-layer concept). Future profiles are
    additive and do not silently reinterpret V1.
22. **No Link-layer fragment retransmission; replay state is never rolled
    back.** N2.4-05 provides NO Link-layer fragment retransmission (§4.5.7).
    A missing fragment causes the reassembly group to time out and the entire
    incomplete LinkFrame to be discarded; the Link does not attempt partial
    fragment recovery. Higher layers (N2.4-04 session/application) recover
    lost logical data. For stream transports, underlying stream reliability
    handles transport loss; for datagram transports, loss of any required
    fragment means loss of the logical LinkFrame. Critically, reassembly
    timeout MUST NOT roll back replay-window state — authenticated fragment
    sequences remain consumed; `commit()` is irreversible for the life of the
    `link_key`. Only a fresh SNP-IK/0.1 handshake resets the replay window.
23. **Fragment wire-size accounts for header + AEAD tag.** The fragmenter MUST
    derive `max_fragment_payload = mtu - fragment_header_bytes - AEAD_TAG_BYTES`
    (§4.3, §4.5.3), not use the raw transport MTU as the maximum plaintext
    payload. A fragment whose wire size (header + ciphertext + AEAD tag)
    exceeds the actual transport MTU is rejected before transmission. This
    is normative because BLE/LoRa/etc. depend on correct MTU accounting — a
    fragment that exceeds the transport MTU is silently lost or truncated.
24. **Frame size and fragment count are MTU-consistent.** The effective maximum
    frame for a specific Link is `min(MAX_LINK_FRAME_BYTES,
    max_fragment_payload(mtu) * MAX_LINK_FRAGMENTS)` (§4.5.3). A logical
    LinkFrame exceeding that value is rejected before transmission; the
    receiver enforces the same bound. This ensures low-MTU transports are
    not asked to represent a frame they cannot fragment within the fragment
    count bound.
25. **Complete sequence range reserved before transmission; pre-flight vs
    post-reservation distinguished.** A fragmented logical frame consumes N
    consecutive Link sequence numbers; the sender MUST verify the complete
    range fits in the remaining sequence space before transmitting any fragment
    (§4.5.8). Pre-flight failures (fragment_count/MTU/sequence-space check
    before reservation) consume **NO** sequence — this matches the N2.3
    principle that a failed packet construction MUST NOT consume a sequence
    number. Successful reservation permanently consumes the range (irrevocable).
    Post-reservation failures (AEAD/construction error after reservation) and
    transport losses do NOT roll back the reservation — sequences remain
    consumed (consistent with §4.5.7 replay-no-rollback). Partial logical-frame
    transmission due to sequence exhaustion or post-reservation construction
    failure is forbidden.

## 14. Relationship to Mode C (TUN/VPN)

Mode C (N2.4-03 §12) is **deferred to N2.7+** (platform-integration ADR).
N2.4-05 does NOT define TUN/VPN/VpnService/NEPacketTunnelProvider plumbing.
Those are L9 (Virtual Net) concerns, not L8 (Transport):

- **L8 (Transport, this ADR):** carries framed bytes between two ShareNet nodes.
- **L9 (Virtual Net, deferred):** OS integration, packet capture from TUN,
  flow mapping. Mode C's TUN interface is L9; it feeds packets into L8 Links.

N2.4-05 defines the Link trait that L9 adapters use; it does not define the
L9 adapters themselves. Mode C will, when implemented (N2.7+), sit above L8
Links exactly as Mode A/B do — the TUN interface feeds the TransportSession
which feeds circuits which ride Links.

## 17. Implementation Boundaries

N2.4-05 defines the **architecture**. Implementation will produce:

- L8 `Link` trait + `TransportEndpoint` + `LinkTransportKind` + `LinkMode`
  (core ShareNet, platform-neutral)
- L8 `TransportProvider` / `LinkListener` trait definitions
- L8 Link framing (length-prefixed AEAD for Stream; datagram AEAD for Datagram)
- L8 Link liveness state machine (Live/Degraded/Dead, keepalive)
- L8 Link multiplexing (circuit_id demux in frame header)
- L9 platform adapters (one per transport per platform):
  - `platform/linux/tcp`, `platform/linux/ble` (BlueZ), `platform/linux/quic`,
    `platform/linux/udp`, `platform/linux/wifi-direct` (wpa_supplicant)
  - `platform/android/tcp`, `platform/android/ble`, `platform/android/quic`,
    `platform/android/wifi-direct`, `platform/android/nearby`
  - `platform/windows/tcp`, `platform/windows/ble` (WinRT), `platform/windows/wifi-direct`
  - `platform/macos/tcp`, `platform/macos/ble` (CoreBluetooth)
  - `platform/ios/tcp` (BLE/Multipeer deferred — iOS is client-only for mesh)
  - `platform/rpi/*` (reference embedded platform, all transports)
- Per-transport MTU measurement / negotiation
- IP-pinned connect support for gateway egress adapters

Implementation is **blocked** until:
- N2.4-05 is approved
- N2.4-06 (Mobile Node Lifecycle) is at least proposed (mobile-IP-change,
  sleep/wake behavior depends on the transport contract)
- Conformance vectors are defined

**N2.3 frozen implementation MUST NOT be modified.**

Implementation MUST NOT:
- Import L6 (routing) from L8 (transport) — invariant I9.
- Import a platform SDK from L6 (routing) — invariant I10.
- Place platform-specific code outside `platform/*` directories (L9) —
  invariant I11, spec/07-MIGRATION-AND-ROADMAP.md §3.
- Auto-accept Links without SNP-IK/0.1 handshake (ADR-0003).
- Return permissive defaults from stubs (I20).
- Silently fall back between transports (§12.2).
- Modify V1/V2 packet format, AAD, nonce, or golden vectors (frozen N2.3).
- Modify N2.3 `PayloadTooLarge` / path-MTU semantics based on transport MTU
  (§4.3 — Architecture B: L8 fragments; N2.3 is unaware of transport MTUs).
- Conflate `TransportEndpoint` (locator) with `TransportCredential`
  (transport-specific auth material) or with `NodeId` (§5.4).
- Wrap the Link AEAD sequence to 0 (§4.4 — fail-closed: LinkSequenceExhausted
  on u32::MAX, teardown + re-establish).
- Allow unbounded fragmentation memory (§4.5 — all MAX_* bounds enforced).
- Use QUIC migration to silently substitute the authenticated peer NodeId
  (§10.2).
- Imply that N2.3 circuit packets implement generic reliable transport
  (§10.3 — Datagram Links are authenticated/unordered/lossy; recovery is
  higher-layer).
- Persist Link state (`link_key`, sequence, replay window) across restart
  (§7.4 — fresh handshake on each restart; no Link persistence).
- Use a separate fragment-sequence space — fragments consume Link transmit
  sequences (§4.5.1; one fragment = one Link sequence; no double-AEAD of an
  already-authenticated LinkFrame).
- Use a non-HKDF-SHA256 or otherwise-divergent nonce construction — the
  fragment AEAD nonce is the exact HKDF-SHA256 construction in §4.5.2
  (byte-identical across implementations; not an implementation choice).
- Allow cross-frame fragment splicing — fragments are bound to exactly one
  logical frame via ReassemblyKey + AEAD AAD (§4.5.2, §4.5.4); conflicting
  metadata causes group discard.
- Deliver incomplete/overlapping/overlength reassemblies to the
  LinkMultiplexer (§4.5.3 — only fully-validated, complete, authenticated
  LinkFrames reach the circuit layer).
- Silently reinterpret an unknown LinkFragmentProfile (§4.5.5 — unknown
  profile fails closed; fragment rejected, group discarded).
- Conflate LinkFragmentProfile (N2.4-05 Link framing) with frozen N2.3
  PacketProfile (circuit-layer concept) — they are independent.
- Provide Link-layer fragment retransmission (§4.5.7 — N2.4-05 provides
  NONE; missing fragment → reassembly timeout → discard entire incomplete
  LinkFrame; higher layers recover lost logical data).
- Roll back replay-window state on reassembly timeout (§4.5.7, §13
  invariant 22 — authenticated fragment sequences remain consumed;
  commit() is irreversible for the life of link_key; reassembly timeout
  MUST NOT make any previous sequence reusable).
- Use the raw transport MTU as the maximum fragment plaintext payload — the
  fragmenter MUST derive `max_fragment_payload = mtu - fragment_header_bytes -
  AEAD_TAG_BYTES` (§4.3, §4.5.3, §13 invariant 23). A fragment whose wire size
  exceeds the MTU is silently lost.
- Exceed `effective_max_frame_for_link` — a logical LinkFrame exceeding
  `min(MAX_LINK_FRAME_BYTES, max_fragment_payload(mtu) * MAX_LINK_FRAGMENTS)`
  MUST be rejected before transmission; the receiver enforces the same bound
  (§4.5.3, §13 invariant 24).
- Begin fragmenting a logical frame without verifying the complete sequence
  range fits in the remaining sequence space — partial logical-frame
  transmission from sequence exhaustion is forbidden (§4.5.8, §13 invariant
  25). If the range does not fit, `LinkSequenceExhausted` and ZERO fragments.
