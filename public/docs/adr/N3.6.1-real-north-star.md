# N3.6.1 — Real End-to-End North-Star Integration

**Status:** COMPLETE

**Parent:** N3.5 External Crypto Bridge

**Baseline:** commit `aca16a2`

---

## 1. Problem Statement

N3.6 was a STUB. The proxy simulated the fetch locally instead of routing
through the mesh. The `X-ShareNet: true` header was fabricated by the proxy,
not produced by the mesh.

N3.6.1 fixes this: the proxy ACTUALLY routes through:
```
curl → proxy → relay → gateway → HTTP server → response
```

And the tests prove non-bypassability:
- If the relay is disabled → request MUST fail
- If there is no mesh → request MUST fail
- The response body MUST come from the external HTTP server
- The gateway NodeId MUST be in the response

## 2. What Changed

### 2.1 NorthStarProxy rewritten

The proxy no longer simulates. It:
1. Parses the HTTP request from the ordinary client.
2. Creates a `SimpleTransitRequest` (CBOR).
3. Connects to the relay via TCP (not directly to the gateway).
4. Sends a `TransitForward` message.
5. Receives the response from the relay (which got it from the gateway).
6. Returns the response as an ordinary HTTP response with `X-ShareNet-Gateway: <node_id>`.

If the relay is unreachable, the proxy returns `502 Bad Gateway`.

### 2.2 NorthStarMesh

Spawns the real mesh topology:
- HTTP server (simulating the "real Internet")
- Gateway process (fetches from the HTTP server via TCP)
- Relay process (forwards between proxy and gateway)

### 2.3 Proof of mesh usage

The `X-ShareNet-Gateway` header contains the real gateway's NodeId prefix.
This is NOT fabricated by the proxy — it comes from the `SimpleTransitResponse`
that the gateway created and sent through the relay.

The response body comes from the external HTTP server — verified by checking
it matches the unique string the server was configured to return.

## 3. Negative Tests

- **Relay disabled** → request returns 502 (relay unreachable)
- **No mesh at all** → request returns 502 (port 1 unreachable)
- **Malformed request** → proxy returns 400 Bad Request
