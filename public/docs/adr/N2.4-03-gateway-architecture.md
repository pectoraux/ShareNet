## 1. Problem Statement

N2.3 provides authenticated, encrypted, replay-protected circuit
forwarding from source to gateway. N2.4-02 provides a capability
authorization model (governance → issuer → authorization → capability).

N2.4-03 defines the **Internet gateway** — the node that bridges
ShareNet circuits to the real Internet. This is the first point where
the abstract capability/authorization model becomes a real security
boundary: a gateway decrypts the ShareNet circuit layer and makes
outbound Internet connections on behalf of the user. Whether the
gateway can see application plaintext depends on the Internet mode
(§12): Mode A terminates the application-layer request at the gateway;
Mode B forwards a byte stream and may preserve end-to-end TLS.

The gateway ADR MUST consume the N2.4-02 authority model. It MUST NOT
create a parallel gateway authorization system.

---

## 2. Gateway Terminology

| Term | Definition |
|------|-----------|
| **GatewayClaim** | A node self-asserts `INTERNET_GATEWAY` capability. Signed by the node. |
| **GatewayAuthorization** | A `CapabilityAuthorization` for `INTERNET_GATEWAY`, signed by an authorized issuer, bound to an `IssuerAuthority` version/digest. |
| **GatewayPolicy** | What the gateway claims it permits (destinations, protocols, bandwidth, logging). Self-asserted by the gateway. |
| **GatewayCapacity** | What the gateway claims it can provide (bandwidth, concurrency, latency). Self-asserted. |
| **GatewayObservation** | What the network has measured about this gateway (uptime, latency, throughput). Empirical. |
| **GatewaySelection** | The client's choice among authorized, available gateways based on policy, capacity, observation, and preferences. |
| **GatewayExit** | The act of making an outbound Internet connection from a ShareNet circuit's terminal gateway. |

**Critical separation (from N2.4-02):**

```
Authorization   = "this node is permitted to act as a gateway"
Policy          = "what the gateway says it permits"
Capacity        = "what the gateway says it can provide"
Observation     = "what the network has actually observed"
```

These are NOT collapsed into one struct.

## 3. Capability/Authorization Integration

### 3.1 Gateway trust chain

```
Node identity (Ed25519)
    ↓
GatewayClaim (self-asserted, signed by node)
    ↓
GatewayAuthorization (CapabilityAuthorization, issuer-signed,
                     bound to IssuerAuthority version + digest)
    ↓
IssuerAuthority (governance-signed, versioned)
    ↓
GovernanceTrustAnchor (deployment-configured root key)
```

A self-asserted `INTERNET_GATEWAY` claim MUST NEVER itself authorize
privileged gateway operation. The claim is advertisement; only the
`CapabilityAuthorization` from a recognized issuer permits operation.

### 3.2 Authorization verification

Gateway authorization uses the N2.4-02 `verify_authorization()` algorithm
(12 steps) with:
- `capability = INTERNET_GATEWAY`
- The `issuer_authority_version` and `issuer_authority_digest` in the
  authorization bind it to the exact governance-signed authority state.
- Authorization lifetime is bounded by authority lifetime.

### 3.3 Scope evaluation

`evaluate_scope(auth, requested_exit)` tests set membership only:

> Does the requested exit (destination, protocol, port) fall within
> the `AuthScope` of the authorization?

It is a **declarative membership test**. It is NOT a guarantee that the
gateway will actually permit the exit — that is gateway-enforced
policy (§5). It is also NOT the complete permission test: the
*effective* permission is the intersection of the authorization scope
and the gateway's declared policy (§17, invariant 13). Scope
evaluation is separate from cryptographic authorization verification
(§3.2).

## 4. Gateway Lifecycle

```
advertised (GatewayClaim exists)
    ↓
authorized (GatewayAuthorization valid)
    ↓
available (reachable + observed active)
    ↓
degraded (reachable but poor performance/observation)
    ↓
unavailable (unreachable or expired)
    ↓
revoked / expired (authorization revoked or expired)
```

**Separate dimensions:**

| Dimension | Source | Meaning |
|-----------|--------|---------|
| Authorization validity | `verify_authorization()` | The gateway is permitted to operate |
| Reachability | Network transport | The gateway is currently connected |
| Observed availability | `GatewayObservation` | The gateway has been measured as working |
| Policy availability | `evaluate_scope()` | The gateway's policy permits the requested exit |

A gateway can be authorized but offline. A gateway can be reachable
but unauthorized. A gateway can be authorized and reachable but
policy-incompatible.

## 5. Gateway Policy

### 5.1 Policy structure

```text
GatewayPolicy {
    destinations_allowed:  PolicyRule,    // allowlist / denylist / wildcard
    destinations_denied:    PolicyRule,    // explicit deny (SSRF protection)
    protocols_allowed:     PolicyRule,    // TCP / UDP / QUIC / all
    ports_allowed:         PolicyRule,    // port ranges
    bandwidth_claim:       u64,            // claimed bps
    byte_quota_per_period: Option<u64>,    // claimed quota
    period_seconds:        u64,            // quota period
    region:                Option<String>, // claimed geographic region
    exit_logging:          bool,           // does the gateway log? (claimed)
    concurrent_circuit_limit: Option<u32>, // claimed max circuits
}
```

### 5.2 Policy enforcement classification

| Policy item | Enforcement layer | ShareNet can enforce? |
|------------|-------------------|---------------------|
| Destination allowlist | Gateway-enforced | No — gateway can bypass |
| Destination denylist (SSRF) | Gateway-enforced | No — gateway can bypass |
| Protocol restrictions | Gateway-enforced | No — gateway can bypass |
| Port restrictions | Gateway-enforced | No — gateway can bypass |
| Bandwidth limits | Gateway-enforced | No — best-effort |
| Byte quotas | Gateway-enforced | No — best-effort |
| Logging declaration | Informational | No — cannot verify |
| Concurrent circuit limit | Gateway-enforced | No — gateway can accept more |

### 5.2.1 Three properties of gateway policy (normative)

Gateway policy is decomposed into three **separate** properties. They
MUST NOT be collapsed into a single notion of "authenticated policy":

| Property | Meaning | Verifiable by ShareNet? |
|----------|---------|-------------------------|
| **Policy provenance** | This exact policy was signed by gateway `G`. | Yes — the signature is verified against `G`'s identity. |
| **Policy truthfulness** | `G` actually enforces this policy in practice. | **No.** A gateway may claim "no logging" while actually logging. |
| **Policy enforcement** | The mechanism that applies the policy to a connection. | **Gateway-local.** Enforcement happens inside the gateway, outside the ShareNet protocol boundary. |

### 5.2.2 What `evaluate_scope()` means (against policy)

When applied to a gateway's declared policy, `evaluate_scope()` means
**only**:

> The requested operation is a member of the gateway's declared policy
> set (destinations, protocols, ports).

It does **NOT** mean:

> The gateway will actually enforce this policy for this connection.

A gateway whose declared policy contains the denylist but does not
enforce it remains indistinguishable to the protocol from a compliant
gateway, except via out-of-band `GatewayObservation` (§7).

### 5.2.3 Architectural invariant

ShareNet authenticates **authorization** and **policy provenance**.
ShareNet does NOT verify **policy truthfulness** and does NOT perform
**policy enforcement**. The protocol's job is to make policy **visible**
(so users can choose) and **provenance-authenticated** (so the policy
bytes are what the gateway signed), not to **enforce** it. Enforcement
is a gateway-local responsibility that the protocol cannot audit.

### 5.3 SSRF protection (destination validation)

Destination safety is an **architectural procedure**, not merely a
static denylist in policy text. A gateway that lists forbidden ranges
but connects to a DNS-resolved private address still performs SSRF.
This section defines the procedure the gateway MUST execute; §10
enumerates the forbidden ranges and §10.3 defines the DNS-safety
sub-procedure.

#### 5.3.1 Destination validation procedure (normative)

For every outbound Internet connection, the gateway MUST execute:

```text
1. resolve      — resolve the requested destination to a concrete
                  set of candidate IP addresses (DNS, or a literal IP).
2. canonicalize — reduce every candidate address to a canonical form,
                  including expanding IPv4-mapped IPv6 (::ffff:a.b.c.d)
                  to its IPv4 form, and normalizing zone IDs / scopes.
3. validate     — check EVERY canonicalized address against the
                  forbidden-range set (§10.1). If ANY candidate
                  address is forbidden, the connection is rejected.
4. pin & connect — connect to EXACTLY one of the validated addresses
                   from step 3. The resolved address MUST be pinned
                   (used directly for connect()) so a second DNS
                   lookup cannot substitute a different address.
```

#### 5.3.2 TOCTOU / DNS-rebinding prevention (normative)

Steps 3 and 4 MUST NOT be separated by a fresh DNS resolution. The
classic failure mode is:

```text
DNS lookup #1  →  203.0.113.10   (validate OK)
                                      ↓ (time passes)
DNS lookup #2  →  10.0.0.5        (private — but connect() uses this)
```

To prevent this, the gateway MUST:

- resolve once, validate every result, and `connect()` to a validated
  IP literal directly (pinned resolution), OR
- use a resolver + connect path that guarantees the validated address
  is the connected address (e.g. hold the `getaddrinfo` result and pass
  it to `connect()` without re-resolution).

A second DNS lookup between validation and connection is a protocol
violation. This is **architectural**, not an implementation detail;
implementation detail is deferred to ADR-0008 (gateway egress
DNS-rebinding defence).

#### 5.3.3 Classification

Destination validation is **gateway-enforced**, not protocol-enforced.
The protocol REQUIRES the policy to contain the forbidden-range set
(§10.1) so users can see it and so `evaluate_scope()` (policy) can
reject forbidden destinations declaratively. The protocol cannot
guarantee the gateway actually executes §5.3.1–5.3.2; only
`GatewayObservation` (§7) or destination-side audits can detect
violation.

## 6. Gateway Capacity

### 6.1 Capacity structure

```text
GatewayCapacity {
    bandwidth_bps:              u64,
    max_concurrent_circuits:    u32,
    byte_budget_per_period:     Option<u64>,
    period_seconds:             u64,
    latency_ms_claim:           u32,
    uptime_percentage_claim:    u8,    // 0-100
}
```

### 6.2 Claimed vs measured vs available

```
Claimed capacity  = GatewayCapacity (self-asserted)
Measured capacity = GatewayObservation (empirical)
Available capacity = Claimed ∩ Measured ∩ current_load
```

Self-reported capacity MUST NOT become trusted routing fact. It is an
input to GatewaySelection, not an authorization.

## 7. Gateway Observation

### 7.1 What is measured

```text
GatewayObservation {
    measured_uptime:       u8,     // 0-100
    measured_latency_ms:   u32,
    measured_throughput:   u64,    // bps
    measured_circuit_count: u32,
    last_seen_active:      u64,    // unix seconds
    observation_count:     u32,    // how many observations
}
```

### 7.2 What observations can and cannot do

Observations CAN:
- Inform GatewaySelection (a user prefers gateways with good uptime)
- Trigger revocation proposals (if a gateway is observed violating policy)
- Feed reputation systems (future, separate from protocol)

Observations CANNOT:
- Grant authorization (only issuer signatures authorize)
- Override revocation
- Replace cryptographic authorization

## 8. Gateway Selection

### 8.1 Selection inputs

A client choosing among authorized gateways may consider:

| Input | Source | Trust level |
|-------|--------|-------------|
| Authorization validity | `verify_authorization()` | Cryptographic |
| Authorization scope | `evaluate_scope()` (against authorization) | Cryptographic membership test |
| Policy provenance | signature verification | Cryptographic (provenance only) |
| Policy compatibility | `evaluate_scope()` (against declared policy) | Provenance-authenticated; truthfulness unverified (§5.2.1) |
| Effective permission | authorization scope ∩ declared policy (§17, inv. 13) | Compositional |
| Measured availability | `GatewayObservation` | Empirical |
| Latency | Network measurement | Empirical |
| Throughput | `GatewayObservation` | Empirical |
| Trust/reputation | External reputation system | Non-protocol |
| User preferences | Client configuration | Local |
| Cost/Civic Points | Economic layer (if approved) | Non-protocol |

### 8.2 Selection ordering (normative)

Selection MUST be ordered so that an unauthorized or scope-incompatible
gateway CANNOT influence trusted selection results. The order is:

```text
candidate gateway (GatewayClaim observed)
    ↓
1. verify CapabilityAuthorization          (cryptographic; reject if absent/invalid)
    ↓
2. verify authorization validity/revocation (not expired, not revoked,
   authority version/digest valid)
    ↓
3. evaluate authorization scope             (requested exit ∈ AuthScope?)
    ↓
4. evaluate declared gateway policy         (requested exit ∈ declared policy?
   provenance verified; truthfulness unverified)
    ↓
5. compute effective permission             (authorization scope ∩ policy,
   §17 invariant 13)
    ↓
6. verify reachability                      (transport)
    ↓
7. evaluate observations                    (GatewayObservation)
    ↓
8. apply user preferences / economics       (Civic Points, cost, region)
    ↓
9. select gateway
```

**Mandatory property:** A gateway that fails step 1, 2, 3, or 4 MUST
NOT appear in trusted selection results. Economic and observation
inputs (steps 7–8) are applied ONLY to gateways that already passed
steps 1–5. An unauthorized gateway cannot "win" selection by offering
lower cost or better observed performance.

### 8.3 Selection invariant

> Economic incentives MUST NOT silently become cryptographic authority.

A gateway with more Civic Points is NOT more authorized. Civic Points
may influence **selection priority** (a user may prefer cheaper gateways)
but MUST NOT influence **authorization validity** (only `verify_authorization()`
determines that).

## 9. Gateway Exit Boundary

### 9.1 What the gateway sees (mode-dependent)

What the gateway can see is determined by the Internet mode (§12), not
by a single universal rule:

```text
Mode A — Application-layer gateway fetch (§12 Mode A):
    The gateway terminates the ShareNet application request and itself
    constructs the outbound Internet request. The gateway MAY see
    application plaintext, request method, headers, and body, because
    it terminates the application-layer request at the gateway.
    End-to-end TLS (user → destination) is NOT provided by Mode A.

Mode B — Byte-stream proxy (§12 Mode B):
    The gateway forwards a raw byte stream (TCP/CONNECT). The user's
    application speaks directly to the destination through the tunnel.
    If the user's application runs TLS, that TLS is end-to-end
    (user → destination); the gateway sees network metadata
    (destination IP, timing, volume) but NOT the application plaintext.
```

In both modes the gateway sees destination network metadata, including
destination IP and, where exposed by the protocol/application, hostname
and other metadata (e.g. SNI in TLS for Mode B, the Host header for
Mode A).

### 9.2 What ShareNet does NOT guarantee

- ShareNet does NOT guarantee anonymity (gateway sees destination
  network metadata; first relay sees source; timing correlation is
  possible).
- ShareNet does NOT guarantee that the gateway honors its declared
  policy (§5.2.1: policy truthfulness is unverified).
- ShareNet does NOT terminate the user's TLS session in Mode B; the
  user's application is responsible for verifying the destination's
  TLS certificate. In Mode A the gateway terminates the application
  request; end-to-end TLS is not a property of Mode A (§12).
- ShareNet does NOT prevent a malicious gateway from modifying
  unencrypted responses (Mode A) or from observing plaintext it is
  positioned to see.

### 9.3 Traffic metadata exposure

| What | Visible to gateway? | Visible to relay? | Visible to destination? |
|------|--------------------|--------------------|----------------------|
| Source NodeId | No (only predecessor relay) | No (only predecessor) | No |
| Destination network metadata (IP +, where exposed, hostname / protocol metadata) | Yes | No | N/A |
| Application plaintext (unencrypted, both modes) | Yes | No | N/A |
| Application plaintext (TLS, Mode A) | Yes — gateway terminates app request | No | N/A |
| Application plaintext (TLS, Mode B) | No — TLS is user→destination | No | N/A |
| Packet timing | Yes | Yes (per-hop) | N/A |
| Traffic volume | Yes | Yes (per-hop) | N/A |
| Connection frequency | Yes | No | N/A |

## 10. Destination Safety

### 10.1 Mandatory forbidden-range set (gateway-declared, gateway-enforced)

The gateway policy MUST include a forbidden-range set covering at least
the following. This is the data that step 3 of §5.3.1 validates against:

**IPv4:**
- `0.0.0.0/8` — "this host" / unspecified source
- `10.0.0.0/8` — RFC 1918 private
- `100.64.0.0/10` — carrier-grade NAT (RFC 6598)
- `127.0.0.0/8` — loopback
- `169.254.0.0/16` — link-local (includes `169.254.169.254` cloud
  metadata endpoints)
- `172.16.0.0/12` — RFC 1918 private
- `192.0.0.0/24` — IETF protocol assignments (IANA special registry)
- `192.0.2.0/24` — TEST-NET-1 (documentation)
- `192.168.0.0/16` — RFC 1918 private
- `198.18.0.0/15` — benchmarking
- `198.51.100.0/24` — TEST-NET-2 (documentation)
- `203.0.113.0/24` — TEST-NET-3 (documentation)
- `224.0.0.0/4` — multicast
- `240.0.0.0/4` — reserved (includes `255.255.255.255/32` broadcast)

**IPv6:**
- `::/128` — unspecified
- `::1/128` — loopback
- `::ffff:0:0/96` — IPv4-mapped IPv6 (MUST be canonicalized to IPv4
  and checked against the IPv4 set per §5.3.1 step 2)
- `64:ff9b::/96` — IPv4/IPv6 translation (NAT64 well-known prefix)
- `100::/64` — discard prefix
- `2001::/23` — IETF protocol / reserved
- `2001:db8::/32` — documentation
- `fc00::/7` — unique local addresses
- `fe80::/10` — link-local
- `ff00::/8` — multicast

**ShareNet-internal:**
- All ShareNet relay/gateway/seed node addresses, to prevent
  gateway-to-gateway loops and exfiltration to the overlay itself.
  (Gateway-to-gateway loop prevention is finalized in N2.4-04.)

### 10.2 Enforcement classification

- **Protocol-level (declarative):** The policy MUST contain the
  forbidden-range set, provenance-authenticated in the signed policy.
  The protocol verifies the set is present. The protocol CANNOT verify
  the gateway executes validation against it (§5.2.1 truthfulness).
- **Gateway-enforced (procedural):** The gateway MUST execute the
  destination validation procedure (§5.3.1) for every connection,
  including the DNS-safety sub-procedure (§10.3). The protocol cannot
  guarantee this.
- **Client-side:** The client can verify the policy contains the
  forbidden-range set before selecting the gateway (§8.2 step 4).

### 10.3 DNS safety (sub-procedure of §5.3)

DNS resolution is part of the destination validation procedure, not a
separate concern. The gateway resolves DNS on behalf of the user (the
user cannot make direct DNS queries through ShareNet). The gateway
MUST:

- Resolve the name to the full set of candidate addresses (A and AAAA).
- Canonicalize each (§5.3.1 step 2), including IPv4-mapped IPv6.
- Validate EVERY candidate address against §10.1. If ANY candidate is
  forbidden, reject the connection (do not fall through to another
  candidate).
- Pin the validated address and connect to it directly (§5.3.2). No
  re-resolution between validation and connect().

This defeats both DNS rebinding (the address used at connect() is the
address that was validated) and TOCTOU (no second lookup).

**Classification:** Gateway-enforced, architecturally normative (§5.3).
The protocol cannot verify DNS behaviour; only `GatewayObservation`
(§7) or destination-side audits can detect violation. Detailed
implementation is specified in ADR-0008 (gateway egress DNS-rebinding
defence).

## 11. Abuse Controls

### 11.1 Gateway operator controls

- Quotas (byte/circuit/time) — gateway-enforced, best-effort
- Rate limiting — gateway-enforced, best-effort
- User identity exposure — the gateway sees the predecessor relay's
  NodeId, not the source's NodeId (unless the source is the direct
  predecessor). This is inherent in the onion model.
- Emergency gateway disable — the issuer can subject-revoke the
  gateway's authorization; governance can revoke the issuer.

### 11.2 Abuse reporting

- Abuse reports are out-of-protocol (not a ShareNet protocol message).
- The gateway operator is responsible for handling abuse from
  destination networks (DMCA, complaints, etc.).
- ShareNet does NOT provide a protocol-level abuse-reporting mechanism
  in N2.4-03.

### 11.3 Legal/liability

ShareNet does NOT make legal conclusions. Gateway operators are
responsible for compliance with their jurisdiction. This ADR identifies
areas requiring jurisdiction-specific review but does NOT provide
legal guidance.

## 12. Internet Modes

### Mode A — Application-layer gateway fetch

> **TLS property:** End-to-end TLS (user → destination) is **NOT**
> provided by Mode A. The gateway terminates the ShareNet
> application-layer request and may see application plaintext.

```
User → ShareNet circuit → Gateway → HTTP request → Internet
                                         ↓
                              HTTP response → Gateway → ShareNet → User
```

- Gateway role: the gateway terminates the ShareNet application-layer
  request and itself constructs the outbound HTTP/HTTPS request to the
  destination.
- Transport assumptions: HTTP/HTTPS over the gateway's Internet
  connection.
- Security boundary: the gateway MAY see application plaintext, request
  method, headers, and body, because it terminates the application-layer
  request at the gateway. **End-to-end TLS (user → destination) is NOT
  a property of Mode A.** If payload confidentiality against the gateway
  is required, use Mode B, or layer an additional end-to-end protection
  (application-level signing/encryption, or a Mode-A-specific protocol
  that carries an outer TLS session the gateway forwards verbatim).
- Failure behavior: if the gateway fails mid-request, the circuit tears
  down. The user retries with a different gateway.
- Policy enforcement point: gateway (before making the outbound request,
  via §5.3 destination validation).
- Platform requirements: none beyond ShareNet client + circuit.

### Mode B — Byte-stream proxy

> **TLS property:** End-to-end TLS (user → destination) **MAY** remain
> in place. The gateway forwards a raw byte stream and does not
> terminate the user's TLS session.

```
User → ShareNet circuit → Gateway → CONNECT/TCP proxy → Internet
```

- Gateway role: the gateway forwards a raw byte stream. It establishes
  an outbound TCP connection to the destination on behalf of the user
  and pipes bytes in both directions.
- Transport assumptions: TCP tunnel. The user's application speaks
  directly to the destination through the tunnel.
- Security boundary: TLS MAY remain end-to-end (user → destination).
  If the user's application runs TLS, the gateway sees network metadata
  (destination IP, SNI, timing, volume) but NOT the application
  plaintext. The gateway does not terminate the user's TLS session.
- Failure behavior: circuit teardown. The TCP connection is lost.
- Policy enforcement point: gateway (before establishing the tunnel,
  via §5.3 destination validation).
- Platform requirements: client-side proxy configuration (SOCKS / HTTP
  CONNECT).

### Mode C — Transparent OS-level Internet

```
OS application → TUN/VPN → ShareNet client → circuit → Gateway → Internet
```

- Gateway role: transparent IP egress.
- Transport assumptions: IP tunnel from the OS to the ShareNet client.
- Security boundary: TLS end-to-end. Gateway sees IP-level metadata.
- Failure behavior: TUN interface goes down. Applications see
  connection loss.
- Policy enforcement point: gateway (IP-level filtering) +
  ShareNet client (circuit management).
- Platform requirements: TUN/VPN support, OS-level routing.

**N2.4-03 scope:** Modes A and B are architectural candidates. Mode C
is deferred to a future platform-integration ADR (N2.7+).

## 13. Privacy

### 13.1 What is visible to each party

| Party | Sees |
|-------|------|
| Source (user) | Everything (their own traffic) |
| Intermediate relay | Ciphertext, predecessor NodeId, timing |
| Gateway | Destination network metadata (IP +, where exposed, hostname / protocol metadata), connection metadata, application plaintext where the mode terminates it at the gateway (Mode A), timing, volume |
| Internet destination | Gateway's source IP (not the user's), application traffic |

### 13.2 What ShareNet does NOT guarantee

- Anonymity: gateway sees destination network metadata; first relay
  sees source.
- End-to-end TLS in Mode A: Mode A terminates the application-layer
  request at the gateway (§12). End-to-end TLS (user → destination)
  is available in Mode B, not Mode A.
- Policy truthfulness: a gateway may violate its declared policy
  (§5.2.1).
- Traffic analysis resistance: timing correlation is possible.
- Fingerprint resistance: packet sizes may leak information.

### 13.3 Privacy improvements (future)

- Padding (uniform packet sizing) — N2.4-08 (if required)
- Timing obfuscation — future
- Entry guards (source uses a fixed first relay) — future
- Multi-circuit diversity — future

## 14. Failure/Recovery

### 14.1 Gateway failure modes

| Failure | Detection | Recovery |
|---------|-----------|----------|
| Gateway offline (transport) | Circuit timeout | Re-establish circuit with different gateway |
| Gateway authorization expired | `verify_authorization()` fails | Select a different authorized gateway |
| Gateway authorization revoked | Revocation list check | Select a different authorized gateway |
| Gateway degraded (slow) | `GatewayObservation` | Select a different gateway (user preference) |
| Gateway policy violation (observed) | `GatewayObservation` | Reputation impact; user selects different gateway |
| Issuer compromised | Governance revocation | All authorizations from that issuer expire |

### 14.2 Circuit interaction

```
Gateway selection
    ↓
Route discovery (find path to selected gateway)
    ↓
Route authorization (signed acceptances from relays + gateway)
    ↓
CommittedRoute (cryptographically bound)
    ↓
Circuit (N2.3 forwarding)
    ↓
Gateway receives forward traffic
    ↓
Gateway exits to Internet (Mode A/B)
```

An authorized gateway does NOT automatically imply a valid route. The
client must discover a route, get acceptances, and establish a circuit
using the N2.3 protocol.

## 15. Revocation/Partition Behavior

Uses N2.4-02's exact bounded-staleness model:

| Event | Immediate effect | Bounded stale window |
|-------|-----------------|---------------------|
| Gateway authorization expires | Gateway cannot accept new circuits | Existing circuits continue until circuit expiry |
| Gateway authorization revoked (subject) | Gateway cannot accept new circuits | Existing circuits continue until circuit expiry |
| Issuer governance-revoked | Issuer cannot sign new authorizations | Existing authorizations valid until their own expiry |
| Network partition | Node cannot verify new authorizations | Existing authorizations valid until their own expiry |
| Node restart | Persistent state recovered (N2.4-02 invariant #11) | No stale-state window (if persistence succeeds) |

## 16. Civic Points Boundary

### 16.1 What Civic Points MAY influence

- Gateway selection priority (user prefers cheaper gateways)
- Resource pricing (gateway charges per byte/circuit)
- Quota allocation (higher-paying users get more bandwidth)
- Reputation weight (economic reputation informs selection)

### 16.2 What Civic Points MAY NOT influence

- Cryptographic authorization (only `verify_authorization()` determines validity)
- Routing security decisions (the protocol must work without Civic Points)
- Revocation (subject-level: issuer-signed; issuer-level: governance-signed)

### 16.3 Boundary

```
Authorization
    ↓
security authority (issuer signature, verify_authorization())

Civic Points
    ↓
economic/resource accounting (separate layer)

Selection
    ↓
user preference (may consider both, but authorization is a prerequisite)
```

## 17. Security Invariants

1. **Self-asserted gateway claim never equals authorization.** A claim
   is advertisement; only `CapabilityAuthorization` permits operation.
2. **Unauthorized gateway cannot become a circuit destination.** The
   client MUST verify authorization before routing to a gateway.
3. **Expired authorization cannot authorize new service.** New circuits
   require currently-valid authorization.
4. **Revoked authorization cannot authorize new service.** Revocation
   check is mandatory before new circuit establishment.
5. **Gateway policy cannot expand authorization scope.** Policy is a
   claim; it cannot grant capabilities beyond the authorization's scope.
6. **Self-reported capacity cannot become measured capacity.** Claims
   are inputs to selection, not trusted facts.
7. **Authorized gateway ≠ reachable gateway.** Authorization is
   cryptographic; reachability is empirical.
8. **Reachable gateway ≠ trusted gateway.** Network connectivity is
   not authorization.
9. **Gateway selection ≠ cryptographic authorization.** Selection is
   user preference; authorization is issuer-signed.
10. **Economic value ≠ authorization.** Civic Points may influence
    selection but MUST NOT determine cryptographic authority.
11. **Gateway authorization must bind to exact authority version/digest.**
    Later authority versions do not silently change existing
    authorization semantics.
12. **All security-critical authorization state survives restart.**
    Persistent state per N2.4-02 invariant #11.
13. **Effective permission is authorization scope ∩ declared policy
    (composition rule).** The effective permission for a requested exit
    is the intersection of the authorization's `AuthScope` and the
    gateway's declared `GatewayPolicy` scope. Policy MAY narrow
    authorization; policy MUST NOT expand authorization. A policy
    broader than the authorization has no authority for the
    out-of-scope portion.

    ```text
    effective_scope(request) =
        auth_scope(request) ∩ declared_policy_scope(request)
    ```
14. **Policy provenance, truthfulness, and enforcement are distinct.**
    Provenance is cryptographically authenticated; truthfulness is NOT
    cryptographically verified; enforcement is gateway-local (§5.2.1).
    `evaluate_scope()` against policy is a membership test, not an
    enforcement guarantee.
15. **Gateway selection is ordered authorization-first.** A gateway
    that fails authorization, validity/revocation, authorization-scope,
    or policy-compatibility checks MUST NOT enter trusted selection
    results. Observation and economic inputs are applied only to
    gateways that already passed authorization and scope (§8.2).
16. **End-to-end TLS is mode-dependent.** Mode A does NOT provide
    end-to-end TLS (user → destination); the gateway terminates the
    application-layer request. Mode B MAY provide end-to-end TLS, with
    the gateway seeing only network metadata (§12).
17. **Destination validation is a procedure, not a list.** The gateway
    MUST execute resolve → canonicalize → validate → pin-and-connect,
    with no DNS re-resolution between validation and connection
    (§5.3.1, §5.3.2).

## 20. Implementation Boundaries

N2.4-03 defines the **architecture**. Implementation will produce:

- Gateway advertisement types (claim + policy + capacity)
- Gateway authorization verification (reuse N2.4-02)
- Gateway selection logic, ordered authorization-first (§8.2)
- Gateway exit protocol (Mode A/B), with Mode A explicitly NOT
  promising end-to-end TLS (§12)
- Destination validation procedure (§5.3.1: resolve → canonicalize →
  validate → pin-and-connect), not merely a denylist in policy
- Authorization/policy composition (§17 invariant 13:
  effective_scope = auth_scope ∩ declared_policy)

Implementation is **blocked** until:
- N2.4-03 is approved
- N2.4-04 (Circuit Recovery) is at least proposed
- Conformance vectors are defined

**N2.3 frozen implementation MUST NOT be modified.**
