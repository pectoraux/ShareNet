## 1. Problem Statement

N2.3 provides circuits: authenticated, encrypted, replay-protected forwarding
from source to gateway over a cryptographically bound `CommittedRoute`. N2.4-03
provides the gateway architecture and lifecycle (authorization, policy,
selection, exit, revocation). Neither defines what happens when a live circuit's
underpinnings fail.

A ShareNet deployment is a **delay-tolerant distributed network over
participating devices**. Devices disappear: laptops close, phones lose signal,
relays restart, gateways expire or are revoked. A circuit that worked at
establishment time may, minutes later, sit over a dead relay or an unauthorized
gateway. The system must recover — and it must do so without lying about what
"recovery" can preserve.

N2.4-04 defines the **recovery architecture**: how failure is detected, how
recovery is decided, what is re-established, what state may be migrated, and
the hard limits on what can survive.

### The non-negotiable constraint

> **N2.4-04 MUST NOT modify the frozen N2.3 packet semantics.**

The N2.3 V1 protocol (5-field CBOR, raw AAD, `circuit_id[0..8] ‖ seq` nonce)
and the V2 protocol (8-field CBOR, domain-separated AAD, direction-XOR nonce)
are frozen at `425eccb` / `0efaaac`. The golden wire vectors are immutable.
The replay-window ordering (check-before-AEAD, commit-after-AEAD), the
`!Clone` sequence allocator, the `commitment_hash` route binding, the per-hop
TTL authentication, and the `CircuitSeqState` no-wraparound/no-exhaustion
invariants are all immutable. N2.4-04 operates **around** this frozen layer,
never **within** it. Any future in-band migration primitive that requires
packet-format changes is a `PacketProfile::V3` concern — explicitly deferred to
N2.4-07 (charter §6), not this ADR.

## 2. The Central Tension

The frozen N2.3 circuit layer **binds a circuit to exactly one `CommittedRoute`**
via `handshake.commitment_hash == route.commitment()`. The commitment covers the
proposal, all validated hops (node records + link evidence + roles), and the
sorted route acceptances. Change one relay → different commitment → different
circuit. The circuit's per-hop keys are derived from `(ephemeral_x25519_secret,
relay_pub, circuit_id, commitment_hash)` — so a different route yields different
keys. The sequence allocator is `!Clone` and owned by the single `ActiveCircuit`
instance. There is **no** frozen primitive for changing a route, a relay, or a
key under an existing `circuit_id`.

Simultaneously, spec §6.7 (02-PROTOCOL-SPEC.md:401–433) aspires to:

> "`CircuitId` is independent of both route and gateway."
> "Route switch... Circuit state preserved. Application sees a latency blip."

These two statements are in tension. The frozen implementation **does not**
make `circuit_id` independent of route — it binds them cryptographically. A
literal reading of spec §6.7 as a frozen circuit-layer property would require
modifying N2.3, which is forbidden.

### Resolution

N2.4-04 resolves the tension by **reframing the layer at which continuity
lives**:

- At the **circuit layer** (frozen N2.3): a circuit is bound to one route and
  is **not** migratable. Recovery = teardown + re-establishment under a new
  `circuit_id`.
- At the **transport session layer** (N2.4-04, new): a *session* is bound to
  neither a circuit nor a route. The session survives circuit replacement.
  The application sees continuity — or, where that is impossible (gateway
  migration with a live TCP socket), an honest reset.

This makes spec §6.7's aspiration achievable **as a session-layer property**
without modifying the frozen circuit layer. "Circuit state preserved" is
reframed as "session state preserved; underlying circuit replaced transparently
where possible, honestly-reset where not."

## 3. Architecture Overview

```
Application layer (TCP / HTTP / custom)
    ↑  sees: session continuity OR honest reset
Transport Session Layer  (N2.4-04 — NEW)
    TransportSession { session_id, current_circuit, mode, recovery_state }
    ↑  maps application sessions to circuits; survives circuit replacement
Circuit layer  (N2.3 FROZEN — V1 / V2, NOT modified by N2.4-04)
    ActiveCircuit { circuit_id, route, keys, seq_state, expires_at }  ← !Clone
    ↑  one circuit = one CommittedRoute = one commitment_hash
    ↑  recovery = teardown + re-establish (NEW circuit_id)
Route layer  (N2.1 / N2.2)
    CommittedRoute { proposal, validated_hops, commitment, acceptances }
```

**Key architectural principle:** circuits are **replaceable units**. The
session layer treats a circuit the way a TCP stack treats a network interface
card — it can be unplugged and replaced; the session above survives (or fails
honestly) depending on what the new circuit can reach.

## 4. Transport Session Layer

### 4.1 TransportSession

```text
TransportSession {
    session_id:           TransportSessionId,   // see §4.2
    mode:                 InternetMode,          // Mode A | Mode B (§12 of N2.4-03)
    current_circuit:      Option<ActiveCircuit>, // the live circuit, or None during recovery
    destination:          DestinationDescriptor, // the application's target
    binding_epoch:        u64,                    // monotonic session binding generation (§4.3)
    gateway_session_key:  Option<SessionBindingKey>, // gateway-side re-association (§4.4)
    recovery_state:       RecoveryState,         // §6
    created_at:           u64,
    recovery_budget:      u8,                     // §13
}
```

A `TransportSession` is a **client-side** abstraction. It is NOT a protocol
message type and is NOT sent over the wire as a single object. It is local
state that coordinates circuit lifecycle with application continuity.

### 4.2 TransportSessionId (TSID)

The `TransportSessionId` (TSID) is a **session identifier carried in the gateway
application protocol**, NOT in the circuit packet wire format. This is the
critical design choice that keeps N2.4-04 out of the frozen packet layer.

- **Mode A (application fetch):** the TSID is an attribute of the Mode A
  request (e.g., an application-layer header in the gateway application
  protocol). The gateway maps `TSID → outbound request context`.
- **Mode B (byte-stream proxy):** the TSID is carried in the CONNECT
  request metadata when the tunnel is first established. The gateway maps
  `TSID → outbound TCP connection`.

The TSID is:
- **Opaque to relays.** Relays forward encrypted circuit packets; they never
  see or interpret the TSID.
- **Not part of the circuit packet.** No V1/V2 field, no AAD binding, no
  nonce contribution. The frozen packet format is untouched.
- **Gateway-interpreted.** Only the source and the gateway understand the TSID.
- **Random and unguessable** (≥128 bits from the OS CSPRNG), to prevent
  session-hijacking by guessing.

### 4.3 Session Binding Epoch (monotonic generation)

R1 recovery and proactive (make-before-break) recovery replace the circuit
bound to a session. To reject stale traffic from an **old** circuit after
rebinding — including delayed packets from C1 arriving after the gateway has
rebound to C2 — the binding has a **monotonic epoch** that the gateway checks
on every packet/request for the session:

```text
SessionBindingEpoch {
    tsid:        TransportSessionId,
    epoch:       u64,                 // monotonic, starts at 1
    circuit_id:  CircuitId,           // the circuit bound at this epoch
}
```

**Epoch rules (normative):**

| Event | epoch effect |
|-------|--------------|
| First binding (session establishment) | `epoch = 1`, `circuit_id = C1` |
| RESUME to a new circuit (R1 / R0) | `new_epoch = current_epoch + 1`, `circuit_id = new` |
| Same epoch, same circuit_id (duplicate RESUME) | idempotent no-op (do not advance) |
| Same epoch, different circuit_id | protocol violation — reject |
| Lower epoch (stale/delayed) | reject — the binding has moved forward |
| Equal-or-higher epoch from a non-source principal | reject — only the source advances epochs |

**Gateway acceptance rule (normative):** the gateway accepts traffic
for a session only from the circuit_id at the **current** epoch recorded in
its `GatewaySessionTable` (§9.2). Traffic on a `circuit_id` that is **not**
the current epoch's circuit is rejected as stale, regardless of whether the
packet decrypts correctly under that old circuit's keys. This closes the
stale-old-circuit race that a mere equality check on `bound_circuit_id`
would leave open during make-before-break, when two circuits briefly coexist.

**Ordering mechanism (normative):** the epoch is a **monotonic persistent
integer**, NOT a timestamp and NOT a random nonce. This is consistent with
ShareNet's established pattern of monotonic state for ordering (N2.4-02
authority versions, N2.3 sequence numbers). The epoch is incremented by the
source on each successful RESUME and persisted as part of the session state
(§11). It survives source restart as a counter (but see §7.5: the binding
**key** does NOT survive restart, even though the epoch counter does).

**Make-before-break interaction (§7.4):** during proactive recovery, the
old circuit continues to carry traffic at epoch N while the new circuit is
being established. The source MUST NOT send user traffic on the new circuit
until the gateway has confirmed the RESUME (epoch N+1). Until then, the
gateway's current epoch remains N and it accepts only the old circuit. The
epoch advances atomically on confirmed RESUME; there is no window in which
both circuits are accepted for new user traffic.

### 4.4 SessionBindingKey

For **Mode B** relay-only recovery (§8.1), the gateway must re-associate a
new circuit's traffic with an existing outbound TCP connection. The gateway
holds a `SessionBindingKey` that authenticates the re-binding (RESUME)
request on the new circuit.

The binding credential is **two-tier**: a long-lived
`SessionBindingRootKey` (shared between source and gateway at the same
gateway) plus an **epoch-specific** `SessionBindingKey` derived from it.
This resolves the cryptographic contradiction between "the key is bound to
the exact epoch" and "the key is reused across epoch changes": the **root**
key survives same-gateway circuit replacement; the **epoch-specific** key
changes with every epoch.

```text
SessionBindingRootKey                         // established at first binding
        ↓
    KDF(domain_separator,
        gateway_node_id,
        TSID,
        binding_epoch,                          // the epoch this key is for
        expiry)
        ↓
SessionBindingKey(epoch)                      // epoch-specific RESUME credential
```

Therefore:

```text
epoch 1 → K1   (distinct epoch-specific key)
epoch 2 → K2   (distinct epoch-specific key)
epoch 3 → K3   (distinct epoch-specific key)
```

The **root** key remains the same at the same gateway across R1/R0 circuit
replacements; the **epoch-specific** key changes with each epoch. The gateway
verifies the epoch-specific key for the epoch claimed in the RESUME. This makes
the epoch binding cryptographically meaningful: each epoch has a distinct
RESUME credential, so a stale lower-epoch key cannot authorize a higher-epoch
RESUME (the derivation input differs).

#### 4.4.1 Cryptographic binding context (normative)

The **epoch-specific** `SessionBindingKey(epoch)` MUST be cryptographically
bound to the **exact** session, gateway, and epoch context it authorizes. A
valid key presented for the wrong TSID, wrong gateway, wrong epoch, or wrong
expiry MUST be rejected. The binding context (KDF input) is:

```text
SessionBindingKeyContext(epoch) =
    domain_separator            // e.g. "SNP/0.1/session/binding/v1"
    || gateway_node_id          // the gateway's authenticated NodeId (spec/02-identity)
    || tsid                     // the TransportSessionId this key authorizes
    || binding_epoch            // the exact epoch this key is derived for
    || expiry                   // when this binding key ceases to be valid
```

The exact KDF (HKDF, KDF from the first circuit's Mode B handshake, or a
fresh ephemeral exchange) and the `SessionBindingRootKey` derivation are
implementation/N2.5 concerns, but the **binding invariant** is normative in
N2.4-04: the epoch-specific key MUST be derived as `KDF(root, context(epoch))`
where `context(epoch)` covers all five fields, and the gateway MUST verify the
derivation against the claimed epoch on every RESUME. The root key MUST NOT be
used directly as a RESUME credential — only epoch-specific derivations are
presented in RESUME messages.

#### 4.4.2 Anti-confused-deputy rule (normative)

The epoch-specific `SessionBindingKey(epoch)` authorizes **resumption of
this exact session at this exact gateway for the circuit identified in the
RESUME at the exact epoch `epoch`**. It MUST NOT be treated as a general
bearer credential. Specifically:

- A `SessionBindingKey(epoch)` for TSID `A` MUST NOT authorize resumption of
  TSID `B`.
- A `SessionBindingKey(epoch)` established at Gateway `G1` MUST NOT authorize
  resumption at Gateway `G2` (the binding context's `gateway_node_id` differs).
- A `SessionBindingKey(N)` MUST NOT authorize resumption at epoch `N+1` or
  any other epoch — the epoch-specific derivation differs. The gateway checks
  epoch monotonicity (§4.3) AND that the presented key matches
  `KDF(root, context(new_epoch))`.
- A `SessionBindingKey(epoch)` past its `expiry` MUST NOT authorize any
  resumption.
- The `SessionBindingRootKey` MUST NEVER be presented in a RESUME message;
  only epoch-specific derivations are. The root key is not itself a RESUME
  credential.

#### 4.4.3 Separation from circuit forwarding keys (normative)

The `SessionBindingRootKey` and epoch-specific `SessionBindingKey` are
**distinct from circuit forwarding keys**. They are not AEAD keys for packet
forwarding (the frozen N2.3 per-hop forwarding keys are); they authenticate
only the RESUME control message in the gateway application protocol. They MUST
NOT be used to wrap or unwrap circuit packets. This separation is structural:
the binding keys live in the session layer (above the circuit layer); circuit
forwarding keys live in the frozen circuit layer. They are never mixed.

The `SessionBindingRootKey` survives across circuit replacement **at the
same gateway** (R1 / R0); it does NOT survive gateway replacement (R2 — a
different gateway has no record of it, §8.2) and it does NOT survive source
restart (§7.5). Each epoch yields a fresh epoch-specific
`SessionBindingKey(epoch)`; the root key is the stable anchor that allows
the source to derive successive epoch-specific credentials without a fresh
DH exchange per epoch.

## 5. Failure Taxonomy and Detection

### 5.1 Failure modes

| # | Failure | Layer | Detection signal |
|---|---------|-------|------------------|
| F1 | Intermediate relay disappears (transport) | Circuit | Transport timeout on forwarded packet; relay-signalled `NO_ROUTE` from an adjacent relay; keepalive timeout (3 missed) |
| F2 | Intermediate relay restarts (state loss) | Circuit | `UnknownCircuit` / `CircuitTornDown` returned for an in-flight packet; the relay's `RelayForwardingTable` was wiped on restart |
| F3 | Gateway offline (transport) | Circuit + Gateway | Transport timeout; circuit's terminal hop unreachable |
| F4 | Gateway authorization expired | Gateway | Pre-flight `verify_authorization()` fails (N2.4-02); gateway's own `expires_at` check |
| F5 | Gateway authorization revoked | Gateway | Revocation list check; `verify_authorization()` fails |
| F6 | Gateway authorization scope no longer covers the destination | Gateway | `evaluate_scope()` (against authorization) fails for the current destination |
| F7 | Issuer authority governance-revoked | Issuer | Governance revocation propagation; issuer cannot sign new authorizations (existing authorizations remain valid until own expiry — N2.4-02, N2.4-03 §15) |
| F8 | Circuit expired (`now >= expires_at`) | Circuit | `CircuitExpired` from `ActiveCircuit::send_packet` or relay `forward_packet` |
| F9 | Sequence exhaustion (`seq == u32::MAX`) | Circuit | `SequenceExhausted` from the `CircuitSeqState` |
| F10 | Network partition | Network | Cannot verify new authorizations; existing circuits continue until expiry (bounded staleness, N2.4-02) |
| F11 | Source-side restart | Source | Persistent state recovery (N2.4-02 invariant #11); session layer state must persist or be reconstructible |

### 5.2 Detection mechanisms

- **Active keepalive:** the source sends low-overhead keepalive packets at a
  configurable interval (default 1s). If 3 consecutive keepalives go
  unacknowledged (~3s), the circuit is declared degraded (F1/F3).
- **Passive error:** any `TrafficError` returned from `send_packet` or
  observed from the relay (`UnknownCircuit`, `CircuitTornDown`,
  `CircuitExpired`, `TtlExhausted`) is a failure signal.
- **Pre-flight authorization check:** before sending traffic that would
  establish a new session (or at keepalive intervals for an existing session),
  the source re-runs `verify_authorization()` for the gateway. If it fails
  (F4/F5), the session enters proactive recovery **before** the circuit fails
  mid-traffic.
- **Replay-window anomaly:** if the source observes that its own sequence
  numbers are being rejected by relays at a rate inconsistent with normal
  packet loss, this may indicate F2 (relay restart with state loss).

### 5.3 What is NOT a failure

- **Packet loss within the replay window:** normal. The transport session
  layer (or the application) retransmits. No recovery triggered.
- **Gateway authorization about to expire (grace period):** if
  `expires_at - now > CIRCUIT_MAX_LIFETIME_SECS` the gateway can still serve
  the remaining circuit lifetime. Proactive recovery (§7.4) is RECOMMENDED
  but not MANDATORY until the authorization actually expires.
- **Slower-than-expected gateway:** `GatewayObservation` degradation. This
  is a selection concern (N2.4-03 §8), not a recovery trigger.

## 6. Recovery Decision State Machine

A `TransportSession` is always in exactly one recovery state. Recovery is
**make-before-break**: the old circuit MAY continue carrying user traffic while
the new circuit is being established, and the cutover is atomic. This avoids an
unavoidable service interruption and matches the stated recovery objective.

```text
ACTIVE
    The session has a live circuit carrying traffic at the current binding epoch.
    ↓ [F1–F11 detected, OR proactive trigger (§7.4)]
DETECTING
    Confirm the failure is real (not transient packet loss).
    Retry one keepalive with a short timeout (default 500ms).
    ↓ [confirmed failure]
    ↓ [transient — return to ACTIVE]
RECOVERING_PREPARE   (make-before-break — old circuit MAY continue)
    Decide the recovery tier (§8):
      R1 (relay failure, same gateway) — OR
      R2 (gateway failure/expiry/revocation, different gateway)
    The OLD circuit MAY continue carrying user traffic at its current epoch
    while the new circuit is being established.
    The NEW circuit MUST NOT carry user traffic yet — it is being established
    (route discovery, handshake, key derivation, sequence allocator creation).
    Outbound user data continues to flow on the old circuit; no buffering is
    required for in-flight traffic during PREPARE.
    ↓ [new circuit established]
RESUME_CUTOVER   (atomic switch)
    Source sends RESUME(TSID, SessionBindingKey(new_epoch), new_epoch,
                        new_circuit_id) on the new circuit.
    Gateway validates + durably persists the new binding (§9.2, §9.4) BEFORE
    exposing the new epoch.
    ↓ [RESUME confirmed by gateway]
    Binding epoch advances atomically: new circuit becomes current.
    Old circuit STOPS carrying user traffic.
    Old circuit teardown is issued (best-effort, §7.1).
    ↓ [cutover complete]
ACTIVE (new circuit current at the new epoch)
    [R1 success] → outbound TCP preserved (Mode B) / request context (Mode A)
    [R2 success] → outbound TCP NOT preserved for Mode B (RST);
                   Mode A continues with new outbound request
    [budget exhausted] → FAILED
FAILED
    The session is terminated. The application is notified:
      - Mode A: the pending request returns an error; the application may retry.
      - Mode B: the application's TCP connection is reset (RST).
```

### 6.1 State transition invariants

1. **Make-before-break is the recovery model.** In `RECOVERING_PREPARE`, the
   old circuit MAY continue carrying user traffic at its current epoch; the
   new circuit MUST NOT carry user traffic. In `RESUME_CUTOVER`, the binding
   epoch advances atomically on gateway confirmation — at which point the new
   circuit becomes current and the old circuit stops carrying user traffic.
   There is no state in which both circuits carry user traffic simultaneously.
2. **Break-before-make is the fallback for hard failure.** If the old circuit
   is already dead (F2 relay restart, F3 gateway offline, F8 circuit expired),
   `RECOVERING_PREPARE` still runs but the old circuit carries nothing (it is
   gone); outbound user data is buffered (bounded, §13) or back-pressured until
   the new circuit is ready.
3. A session in `RECOVERING_PREPARE` MAY buffer outbound user data (bounded
   buffer, §13) ONLY when the old circuit cannot carry it (hard failure).
   When the old circuit is healthy (proactive recovery, §7.4), no buffering is
   needed — traffic continues on the old circuit.
4. A transition to `FAILED` for Mode B MUST emit a TCP RST to the
   application. It MUST NOT silently drop the connection.
5. A transition to `FAILED` for Mode A MUST return an error to the pending
   request. It MUST NOT hang.
6. `DETECTING` is bounded (single retry, short timeout). It MUST NOT become
   an infinite retry loop.
7. `RESUME_CUTOVER` is bounded (default timeout 5s). If the gateway does
   not confirm the RESUME within the timeout, the session falls back to
   `RECOVERING_PREPARE` (retry) or `FAILED` (budget exhausted). It MUST NOT
   hang indefinitely waiting for cutover confirmation.
8. During `RESUME_CUTOVER`, if the gateway rejects the RESUME (invalid key,
   stale epoch, persistence failure), the binding is unchanged and the
   session returns to `RECOVERING_PREPARE` to retry. The old circuit
   remains current and may continue carrying traffic.

## 7. Recovery Procedure

### 7.1 Step 1 — Teardown the old circuit

```text
if old circuit exists and is not already torn down:
    issue CircuitTeardown (source-signed, N2.3 frozen) to all relays + gateway
    wait for local teardown confirmation (bounded, default 2s)
    (do NOT wait indefinitely — the relays may be unreachable, which is why we're recovering)
```

The teardown is best-effort. If a relay is unreachable (F1/F2), it will not
receive the teardown — but its forwarding state will expire at
`handshake.expiry` (≤ `CIRCUIT_MAX_LIFETIME_SECS` = 3600s) or be wiped on
restart. The source MUST NOT hold the session in `RECOVERING` waiting for an
unreachable relay's teardown acknowledgment.

### 7.2 Step 2 — Discover a replacement route (and gateway, if R2)

```text
if recovery tier R1 (same gateway, relay failure):
    discover a new CommittedRoute to the SAME gateway, avoiding the failed relay
    (the gateway's authorization is still valid; no new gateway selection)

if recovery tier R2 (different gateway):
    run full gateway selection (N2.4-03 §8.2):
      verify CapabilityAuthorization
      → verify validity/revocation
      → evaluate authorization scope
      → evaluate declared policy
      → verify reachability
      → evaluate observations
      → apply preferences/economics
      → select gateway
    then discover a CommittedRoute to the selected gateway
```

### 7.3 Step 3 — Establish a new circuit

```text
new_circuit_id = CSPRNG(32 bytes)        // fresh
new_ephemeral_x25519 = generate()         // fresh
new_handshake = CircuitHandshake {         // fresh, source-signed
    circuit_id: new_circuit_id,
    commitment_hash: new_route.commitment(),
    authorization_root: recompute over new relay authorizations,
    expiry: min(new_route.proposal.expiry, now + CIRCUIT_MAX_LIFETIME_SECS),
    ...
}
new ActiveCircuit {                       // fresh !Clone owner
    circuit_id: new_circuit_id,
    route: new_route,
    keys: fresh per-hop keys (new DH, new HKDF),
    seq_state: fresh CircuitSeqState (next_seq = FIRST_PACKET_SEQ = 1),
    expires_at: new_handshake.expiry,
}
```

**Everything is fresh except the TSID, the binding epoch counter,
and (for R1 Mode B) the `SessionBindingKey` and the gateway's outbound
TCP connection** (see §11). The session's `binding_epoch` is incremented
by 1 (§4.3); the new circuit_id is recorded against the new epoch.
This is the core of the composition rule (§11).

### 7.4 Proactive recovery (before failure)

For F4 (gateway authorization expiring) and F5/F6 (revocation / scope change
detected pre-flight), the source SHOULD initiate recovery **before** the
current circuit fails:

```text
if gateway_authorization.expires_at - now < PROACTIVE_RECOVERY_THRESHOLD:
    (PROACTIVE_RECOVERY_THRESHOLD default = 60s)
    enter RECOVERING_PREPARE
    (old circuit continues carrying traffic at its current epoch)
    establish new circuit to a (possibly different) still-authorized gateway
    ↓
    RESUME_CUTOVER:
        source sends RESUME(new_epoch) on the new circuit
        gateway validates + persists the new binding (§9.2, §9.4)
        ↓ [confirmed]
        binding epoch advances atomically to new_epoch
        new circuit becomes current
        old circuit stops carrying user traffic
        old circuit teardown issued (best-effort)
```

This avoids a hard failure mid-traffic. The old circuit continues to carry
traffic at epoch N during `RECOVERING_PREPARE`; the new circuit carries no
user traffic until `RESUME_CUTOVER` completes and the epoch advances to N+1.
This is the one case where two circuits briefly exist for the same session —
but they have **different `circuit_id`s** and only the old one carries user
traffic during PREPARE. The binding epoch (§4.3) advances atomically on
confirmed RESUME — until then, the gateway's current epoch remains N and it
accepts only the old circuit. This closes the stale-old-circuit race during
make-before-break. There is no circuit multiplexing; the session sends on
exactly one circuit at a time.

### 7.5 Source restart semantics (F11)

A source restart (F11) is a special recovery case. The source's process state
is lost; persistent state is recovered per N2.4-02 invariant #11. The
following rules are normative:

```text
source restart
    ↓
old circuit invalid (the source's ephemeral X25519 secret is gone;
    relays will reject packets — the circuit is effectively dead)
    ↓
old gateway TCP binding is NOT reused
    (the gateway's GatewaySessionTable entry still exists, but the source
    cannot authenticate a RESUME because the SessionBindingRootKey is NOT trusted)
    ↓
SessionBindingRootKey from the prior runtime is NOT trusted / NOT reused
    (it lived in source process memory; a restart cannot prove the key was
    not exfiltrated before the process died. Treating it as trusted would
    make a restarted-source TSID + stale root key a long-lived bearer
    credential — explicitly forbidden, §4.4.2)
    ↓
session enters RECOVERING_PREPARE (the old circuit is gone — this is the
    break-before-make fallback, §6.1 invariant 2: the old circuit carries
    nothing because it is dead; outbound user data is buffered or
    back-pressured until the new circuit is ready)
    ↓
for Mode B: a fresh application connection is required
    (the session layer MUST signal to the application that the prior Mode-B
    connection is gone; new connections succeed via a new circuit)
    ↓
for Mode A: reissue is permitted ONLY if the complete request is still held
    (see §7.5.1 — ShareNet MUST NOT reconstruct an application request
    from TSID + destination alone)
```

**What IS persisted across restart (for bookkeeping/continuity only):**

- `TransportSessionId` (TSID) — for diagnostic and application-layer
  correlation. The TSID by itself authorizes NOTHING.
- `destination` descriptor — the session target.
- `binding_epoch` counter — a monotonic integer; restart does NOT reset it
  (the counter continues from its persisted value, to preserve monotonicity
  across restarts). But because the binding ROOT key is not reused, the
  counter cannot be exercised without a fresh root-key establishment.
- `recovery_budget` — remaining budget (a restart does not grant a fresh
  budget; it inherits the persisted one, to prevent restart-based budget
  reset abuse).

**What is NOT persisted (NOT trusted after restart):**

- `SessionBindingRootKey` and all epoch-specific `SessionBindingKey(epoch)`
  derivations — the prior runtime's root key is discarded. A fresh root key
  MUST be established with the gateway on the new circuit (and then fresh
  epoch-specific keys derived from it).
- The prior circuit's keys, sequence state, replay window — all gone with
  the source's process memory.
- The prior gateway's outbound TCP connection (Mode B) — the gateway MAY
  continue to hold it until its own idle timeout, but the restarted source
  cannot resume it. The gateway's entry will expire and the outbound TCP
  will be closed by the gateway.
- **Pending Mode-A request bodies** — see §7.5.1. ShareNet MUST NOT
  persist or reconstruct application request payloads.

#### 7.5.1 Mode-A request reissue source (normative)

After a source restart, a pending Mode-A request may no longer exist
anywhere to reissue — the application process that issued it may have been
the same process that crashed, and ShareNet's persisted session state
(`TSID + destination + binding_epoch + recovery_budget`) does NOT include
the request body, request envelope, or application replay semantics.

**Normative rule:**

> ShareNet MUST NOT reconstruct an application request from `TSID +
> destination` alone. After a source restart, Mode-A reissue is permitted
> ONLY when the complete request is still held by the application or a
> durable request queue, together with retry/idempotence semantics (§10.4).

If the application does not provide the complete request (with retry
semantics), the session layer MUST return an error to the application for
that request — it MUST NOT invent or reconstruct the request payload from
session metadata. The application is responsible for any durable request
queue it wishes to maintain; ShareNet's session layer coordinates circuit
lifecycle, not application payload durability.

This prevents the session layer from inventing application data and keeps
the boundary between transport-session state and application state clean.

**If persistent binding-key recovery is ever desired** (so that a source
restart could resume a prior gateway TCP binding), that requires a **future
secure-storage / key-management ADR** to define how the `SessionBindingRootKey`
is protected at rest (encrypted storage, hardware-backed key store, OS
keychain, etc.). N2.4-04 does NOT define this; the simpler rule above
(restart discards the root key) is the security boundary.

## 8. Recovery Tiers

### 8.1 Tier R1 — Relay failure, same gateway

**Trigger:** F1, F2 (intermediate relay disappeared or restarted).

**What can be preserved:** the gateway's outbound TCP connection (Mode B) or
outbound request context (Mode A). The destination-side connection is
unaffected — only the ShareNet path changed.

**Procedure:**
1. Teardown old circuit.
2. Discover new route to the **same gateway**, avoiding the failed relay.
3. Establish new circuit (new `circuit_id`, new keys, new sequence).
4. For Mode B: send a `RESUME` control message on the new circuit carrying
   `(TSID, SessionBindingKey, new_epoch)`. The gateway verifies (a) the
   `SessionBindingKey` against the binding context (§4.4.1), (b) the TSID,
   (c) that `new_epoch > current_epoch` (§4.3 epoch monotonicity), and (d)
   that the new `circuit_id` matches the RESUME. On success, the gateway
   atomically advances the binding epoch to `new_epoch` and re-associates
   the new circuit to the existing outbound TCP connection. Traffic on the
   old `circuit_id` is subsequently rejected as stale (lower epoch).
5. For Mode A: the next request on the new circuit carries the TSID and the
   new binding epoch; the gateway verifies the epoch and re-associates to any
   application-layer session state (e.g., cookies, connection pooling) it
   holds for that TSID.

**Application-visible effect:** a latency blip (typically 1–5s for detection
+ recovery). No connection reset. This achieves spec §6.7's "Route switch...
   Circuit state preserved. Application sees a latency blip" **at the session
   layer**, without preserving anything at the (frozen) circuit layer.

### 8.2 Tier R2 — Gateway failure / expiry / revocation, different gateway

**Trigger:** F3, F4, F5, F6 (gateway offline, authorization expired/revoked,
or scope no longer covers the destination).

**What CANNOT be preserved:** the gateway's outbound TCP connection (Mode B).
The origin-side socket lived on Gateway A's kernel. When A is gone, the socket
is gone. **This is the honest limit** (spec §6.7:425–433).

**Procedure:**
1. Teardown old circuit (to Gateway A — best-effort, A may be unreachable).
2. Select a new gateway (full N2.4-03 §8.2 selection).
3. Discover route to new gateway.
4. Establish new circuit to new gateway (new `circuit_id`, new keys).
5. For Mode B: the new gateway has no outbound TCP for this TSID. The session
   **MUST** signal a TCP RST to the application. The application's existing
   connection is lost. **New** connections from the application succeed
   immediately via the new gateway (the session layer accepts the new
   connection and binds it to the new circuit).
6. For Mode A: the pending request is re-issued on the new circuit. **Successful
delivery of a request ≠ confirmed application execution** (§10.4): if the
request was non-idempotent and may have already reached the destination via
Gateway A, the session layer MUST NOT auto-retry (the application must
decide, or an idempotency key must be present — §10.4). **Mode A bundles**
(addressed to a set of acceptable gateways) survive gateway loss at the
**delivery** level — any remaining gateway can complete delivery — but this
does NOT imply **execution idempotence**: a bundle re-issued via Gateway B
after Gateway A may have already executed it can cause duplicate effects
unless the bundle carries an idempotency key or the request is
application-declared idempotent (§10.4).

**Application-visible effect (Mode B):** a TCP RST. This is identical to a
Wi-Fi/cellular handoff dropping a connection. It is **not** transparent TCP
migration. The ADR explicitly forbids claiming otherwise (§16).

**Application-visible effect (Mode A):** for idempotent requests (or
requests carrying an idempotency key, §10.4), a latency blip. For
non-idempotent requests without an idempotency key, an error returned to the
application (which may retry at the application layer). For bundles, no
visible effect at the delivery level — but execution idempotence is the
application's responsibility (§10.4).

### 8.3 Tier R0 — Circuit expiry / sequence exhaustion (same gateway, same route)

**Trigger:** F8, F9 (circuit expired or sequence exhausted).

This is **not** a failure — it is the normal circuit lifecycle. The gateway is
still authorized and reachable; only the circuit object has reached its limit.

**Procedure:** same as R1 (teardown + new circuit to same gateway + rebind).
For Mode B, the `RESUME` mechanism preserves the outbound TCP. This is the
**planned** recovery path — the source SHOULD proactively rotate circuits
before `expires_at` or before sequence exhaustion, using make-before-break
(§7.4).

## 9. Session Rebinding

### 9.1 What is rebound

When a new circuit is established for an existing session:

```text
TransportSession.current_circuit ← new ActiveCircuit
TransportSession.binding_epoch  ← current_epoch + 1   (§4.3 monotonic)
TransportSession.recovery_state ← ACTIVE
```

The TSID is unchanged. The application's view of the session is unchanged
(except where R2 Mode B forces a reset). The binding epoch advances
monotonically; the gateway records the new epoch against the new circuit_id
(§9.2). Traffic on the old circuit_id is subsequently rejected as stale
(lower epoch).

### 9.2 Gateway-side re-association

The gateway maintains:

```text
GatewaySessionTable {
    TSID → {
        outbound_connection:    Option<TcpStream>,      // Mode B
        request_context:        Option<RequestCtx>,      // Mode A
        session_binding_root:    SessionBindingRootKey,   // stable across R1/R0 epochs
        bound_circuit_id:        CircuitId,               // the circuit currently bound
        bound_epoch:             u64,                     // current binding epoch (§4.3)
        binding_key_expiry:      u64,                     // when the root/binding key ceases valid
        last_seen:               u64,
    }
}
```

The gateway stores the **root** key (stable across R1/R0 epoch changes) and
**derives** the epoch-specific `SessionBindingKey(new_epoch)` on demand to
verify each RESUME. It does NOT store every epoch-specific key.

**Epoch-aware acceptance (normative):** for every packet or Mode-A request
arriving for a TSID, the gateway checks:

```text
the arriving circuit_id == bound_circuit_id  AND  bound_epoch is current
```

A packet on a `circuit_id` that does NOT match `bound_circuit_id` is rejected
as stale, **even if it decrypts correctly under that old circuit's keys**.
This is the stale-old-circuit race fix: a delayed packet from C1 (epoch N-1)
arriving after the gateway has rebound to C2 (epoch N) is rejected by the
epoch/circuit_id check, not merely by replay-window or AEAD failure.

**Re-association procedure on a valid RESUME (Mode B) or epoch-tagged request
(Mode A):** the gateway verifies (a) the epoch-specific
`SessionBindingKey(new_epoch)` against the binding context (§4.4.1) by
deriving `KDF(root, context(new_epoch))` and comparing, (b) TSID, (c)
`new_epoch > bound_epoch` (monotonic, §4.3), (d) the RESUME's `circuit_id`
matches the circuit the request arrived on. On success, the gateway **durably
persists** the new binding (§9.4 crash-consistency) BEFORE exposing the new
epoch as current: `bound_circuit_id ← new`, `bound_epoch ← new_epoch`. On any
failure (including persistence failure), the binding is unchanged and the RESUME
is rejected.

- **Mode B R1:** `outbound_connection` is unchanged; `bound_circuit_id` and
  `bound_epoch` advance to the new circuit. Subsequent byte-stream traffic on
  the new circuit is forwarded to the same outbound TCP.
- **Mode B R2:** the gateway has no record of this TSID (different gateway).
  The `RESUME` is rejected. The session layer signals RST.
- **Mode A:** the gateway re-associates the TSID to any application-layer
  session state it holds (cookies, auth tokens — if the user configured the
  gateway to maintain them). A new outbound request is made. The TSID does
  not itself carry application-layer auth; it only lets the gateway correlate
  requests from the same session. The binding epoch check still applies — a
  request on an old circuit_id is rejected as stale.

### 9.3 Session table expiry

The `GatewaySessionTable` entries expire:
- when the last bound circuit expires (no `RESUME` arrived), OR
- when `binding_key_expiry` is reached (the root key ceases valid), OR
- after a gateway-configured idle timeout (default 300s), OR
- when the gateway's own authorization expires/revoked (all entries are
  discarded — the gateway can no longer serve).

The `SessionBindingRootKey` is erased on expiry. A `RESUME` for an expired
TSID is rejected; the session must start fresh (establish a new root key). The
`bound_epoch` counter is also discarded on entry expiry (it is only
meaningful as long as the root key exists to authorize advancement).

### 9.4 Gateway epoch persistence / crash consistency (normative)

The gateway's current binding epoch and bound circuit_id are
security-critical state. Without a persistence discipline, a gateway crash
between accepting a RESUME and persisting the new epoch could allow a stale
lower-epoch circuit to become accepted again after restart — recreating the
stale-circuit race the epoch model was designed to close.

**Normative persistence procedure (the gateway MUST execute this on every
RESUME):**

```text
1. validate RESUME:
     - verify epoch-specific SessionBindingKey(new_epoch) (§4.4.1)
     - verify TSID
     - verify new_epoch > bound_epoch (monotonic, §4.3)
     - verify circuit_id matches the circuit the RESUME arrived on
     ↓ [validation passes]
2. persist atomically:
     - write the new binding (bound_circuit_id ← new,
       bound_epoch ← new_epoch) to durable storage
     ↓ [persistence confirmed]
3. expose the new epoch as current:
     - in-memory GatewaySessionTable entry advances to new_epoch
     - subsequent traffic processing uses the new epoch
     ↓ [new epoch now current]
4. accept new traffic:
     - packets/requests on the new circuit_id at the new epoch are accepted
     - packets/requests on the old circuit_id are rejected as stale
```

**Persistence failure (normative):** if step 2 fails (durability not
confirmed), the RESUME is **rejected**. The old binding remains authoritative
— the gateway continues to accept traffic only at the old epoch/circuit_id.
The session layer (source) sees the rejection and returns to
`RECOVERING_PREPARE` to retry (§6.1 invariant 8). The gateway MUST NOT expose
the new epoch to traffic processing before step 2 completes.

**After gateway restart (normative):** the gateway reconstructs its
`GatewaySessionTable` from durable storage. A stale lower-epoch circuit
MUST NOT become acceptable again — the persisted `bound_epoch` is the
authority, not any in-memory state that may have advanced before the crash.
If the gateway accepted RESUME epoch N+1 but crashed before persisting, on
restart the gateway reverts to epoch N and a delayed packet from the old
circuit at epoch N is accepted (correctly — the binding never advanced). The
new circuit at epoch N+1 is NOT accepted (the RESUME must be retried). This
is the intended behavior: the persisted state is the authority.

This mirrors the same persistence discipline used elsewhere in ShareNet
(N2.4-02 invariant #11 — security-critical authorization state survives
restart) and is consistent with the monotonic-state pattern established for
authority versions and circuit sequence numbers.

## 10. In-Flight Packet Handling

### 10.1 The problem

When a circuit tears down (failure or recovery), packets already sent on it
are in-flight: they are in relay buffers, in transit, or already delivered to
the gateway. The frozen N2.3 layer says: after teardown, `forward_packet`
returns `UnknownCircuit` / `CircuitTornDown` for any further packet. There is
**no graceful drain** mechanism.

### 10.2 N2.4-04 handling

- **Packets already delivered to the gateway** before teardown: they are
  processed normally (the gateway's outbound connection already received
  them). No loss.
- **Packets in transit when the relay disappeared (F1):** lost. The relay
  that disappeared cannot forward them. The adjacent relay's
  `forward_packet` returns an error or silently drops.
- **Packets sent after teardown but before the new circuit is bound:**
  rejected by relays (`UnknownCircuit`). The session layer (in
  `RECOVERING_PREPARE` state, §6) does NOT send user packets on the new
  circuit during this window — traffic continues on the old circuit (if
  alive) or is buffered (bounded, §13) / back-pressured (if the old circuit
  is dead, break-before-make fallback).

### 10.3 Recovery of lost packets

N2.4-04 does **not** define a packet-level retransmission protocol. Lost
in-flight packets are recovered at a higher layer:

- **Mode A (request/response):** the request either completed (response was
  received before failure) or did not. If not, the session layer retries the
  request on the new circuit **only if** the retry conditions of §10.4 are met
  (idempotence declared, idempotency key present, or duplicate-safe semantics).
  For non-idempotent requests without such a key, the application is notified
  and decides.
- **Mode B (byte-stream):** the byte stream is TCP. TCP's own retransmission
  handles in-flight bytes **within the outbound TCP connection** (which
  survives for R1). For R2 (gateway gone), the outbound TCP is gone — the
  bytes are lost and the application's TCP is reset.

### 10.4 Execution vs delivery (Mode A retry safety)

**Successful delivery of a request ≠ confirmed application execution.**
A request may be delivered to Gateway A and executed remotely, while the
response is lost in the subsequent failure. Reissuing it via Gateway B can
cause duplicate effects (e.g., a second payment). Recovery at the session
layer does NOT imply request execution idempotence.

**Automatic retry after recovery MUST require one of:**

1. **Application-declared idempotence** — the application has declared the
   request safe to retry (e.g., a `GET`, a `PUT` with stable content, a
   documented safe method).
2. **Explicit idempotency key** — the request carries an idempotency key
   (e.g., `Idempotency-Key` header) that the destination uses to deduplicate
   across retries.
3. **Protocol-defined duplicate-safe semantics** — a future N2.5+ protocol
   profile defines duplicate-safe request semantics for Mode A.

A request being routed through a different gateway MUST NOT by itself make
it safe to retry. **Mode A bundles** (addressed to a set of acceptable
gateways) survive gateway loss at the **delivery** level — any remaining
gateway can complete delivery — but bundle delivery does NOT imply execution
idempotence. A bundle re-issued via Gateway B after Gateway A may have already
executed it can cause duplicate effects unless the bundle carries an
idempotency key or the request is application-declared idempotent.

This invariant belongs in the session architecture (not deferred to
implementation) because it is the difference between "the network tried
twice" (safe) and "the application executed twice" (unsafe).

### 10.5 No silent loss

A session transition to `FAILED` MUST notify the application. N2.4-04 forbids
silently dropping user data. If recovery fails, the application knows.

## 11. State Migration Rules (Composition)

### 11.1 What MIGRATES across circuit replacement

| State | Migrates? | Condition |
|-------|-----------|-----------|
| `TransportSessionId` (TSID) | Yes | Always — it is the session anchor |
| `binding_epoch` counter | Yes (incremented) | Monotonic; +1 on each RESUME (§4.3) |
| `SessionBindingRootKey` | Yes | R1 / R0 only (same gateway); NOT R2; NOT source restart (§7.5). Stable across epoch changes |
| Epoch-specific `SessionBindingKey(epoch)` | Fresh per epoch | Derived from root key + epoch context; K1, K2, K3 are distinct (§4.4) |
| Gateway's outbound TCP connection (Mode B) | Yes | R1 / R0 only; R2 cannot (§8.2); not source restart |
| Gateway's application-layer session state (Mode A) | Yes | R1 / R0 only, if the gateway maintains it |
| `destination` descriptor | Yes | Always — the session target is unchanged |

### 11.2 What is FRESH on each new circuit (NEVER migrated)

| State | Why fresh |
|-------|-----------|
| `circuit_id` | Frozen N2.3 binds it to a specific route; new route → new `circuit_id` |
| `commitment_hash` | New route → new commitment |
| Per-hop forwarding keys | Derived from `(ephemeral_secret, relay_pub, circuit_id, commitment_hash)` — all four change |
| `CircuitSeqState` | `!Clone`; new circuit owns a fresh allocator (`next_seq = 1`) |
| Replay window | Per-circuit; new circuit = fresh window |
| `expires_at` | New handshake → new expiry |
| `authorization_root` | New relay set → new root |

### 11.3 Composition invariant

> **The only state that crosses a circuit boundary is session-identity state
> (TSID + `SessionBindingRootKey` +, for R1, the gateway's outbound connection).
> All cryptographic and sequence state is circuit-scoped and dies with the
> circuit. The root key survives same-gateway circuit replacement but each
> epoch yields a fresh epoch-specific key derivation.**

This is the formal rule that prevents N2.4-04 from accidentally turning
into frozen-semantics violation: because no cryptographic state migrates,
there is no nonce reuse, no sequence wraparound, no replay-window
contamination, no commitment-hash inconsistency. The frozen invariants hold
because each circuit is a clean, independent cryptographic instance.

## 12. Circuit Invalidity Conditions

A circuit is **invalid** (cannot carry new traffic) when any of:

1. `now >= expires_at` — circuit expired (F8).
2. `seq == u32::MAX` and `exhausted == true` — sequence exhausted (F9).
3. A `CircuitTeardown` was issued and processed — circuit torn down.
4. A relay on the route has restarted and lost its `RelayForwardingState`
   (F2) — the relay returns `UnknownCircuit`.
5. A relay on the route is unreachable (F1) — packets cannot traverse.
6. The gateway's authorization has expired or been revoked (F4/F5) —
   **but note**: per N2.4-03 §15, existing circuits continue until their own
   expiry. So the **circuit** is not immediately invalid; but the session
   layer SHOULD proactively recover (§7.4) because no new circuits can be
   established to that gateway.

An invalid circuit MUST NOT be used to send new traffic. The session layer
MUST transition to `RECOVERING` (or `FAILED` if budget is exhausted) upon
detecting invalidity.

## 13. Recovery Budget and Anti-Oscillation

### 13.1 Recovery budget

Each `TransportSession` has a bounded recovery budget:

```text
DEFAULT_RECOVERY_BUDGET = 3   // attempts
MAX_RECOVERY_BUDGET     = 5   // upper bound (configurable down, never up)
```

Each transition `ACTIVE → DETECTING → RECOVERING → (ACTIVE | FAILED)` that
returns to `ACTIVE` does NOT replenish the budget — but a sustained `ACTIVE`
period (default 60s without a new failure) DOES reset the budget to its
default. This prevents a permanently-flapping session from consuming recovery
attempts forever, while allowing a session that stabilizes to recover its
budget.

When the budget is exhausted, the session transitions to `FAILED`:

- Mode A: return an error to the pending request.
- Mode B: emit TCP RST.

### 13.2 Anti-oscillation

To prevent a session from oscillating between `ACTIVE` and `RECOVERING` (which
would amplify load across relays and gateways):

- **Recovery cooldown:** after a successful recovery, the session MUST remain
  in `ACTIVE` for at least `RECOVERY_COOLDOWN` (default 10s) before another
  recovery can be initiated. Failures during cooldown are buffered (not
  immediately recovered).
- **Backoff:** each successive recovery attempt within a budget window uses
  exponential backoff (base 1s, factor 2, cap 30s) before re-entering
  `RECOVERING`.
- **No concurrent recoveries for the same session:** a session has exactly
  one recovery in flight at a time. (Multiple sessions may recover
  concurrently — that is expected and allowed.)
- **Circuit establishment rate limit:** the source MUST NOT establish
  circuits faster than `MAX_CIRCUIT_ESTABLISHMENT_RATE` (default 10/min per
  gateway) to avoid hammering a recovering gateway or relay set.

### 13.3 Amplification bound

The recovery architecture MUST NOT become a DoS amplifier. If a relay is
flapping (up/down every few seconds), the source's recovery attempts are
bounded by the budget and backoff. After budget exhaustion, the session
fails — it does not retry indefinitely.

## 14. ShareNetOverlayDestination Classification (N2.4-03 dependency)

N2.4-03 §10.1.1 deferred the concrete classification mechanism for
`ShareNetOverlayDestination` to N2.4-04. This section fulfills that
dependency.

### 14.1 Classification mechanism

A gateway classifies a destination as a `ShareNetOverlayDestination` by
checking it against the gateway's **local authenticated peer table** — the set
of ShareNet transport endpoints the gateway has authenticated or currently
maintains sessions with:

```text
ShareNetOverlayDestination check (gateway-local):
    for each authenticated ShareNet transport endpoint E in the gateway's peer table:
        if destination.address matches E.address
           AND destination.transport matches E.transport:
            return IS_OVERLAY
    return IS_NOT_OVERLAY   (fail-open: unknown → not overlay)
```

- **Local, not global:** the gateway checks its own peer table. There is no
  global registry of all ShareNet node IPs. A destination the gateway has
  never seen as a ShareNet peer is classified `IS_NOT_OVERLAY`.
- **Authenticated:** the peer table contains only endpoints that have
  authenticated via the ShareNet transport handshake (Ed25519 → NodeId
  binding, per spec/02-identity.md). An unauthenticated endpoint claiming to
  be a ShareNet node is NOT in the table.
- **Transport-aware:** the classification matches on `(transport, address)`,
  not address alone — the same IP on a different transport (e.g., a ShareNet
  relay's public HTTPS port vs. its ShareNet overlay port) may be classified
  differently.
- **Fail-open for unknown, fail-closed for known:** if the destination
  matches an authenticated peer, it IS overlay → rejected (fail-closed). If it
  matches nothing in the table, it is NOT overlay → allowed (subject to the
  canonical egress deny set and gateway policy).

### 14.2 Completeness and the honest gap

This classification is **best-effort**: a ShareNet node the gateway has never
authenticated (e.g., a relay that joined after the gateway's last peer-table
sync) would not be classified as overlay. This is an accepted limitation. The
canonical egress deny set (N2.4-03 §10.1) still protects against the SSRF
ranges regardless; the overlay classification adds protection against
gateway-to-gateway loops for **known** overlay endpoints.

A future profile (N2.4-07+, if a `PacketProfile::V3` is introduced) MAY add an
in-band overlay-marker field to make the classification authoritative rather
than best-effort. N2.4-04 does not require it.

### 14.3 Gateway-to-gateway loop prevention

With §14.1, gateway-to-gateway loops are prevented as follows: when Gateway A
attempts to exit to a destination, it checks whether that destination is a
`ShareNetOverlayDestination` (i.e., another ShareNet node's transport
endpoint). If it is, the egress is rejected. This prevents Gateway A from
forwarding traffic to Gateway B over the overlay, which would create a loop
(circuit-in-circuit) and enable exfiltration and amplification.

## 15. Interaction with N2.4-03 Gateway Lifecycle

### 15.1 Gateway authorization expiry (F4)

Per N2.4-03 §15: when a gateway authorization expires, the gateway cannot
accept **new** circuits, but **existing** circuits continue until their own
`expires_at` (bounded staleness).

N2.4-04 adds the session-layer behavior:
- The source's pre-flight check (§5.2) detects the expiry before establishing
  new circuits to that gateway.
- Existing sessions on existing circuits continue normally until the circuit
  expires — then R0 recovery (§8.3) selects a **different** gateway (the
  expired gateway can no longer serve).
- Proactive recovery (§7.4) SHOULD rotate the session to a new gateway
  **before** the current circuit expires, to avoid a hard failure.

### 15.2 Gateway authorization revocation (F5)

Same as expiry, but urgent. The source's revocation-list check (run at
keepalive intervals) detects revocation. The session enters
`RECOVERING_PREPARE` immediately. The existing circuit (if still within its
`expires_at`) continues to carry traffic until the new circuit is ready
(make-before-break, §6.1 invariant 1), because N2.4-03 §15 preserves existing
circuits. Then the session switches to the new circuit on a new gateway via
`RESUME_CUTOVER`.

### 15.3 Issuer authority governance-revoked (F7)

Per N2.4-02 and N2.4-03 §15 (corrected in revision 3): governance revocation
prevents the issuer from issuing **new** authorizations; **existing**
authorizations remain valid until their own `validity_end` unless separately
subject-revoked.

N2.4-04 session-layer behavior:
- Existing circuits to gateways authorized by the revoked issuer continue
  until their own `expires_at`.
- No new circuits can be established to those gateways (the issuer cannot
  re-authorize; when the existing authorizations expire, the gateway cannot
  renew).
- The session layer proactively migrates to gateways authorized by a
  **different** issuer before the existing authorizations expire.

**If N2.4-04 (or a later ADR) wants an emergency "kill all active
authorizations from issuer I" mechanism** — that is a **new explicit protocol
decision**, not an accidental consequence of issuer revocation. It is NOT
defined in N2.4-04. It would require either (a) governance signing a
subject-level revocation for each affected gateway, or (b) a new protocol
mechanism (e.g., a governance-signed "authority-class revocation" that
invalidates all authorizations from a specific issuer immediately). Option (b)
is deferred to a future ADR if required.

## 16. What N2.4-04 MUST NOT Do (Frozen Semantics Boundary)

N2.4-04 MUST NOT:

1. **Modify N2.3 V1 or V2 packet format.** The 5-field / 8-field CBOR, the
   AAD construction, the nonce derivation, and the golden wire vectors are
   immutable (protocol-freeze.md).
2. **Re-use a `circuit_id` across different routes.** The frozen
   `commitment_hash` binding makes this a semantic violation. Each new route
   = new `circuit_id`.
3. **Migrate per-hop forwarding keys across circuits.** Keys are derived from
   `(ephemeral_secret, relay_pub, circuit_id, commitment_hash)`; migrating
   them would require migrating `circuit_id` (forbidden by #2) or reusing
   nonces (catastrophic for ChaCha20-Poly1305).
4. **Migrate `CircuitSeqState`.** It is `!Clone`. Two senders on the same
   circuit would emit duplicate `seq` under the same nonce — forbidden.
5. **Migrate replay windows.** A replay window is per-circuit; cross-circuit
   replay contamination is undefined and forbidden.
6. **Introduce in-band session resumption tokens in the packet.** Any such
   field would require `PacketProfile::V3` (deferred to N2.4-07). The TSID
   rides in the gateway application protocol, not the circuit packet.
7. **Claim transparent TCP migration across gateway failure (Mode B).** The
   origin-side socket lives on the gateway; when the gateway dies, the socket
   dies. Applications see a RST. N2.4-04 forbids UI, documentation, or
   protocol claims that imply otherwise (spec §6.7:433).
8. **Modify the replay-window ordering** (check-before-AEAD, commit-after-AEAD,
   O(WINDOW) update, `ProfileMismatch` before AEAD). All frozen.
9. **Modify `CircuitTeardown` semantics.** Teardown is source-signed and
   removes forwarding state immediately. N2.4-04 uses it as-is.
10. **Bypass the canonical egress deny set** (`CanonicalShareNetEgressDenySet`)
    during recovery. A replacement gateway's egress is subject to the same
    destination validation (N2.4-03 §5.3) as the original.
11. **Establish a recovery circuit to an unauthorized gateway.** The full
    N2.4-03 §8.2 selection ordering applies to every recovery circuit.
12. **Reuse a `SessionBindingRootKey` after source restart.** A restarted
    source MUST NOT attempt to RESUME with a root key (or any epoch-specific
    derivation) from the prior runtime. A fresh root key MUST be established
    with the gateway on the new circuit (§7.5). This prevents a
    restarted-source TSID + stale root key from becoming a long-lived
    bearer credential.
13. **Treat the `SessionBindingRootKey` or epoch-specific keys as general
    bearer credentials.** The epoch-specific key is bound to
    `(gateway_node_id, tsid, binding_epoch, expiry)` (§4.4.1) and authorizes
    only resumption of THIS session at THIS gateway for the circuit in the
    RESUME at the claimed epoch. The root key MUST NEVER be presented in a
    RESUME — only epoch-specific derivations are. Neither authorizes anything
    else.
14. **Use timestamps or random nonces as the binding ordering mechanism.**
    The binding epoch is a monotonic persistent integer (§4.3), consistent
    with ShareNet's established pattern (N2.4-02 authority versions, N2.3
    sequence numbers). Timestamps and nonces are explicitly rejected as
    ordering mechanisms for session binding.
15. **Auto-retry a non-idempotent Mode A request after recovery without an
    idempotency key.** Successful delivery ≠ confirmed execution (§10.4).
    A request being routed through a different gateway does NOT make it
    safe to retry.
16. **Carry user traffic on the new circuit during `RECOVERING_PREPARE`.**
    The new circuit MUST NOT carry user traffic until `RESUME_CUTOVER`
    completes and the gateway confirms the new binding (§6.1 invariant 1).
    The old circuit MAY continue carrying traffic at its current epoch during
    PREPARE; the new circuit is established but inactive for user traffic.
17. **Expose a new binding epoch to traffic processing before durable
    persistence.** The gateway MUST persist `(bound_circuit_id, bound_epoch)`
    to durable storage BEFORE exposing the new epoch as current (§9.4).
    Persistence failure = RESUME rejected, old binding authoritative.

## 17. Does N2.4-04 Need PacketProfile::V3?

### 17.1 Analysis

The recovery architecture defined here operates **entirely above** the frozen
circuit layer:
- Detection uses transport timeouts and frozen `TrafficError` variants.
- Recovery uses frozen `CircuitTeardown` + frozen circuit establishment.
- Session rebinding uses the gateway application protocol (TSID), not the
  packet.
- No cryptographic state migrates across circuits.

Therefore **N2.4-04 does NOT require `PacketProfile::V3`** for the core
recovery mechanism. V1 and V2 circuits are replaced via teardown +
re-establishment; the session layer provides continuity.

### 17.2 When V3 would be needed

A future `PacketProfile::V3` would be needed only if the architecture wanted:
- In-band session-resumption tokens in the packet (to avoid the gateway
  application protocol carrying the TSID).
- In-band circuit-migration signaling (to avoid teardown + re-establishment
  for relay-only failure).
- Per-session (rather than per-circuit) replay windows.

These are **optimizations**, not requirements. N2.4-04 deliberately does NOT
introduce them, because:
- They would modify frozen packet semantics (forbidden).
- They would require new golden vectors and a new ADR (N2.4-07).
- The session-layer approach achieves the same continuity without packet
  changes.

### 17.3 Decision

`PacketProfile::V3` is **deferred to N2.4-07** (charter §6) as a conditional
future milestone. N2.4-04 does not block on it and does not introduce it.

## 18. Security Invariants

1. **N2.3 packet semantics are immutable.** N2.4-04 does not modify V1/V2
   wire format, AAD, nonce, replay ordering, or golden vectors.
2. **No `circuit_id` reuse across routes.** A new route always yields a new
   `circuit_id`. The frozen `commitment_hash` binding is preserved.
3. **No cryptographic state migration.** Keys, sequence state, replay windows,
   and `authorization_root` are circuit-scoped and die with the circuit. Only
   session-identity state (TSID, and for R1 the gateway binding key + outbound
   connection) migrates.
4. **No nonce reuse.** Because keys and `circuit_id` are fresh on each new
   circuit, the AEAD nonce space is injective per-circuit. The frozen
   no-wraparound invariant is preserved.
5. **Recovery does not bypass authorization.** Every recovery circuit goes
   through the full N2.4-03 §8.2 selection ordering. An unauthorized gateway
   cannot become a recovery target.
6. **Recovery does not bypass the canonical egress deny set.** A replacement
   gateway's egress is subject to `CanonicalShareNetEgressDenySet`
   unconditionally (N2.4-03 §5.3.1, §10.1).
7. **No transparent TCP migration across gateway failure.** Mode B gateway
   failure yields a TCP RST. The architecture does not claim otherwise.
8. **Recovery is bounded.** A session has a finite recovery budget
   (default 3, max 5) and backoff. It cannot retry forever or amplify load.
9. **No silent data loss.** A transition to `FAILED` notifies the application
   (error for Mode A, RST for Mode B). Buffered data is either delivered (on
   success) or reported lost (on failure).
10. **Teardown is best-effort, not blocking.** Recovery does not stall waiting
    for an unreachable relay's teardown acknowledgment. The relay's state
    expires at `handshake.expiry` or is wiped on restart.
11. **Issuer revocation does not kill existing circuits.** Consistent with
    N2.4-02 and N2.4-03 §15 (revision 3): existing authorizations remain
    valid until their own `validity_end`. An emergency kill mechanism, if
    ever needed, is a separate explicit protocol decision.
12. **`ShareNetOverlayDestination` classification is best-effort, not
    authoritative.** It uses the gateway's local authenticated peer table.
    Unknown destinations are classified `IS_NOT_OVERLAY` (fail-open). The
    canonical egress deny set remains enforced regardless.
13. **Two circuits for one session exist only during make-before-break
    PREPARE.** Proactive recovery (§7.4) may briefly hold an old and a new
    circuit during `RECOVERING_PREPARE`. They have different `circuit_id`s;
    the old circuit carries user traffic at its current epoch; the new circuit
    carries NO user traffic until `RESUME_CUTOVER` completes and the epoch
    advances atomically. There is no state in which both circuits carry user
    traffic simultaneously, and no circuit multiplexing.
14. **Recovery state is persistent across source restart (F11).** The
    `TransportSession` state (TSID, destination, binding_epoch counter,
    recovery_budget) is persisted per N2.4-02 invariant #11. On source
    restart, the session layer reconstructs sessions and enters
    `RECOVERING_PREPARE` (the old circuit is gone — break-before-make
    fallback, §6.1 invariant 2; the old root key is NOT trusted, §7.5).
    In-flight data is lost (consistent with §10).
15. **Recovery does not weaken the composition rule.** The effective
    destination permission on a recovery circuit is still
    `auth_scope ∩ declared_policy ∩ canonical_egress_safety` (N2.4-03 §17
    invariant 18). Recovery introduces no exception to this intersection.
16. **Session binding has a monotonic epoch.** A `SessionBindingEpoch`
    (TSID + epoch:u64 + circuit_id, §4.3) orders circuit replacements.
    First binding = epoch 1; each RESUME requires new_epoch > current;
    same epoch + same circuit_id = idempotent no-op; same epoch + different
    circuit_id = reject; lower epoch = reject. The gateway accepts traffic
    only from the circuit_id at the current epoch. This closes the
    stale-old-circuit race during make-before-break. The epoch is a monotonic
    persistent integer, NOT timestamps or nonces. The cutover is atomic
    (`RECOVERING_PREPARE` → `RESUME_CUTOVER` → `ACTIVE`, §6).
17. **Source restart terminates all resumable Mode-B gateway bindings.**
    The old circuit is invalid; the old gateway TCP binding is NOT reused;
    the prior runtime's `SessionBindingRootKey` (and all epoch-specific
    derivations) is NOT trusted or reused. A fresh Mode-B application
    connection is required. TSID may be persisted for
    bookkeeping/diagnostics, but it MUST NOT by itself authorize resumption
    of an old gateway TCP connection. Mode-A reissue after restart requires
    the complete request to be held by the application or a durable request
    queue — ShareNet MUST NOT reconstruct application payloads from
    TSID + destination (§7.5.1). Persistent binding-key recovery, if ever
    desired, is deferred to a future secure-storage / key-management ADR
    (§7.5).
18. **Delivery ≠ execution (Mode A retry safety).** Successful delivery of
    a Mode A request does not imply confirmed application execution. Automatic
    retry after recovery MUST require application-declared idempotence, an
    explicit idempotency key, or protocol-defined duplicate-safe semantics.
    A request being routed through a different gateway MUST NOT by itself make
    it safe to retry. Mode A bundles survive gateway loss at the delivery
    level only; execution idempotence is the application's responsibility
    (§10.4).
19. **Gateway epoch binding is crash-consistent.** The gateway MUST durably
    persist `(bound_circuit_id, bound_epoch)` BEFORE exposing the new epoch
    to traffic processing (§9.4). Persistence failure = RESUME rejected,
    old binding remains authoritative. After gateway restart, the persisted
    `bound_epoch` is the authority; a stale lower-epoch circuit MUST NOT
    become acceptable again. This mirrors N2.4-02 invariant #11
    (security-critical authorization state survives restart) and is
    consistent with the monotonic-state pattern for authority versions and
    circuit sequence numbers. The epoch-specific `SessionBindingKey(epoch)`
    is derived from the root key + epoch context (§4.4), so each epoch has
    a distinct RESUME credential (K1, K2, K3); the root key survives
    same-gateway circuit replacement but never appears in a RESUME message.

## 19. Conformance Requirements

(To be defined when implementation begins. Will include:)
- Transport session state encoding (TSID, session state, binding_epoch,
  recovery budget) — binding_epoch counter persisted but root key NOT
- Gateway session table encoding (TSID → outbound connection / request

  binding_key_expiry)

  + epoch-specific SessionBindingKey(new_epoch) + new_epoch) — gateway
  application protocol, NOT circuit packet
- `SessionBindingRootKey` + epoch-specific `SessionBindingKey(epoch)` derivation
  conformance (§4.4: KDF(root, context(epoch)) covering domain_separator +
  gateway_node_id + tsid + binding_epoch + expiry; root key never in RESUME)
- Epoch monotonicity + stale-rejection conformance (§4.3, §9.2: lower epoch
  / mismatched circuit_id rejected as stale even if AEAD would pass)
- Gateway epoch crash-consistency conformance (§9.4: validate → persist →
  expose → accept; persistence failure = RESUME rejected; after restart
  persisted bound_epoch is authority)
- State machine conformance (§6: ACTIVE / DETECTING / RECOVERING_PREPARE /
  RESUME_CUTOVER / FAILED; make-before-break invariants §6.1)
- Source-restart binding-discard conformance (§7.5: root key NOT reused
  after restart; fresh root key establishment required; Mode-A reissue
  requires complete request held by application, §7.5.1)
- Mode A retry-safety conformance (§10.4: auto-retry only with idempotence
  declaration, idempotency key, or duplicate-safe semantics)
- Recovery budget conformance (§13: default 3, max 5, backoff, cooldown)
- ShareNetOverlayDestination classification conformance (§14: local peer
  table check, fail-open for unknown)
- Make-before-break conformance (§7.4, §6.1: at most 2 circuits per session
  during RECOVERING_PREPARE; new circuit carries NO user traffic until
  RESUME_CUTOVER; epoch advances atomically)
- Failure detection conformance (§5: keepalive interval, missed-keepalive
  threshold, pre-flight authorization check)
- Honest-reset conformance (§16: Mode B gateway failure → RST; no claim of
  transparent TCP migration)

## 21. Implementation Boundaries

N2.4-04 defines the **architecture**. Implementation will produce:

- Transport session layer (client-side `TransportSession` state machine)
- Gateway session table (TSID → outbound connection / request context)
- `RESUME` control message handler (gateway application protocol)
- Recovery orchestration (detection → decision → teardown → re-establish →
  rebind)
- `ShareNetOverlayDestination` classification (gateway local peer table check)
- Make-before-break proactive recovery controller
- Recovery budget + backoff + cooldown enforcement

Implementation is **blocked** until:
- N2.4-04 is approved
- N2.4-05 (Transport Abstraction) is at least proposed (the session layer
  depends on the transport abstraction boundary)
- Conformance vectors are defined

**N2.3 frozen implementation MUST NOT be modified.**

Implementation MUST NOT:
- Add session-state fields to V1/V2 circuit packets.
- Reuse a `circuit_id` across routes.
- Migrate `CircuitSeqState`, forwarding keys, or replay windows.
- Bypass the canonical egress deny set during recovery.
- Claim transparent TCP migration across gateway failure.
- Reuse a `SessionBindingRootKey` (or any epoch-specific key) after source
  restart (§7.5).
- Present the `SessionBindingRootKey` in a RESUME message — only
  epoch-specific derivations are (§4.4.2).
- Treat binding keys as general bearer credentials (§4.4.2).
- Use timestamps or nonces as the binding ordering mechanism (use the
  monotonic epoch, §4.3).
- Auto-retry a non-idempotent Mode A request after recovery without an
  idempotency key (§10.4).
- Carry user traffic on the new circuit during `RECOVERING_PREPARE` (§6.1
  invariant 1).
- Expose a new binding epoch to traffic processing before durable persistence
  (§9.4).
- Reconstruct an application request payload from `TSID + destination`
  after source restart (§7.5.1).
