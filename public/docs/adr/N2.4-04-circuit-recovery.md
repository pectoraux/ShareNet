# N2.4-04 — Circuit Recovery Architecture

**Status:** PROPOSED — awaiting review

**Parent:** N2.4-03 Gateway Architecture (approved, `18c11c2`)

**Baseline:** N2.3 frozen @ `425eccb` (tag: `v2.3.0-protocol`)

**Approved dependencies:** N2.4-00 Charter, N2.4-01 Threat Model, N2.4-02 Capability System, N2.4-03 Gateway Architecture

---

## 1. Problem Statement

N2.3 provides circuits: authenticated, encrypted, replay-protected forwarding
from source to gateway over a cryptographically bound `CommittedRoute`. N2.4-03
provides the gateway architecture and lifecycle (authorization, policy,
selection, exit, revocation). Neither defines what happens when a live circuit's
underpinnings fail.

A ShareNet deployment is a **delay-tolerant distributed network over
participating devices**. Devices disappear: laptops close, phones lose signal,
relays restart, gateways expire or are revoked. A circuit that worked at
establishment time may, minutes later, sit over a dead relay or an unauthorized
gateway. The system must recover — and it must do so without lying about what
"recovery" can preserve.

N2.4-04 defines the **recovery architecture**: how failure is detected, how
recovery is decided, what is re-established, what state may be migrated, and
the hard limits on what can survive.

### The non-negotiable constraint

> **N2.4-04 MUST NOT modify the frozen N2.3 packet semantics.**

The N2.3 V1 protocol (5-field CBOR, raw AAD, `circuit_id[0..8] ‖ seq` nonce)
and the V2 protocol (8-field CBOR, domain-separated AAD, direction-XOR nonce)
are frozen at `425eccb` / `0efaaac`. The golden wire vectors are immutable.
The replay-window ordering (check-before-AEAD, commit-after-AEAD), the
`!Clone` sequence allocator, the `commitment_hash` route binding, the per-hop
TTL authentication, and the `CircuitSeqState` no-wraparound/no-exhaustion
invariants are all immutable. N2.4-04 operates **around** this frozen layer,
never **within** it. Any future in-band migration primitive that requires
packet-format changes is a `PacketProfile::V3` concern — explicitly deferred to
N2.4-07 (charter §6), not this ADR.

---

## 2. The Central Tension

The frozen N2.3 circuit layer **binds a circuit to exactly one `CommittedRoute`**
via `handshake.commitment_hash == route.commitment()`. The commitment covers the
proposal, all validated hops (node records + link evidence + roles), and the
sorted route acceptances. Change one relay → different commitment → different
circuit. The circuit's per-hop keys are derived from `(ephemeral_x25519_secret,
relay_pub, circuit_id, commitment_hash)` — so a different route yields different
keys. The sequence allocator is `!Clone` and owned by the single `ActiveCircuit`
instance. There is **no** frozen primitive for changing a route, a relay, or a
key under an existing `circuit_id`.

Simultaneously, spec §6.7 (02-PROTOCOL-SPEC.md:401–433) aspires to:

> "`CircuitId` is independent of both route and gateway."
> "Route switch... Circuit state preserved. Application sees a latency blip."

These two statements are in tension. The frozen implementation **does not**
make `circuit_id` independent of route — it binds them cryptographically. A
literal reading of spec §6.7 as a frozen circuit-layer property would require
modifying N2.3, which is forbidden.

### Resolution

N2.4-04 resolves the tension by **reframing the layer at which continuity
lives**:

- At the **circuit layer** (frozen N2.3): a circuit is bound to one route and
  is **not** migratable. Recovery = teardown + re-establishment under a new
  `circuit_id`.
- At the **transport session layer** (N2.4-04, new): a *session* is bound to
  neither a circuit nor a route. The session survives circuit replacement.
  The application sees continuity — or, where that is impossible (gateway
  migration with a live TCP socket), an honest reset.

This makes spec §6.7's aspiration achievable **as a session-layer property**
without modifying the frozen circuit layer. "Circuit state preserved" is
reframed as "session state preserved; underlying circuit replaced transparently
where possible, honestly-reset where not."

## 3. Architecture Overview

```
Application layer (TCP / HTTP / custom)
    ↑  sees: session continuity OR honest reset
Transport Session Layer  (N2.4-04 — NEW)
    TransportSession { session_id, current_circuit, mode, recovery_state }
    ↑  maps application sessions to circuits; survives circuit replacement
Circuit layer  (N2.3 FROZEN — V1 / V2, NOT modified by N2.4-04)
    ActiveCircuit { circuit_id, route, keys, seq_state, expires_at }  ← !Clone
    ↑  one circuit = one CommittedRoute = one commitment_hash
    ↑  recovery = teardown + re-establish (NEW circuit_id)
Route layer  (N2.1 / N2.2)
    CommittedRoute { proposal, validated_hops, commitment, acceptances }
```

**Key architectural principle:** circuits are **replaceable units**. The
session layer treats a circuit the way a TCP stack treats a network interface
card — it can be unplugged and replaced; the session above survives (or fails
honestly) depending on what the new circuit can reach.

## 4. Transport Session Layer

### 4.1 TransportSession

```text
TransportSession {
    session_id:           TransportSessionId,   // see §4.2
    mode:                 InternetMode,          // Mode A | Mode B (§12 of N2.4-03)
    current_circuit:      Option<ActiveCircuit>, // the live circuit, or None during recovery
    destination:          DestinationDescriptor, // the application's target
    gateway_session_key:  Option<SessionBindingKey>, // gateway-side re-association (§4.3)
    recovery_state:      RecoveryState,         // §6
    created_at:           u64,
    recovery_budget:      u8,                    // §13
}
```

A `TransportSession` is a **client-side** abstraction. It is NOT a protocol
message type and is NOT sent over the wire as a single object. It is local
state that coordinates circuit lifecycle with application continuity.

### 4.2 TransportSessionId (TSID)

The `TransportSessionId` (TSID) is a **session identifier carried in the gateway
application protocol**, NOT in the circuit packet wire format. This is the
critical design choice that keeps N2.4-04 out of the frozen packet layer.

- **Mode A (application fetch):** the TSID is an attribute of the Mode A
  request (e.g., an application-layer header in the gateway application
  protocol). The gateway maps `TSID → outbound request context`.
- **Mode B (byte-stream proxy):** the TSID is carried in the CONNECT
  request metadata when the tunnel is first established. The gateway maps
  `TSID → outbound TCP connection`.

The TSID is:
- **Opaque to relays.** Relays forward encrypted circuit packets; they never
  see or interpret the TSID.
- **Not part of the circuit packet.** No V1/V2 field, no AAD binding, no
  nonce contribution. The frozen packet format is untouched.
- **Gateway-interpreted.** Only the source and the gateway understand the TSID.
- **Random and unguessable** (≥128 bits from the OS CSPRNG), to prevent
  session-hijacking by guessing.

### 4.3 SessionBindingKey

For **Mode B** relay-only recovery (§8.1), the gateway must re-associate a
new circuit's traffic with an existing outbound TCP connection. The gateway
holds a `SessionBindingKey` — a short-lived secret shared between the source
and gateway (established during the first circuit's Mode B CONNECT handshake)
that authenticates the re-binding request on the new circuit:

```text
new circuit established (new circuit_id)
    ↓
source sends Mode B RESUME on new circuit, carrying (TSID, SessionBindingKey)
    ↓
gateway verifies SessionBindingKey matches its record for TSID
    ↓
gateway re-associates new circuit → existing outbound TCP
```

The `SessionBindingKey` is distinct from circuit keys (it is not an AEAD key
for packet forwarding; it authenticates the resumption control message only).
It survives across circuit replacement; it does NOT survive gateway
replacement (a different gateway has no record of it).

## 5. Failure Taxonomy and Detection

### 5.1 Failure modes

| # | Failure | Layer | Detection signal |
|---|---------|-------|------------------|
| F1 | Intermediate relay disappears (transport) | Circuit | Transport timeout on forwarded packet; relay-signalled `NO_ROUTE` from an adjacent relay; keepalive timeout (3 missed) |
| F2 | Intermediate relay restarts (state loss) | Circuit | `UnknownCircuit` / `CircuitTornDown` returned for an in-flight packet; the relay's `RelayForwardingTable` was wiped on restart |
| F3 | Gateway offline (transport) | Circuit + Gateway | Transport timeout; circuit's terminal hop unreachable |
| F4 | Gateway authorization expired | Gateway | Pre-flight `verify_authorization()` fails (N2.4-02); gateway's own `expires_at` check |
| F5 | Gateway authorization revoked | Gateway | Revocation list check; `verify_authorization()` fails |
| F6 | Gateway authorization scope no longer covers the destination | Gateway | `evaluate_scope()` (against authorization) fails for the current destination |
| F7 | Issuer authority governance-revoked | Issuer | Governance revocation propagation; issuer cannot sign new authorizations (existing authorizations remain valid until own expiry — N2.4-02, N2.4-03 §15) |
| F8 | Circuit expired (`now >= expires_at`) | Circuit | `CircuitExpired` from `ActiveCircuit::send_packet` or relay `forward_packet` |
| F9 | Sequence exhaustion (`seq == u32::MAX`) | Circuit | `SequenceExhausted` from the `CircuitSeqState` |
| F10 | Network partition | Network | Cannot verify new authorizations; existing circuits continue until expiry (bounded staleness, N2.4-02) |
| F11 | Source-side restart | Source | Persistent state recovery (N2.4-02 invariant #11); session layer state must persist or be reconstructible |

### 5.2 Detection mechanisms

- **Active keepalive:** the source sends low-overhead keepalive packets at a
  configurable interval (default 1s). If 3 consecutive keepalives go
  unacknowledged (~3s), the circuit is declared degraded (F1/F3).
- **Passive error:** any `TrafficError` returned from `send_packet` or
  observed from the relay (`UnknownCircuit`, `CircuitTornDown`,
  `CircuitExpired`, `TtlExhausted`) is a failure signal.
- **Pre-flight authorization check:** before sending traffic that would
  establish a new session (or at keepalive intervals for an existing session),
  the source re-runs `verify_authorization()` for the gateway. If it fails
  (F4/F5), the session enters proactive recovery **before** the circuit fails
  mid-traffic.
- **Replay-window anomaly:** if the source observes that its own sequence
  numbers are being rejected by relays at a rate inconsistent with normal
  packet loss, this may indicate F2 (relay restart with state loss).

### 5.3 What is NOT a failure

- **Packet loss within the replay window:** normal. The transport session
  layer (or the application) retransmits. No recovery triggered.
- **Gateway authorization about to expire (grace period):** if
  `expires_at - now > CIRCUIT_MAX_LIFETIME_SECS` the gateway can still serve
  the remaining circuit lifetime. Proactive recovery (§7.4) is RECOMMENDED
  but not MANDATORY until the authorization actually expires.
- **Slower-than-expected gateway:** `GatewayObservation` degradation. This
  is a selection concern (N2.4-03 §8), not a recovery trigger.

## 6. Recovery Decision State Machine

A `TransportSession` is always in exactly one recovery state:

```text
ACTIVE
    The session has a live circuit carrying traffic.
    ↓ [F1–F11 detected, OR proactive trigger]
DETECTING
    Confirm the failure is real (not transient packet loss).
    Retry one keepalive with a short timeout (default 500ms).
    ↓ [confirmed failure]
    ↓ [transient — return to ACTIVE]
RECOVERING
    Decide the recovery tier (§8):
      R1 (relay failure, same gateway) — OR
      R2 (gateway failure/expiry/revocation, different gateway)
    ↓
    teardown old circuit (if not already torn down by the failure)
    ↓
    discover replacement route + (for R2) replacement gateway
    ↓
    establish new circuit (NEW circuit_id, NEW keys, NEW sequence)
    ↓
    rebind session to new circuit (§9)
    ↓
    [R1 success] → ACTIVE (outbound TCP preserved)
    [R2 success] → ACTIVE (outbound TCP NOT preserved for Mode B;
                            Mode A continues with new outbound request)
    [budget exhausted] → FAILED
FAILED
    The session is terminated. The application is notified:
      - Mode A: the pending request returns an error; the application may retry.
      - Mode B: the application's TCP connection is reset (RST).
```

### 6.1 State transition invariants

1. A session in `RECOVERING` MUST NOT carry user traffic on the old circuit.
   The old circuit is torn down before any new traffic is sent.
2. A session in `RECOVERING` MAY buffer outbound user data (bounded buffer,
   §13) so that if recovery succeeds, buffered data is sent on the new circuit.
3. A transition to `FAILED` for Mode B MUST emit a TCP RST to the
   application. It MUST NOT silently drop the connection.
4. A transition to `FAILED` for Mode A MUST return an error to the pending
   request. It MUST NOT hang.
5. `DETECTING` is bounded (single retry, short timeout). It MUST NOT become
   an infinite retry loop.

## 7. Recovery Procedure

### 7.1 Step 1 — Teardown the old circuit

```text
if old circuit exists and is not already torn down:
    issue CircuitTeardown (source-signed, N2.3 frozen) to all relays + gateway
    wait for local teardown confirmation (bounded, default 2s)
    (do NOT wait indefinitely — the relays may be unreachable, which is why we're recovering)
```

The teardown is best-effort. If a relay is unreachable (F1/F2), it will not
receive the teardown — but its forwarding state will expire at
`handshake.expiry` (≤ `CIRCUIT_MAX_LIFETIME_SECS` = 3600s) or be wiped on
restart. The source MUST NOT hold the session in `RECOVERING` waiting for an
unreachable relay's teardown acknowledgment.

### 7.2 Step 2 — Discover a replacement route (and gateway, if R2)

```text
if recovery tier R1 (same gateway, relay failure):
    discover a new CommittedRoute to the SAME gateway, avoiding the failed relay
    (the gateway's authorization is still valid; no new gateway selection)

if recovery tier R2 (different gateway):
    run full gateway selection (N2.4-03 §8.2):
      verify CapabilityAuthorization
      → verify validity/revocation
      → evaluate authorization scope
      → evaluate declared policy
      → verify reachability
      → evaluate observations
      → apply preferences/economics
      → select gateway
    then discover a CommittedRoute to the selected gateway
```

### 7.3 Step 3 — Establish a new circuit

```text
new_circuit_id = CSPRNG(32 bytes)        // fresh
new_ephemeral_x25519 = generate()         // fresh
new_handshake = CircuitHandshake {         // fresh, source-signed
    circuit_id: new_circuit_id,
    commitment_hash: new_route.commitment(),
    authorization_root: recompute over new relay authorizations,
    expiry: min(new_route.proposal.expiry, now + CIRCUIT_MAX_LIFETIME_SECS),
    ...
}
new ActiveCircuit {                       // fresh !Clone owner
    circuit_id: new_circuit_id,
    route: new_route,
    keys: fresh per-hop keys (new DH, new HKDF),
    seq_state: fresh CircuitSeqState (next_seq = FIRST_PACKET_SEQ = 1),
    expires_at: new_handshake.expiry,
}
```

**Everything is fresh except the TSID** (and, for R1 Mode B, the
`SessionBindingKey` and the gateway's outbound TCP connection). This is the
core of the composition rule (§11).

### 7.4 Proactive recovery (before failure)

For F4 (gateway authorization expiring) and F5/F6 (revocation / scope change
detected pre-flight), the source SHOULD initiate recovery **before** the
current circuit fails:

```text
if gateway_authorization.expires_at - now < PROACTIVE_RECOVERY_THRESHOLD:
    (PROACTIVE_RECOVERY_THRESHOLD default = 60s)
    enter RECOVERING
    establish new circuit to a (possibly different) still-authorized gateway
    rebind session to new circuit
    teardown old circuit
```

This avoids a hard failure mid-traffic. The old circuit continues to carry
traffic until the new circuit is ready (make-before-break), then the session
atomically switches over. This is the one case where two circuits may briefly
exist for the same session — but they have **different `circuit_id`s** and the
old one is being torn down. There is no circuit multiplexing; the session sends
on exactly one circuit at a time.

## 8. Recovery Tiers

### 8.1 Tier R1 — Relay failure, same gateway

**Trigger:** F1, F2 (intermediate relay disappeared or restarted).

**What can be preserved:** the gateway's outbound TCP connection (Mode B) or
outbound request context (Mode A). The destination-side connection is
unaffected — only the ShareNet path changed.

**Procedure:**
1. Teardown old circuit.
2. Discover new route to the **same gateway**, avoiding the failed relay.
3. Establish new circuit (new `circuit_id`, new keys, new sequence).
4. For Mode B: send a `RESUME` control message on the new circuit carrying
   `(TSID, SessionBindingKey)`. The gateway verifies the key and re-associates
   the new circuit to the existing outbound TCP connection.
5. For Mode A: the next request on the new circuit carries the TSID; the
   gateway re-associates to any application-layer session state (e.g., cookies,
   connection pooling) it holds for that TSID.

**Application-visible effect:** a latency blip (typically 1–5s for detection
+ recovery). No connection reset. This achieves spec §6.7's "Route switch...
   Circuit state preserved. Application sees a latency blip" **at the session
   layer**, without preserving anything at the (frozen) circuit layer.

### 8.2 Tier R2 — Gateway failure / expiry / revocation, different gateway

**Trigger:** F3, F4, F5, F6 (gateway offline, authorization expired/revoked,
or scope no longer covers the destination).

**What CANNOT be preserved:** the gateway's outbound TCP connection (Mode B).
The origin-side socket lived on Gateway A's kernel. When A is gone, the socket
is gone. **This is the honest limit** (spec §6.7:425–433).

**Procedure:**
1. Teardown old circuit (to Gateway A — best-effort, A may be unreachable).
2. Select a new gateway (full N2.4-03 §8.2 selection).
3. Discover route to new gateway.
4. Establish new circuit to new gateway (new `circuit_id`, new keys).
5. For Mode B: the new gateway has no outbound TCP for this TSID. The session
   **MUST** signal a TCP RST to the application. The application's existing
   connection is lost. **New** connections from the application succeed
   immediately via the new gateway (the session layer accepts the new
   connection and binds it to the new circuit).
6. For Mode A: the pending request is re-issued on the new circuit. If the
   destination is reachable and the request is idempotent, it succeeds. If the
   request was non-idempotent and may have already reached the destination
   via Gateway A, the session layer MUST NOT auto-retry (the application must
   decide). **Mode A bundles** (addressed to a set of acceptable gateways)
   survive gateway loss entirely — any remaining gateway completes them.

**Application-visible effect (Mode B):** a TCP RST. This is identical to a
Wi-Fi/cellular handoff dropping a connection. It is **not** transparent TCP
migration. The ADR explicitly forbids claiming otherwise (§16).

**Application-visible effect (Mode A):** for idempotent requests, a latency
blip. For non-idempotent requests, an error returned to the application (which
may retry at the application layer). For bundles, no visible effect.

### 8.3 Tier R0 — Circuit expiry / sequence exhaustion (same gateway, same route)

**Trigger:** F8, F9 (circuit expired or sequence exhausted).

This is **not** a failure — it is the normal circuit lifecycle. The gateway is
still authorized and reachable; only the circuit object has reached its limit.

**Procedure:** same as R1 (teardown + new circuit to same gateway + rebind).
For Mode B, the `RESUME` mechanism preserves the outbound TCP. This is the
**planned** recovery path — the source SHOULD proactively rotate circuits
before `expires_at` or before sequence exhaustion, using make-before-break
(§7.4).

## 9. Session Rebinding

### 9.1 What is rebound

When a new circuit is established for an existing session:

```text
TransportSession.current_circuit ← new ActiveCircuit
TransportSession.recovery_state ← ACTIVE
```

The TSID is unchanged. The application's view of the session is unchanged
(except where R2 Mode B forces a reset).

### 9.2 Gateway-side re-association

The gateway maintains:

```text
GatewaySessionTable {
    TSID → {
        outbound_connection:  Option<TcpStream>,   // Mode B
        request_context:      Option<RequestCtx>,    // Mode A
        session_binding_key:   SessionBindingKey,
        bound_circuit_id:      CircuitId,            // the circuit currently bound
        last_seen:             u64,
    }
}
```

When a new circuit (new `circuit_id`) carries a `RESUME` (Mode B) or a
request (Mode A) with a known TSID and valid `SessionBindingKey`:

- **Mode B R1:** the gateway re-points `bound_circuit_id` to the new
  `circuit_id`. The `outbound_connection` (existing TCP) is unchanged.
  Subsequent byte-stream traffic on the new circuit is forwarded to the same
  outbound TCP.
- **Mode B R2:** the gateway has no record of this TSID (it's a different
  gateway). The `RESUME` is rejected. The session layer signals RST.
- **Mode A:** the gateway re-associates the TSID to any application-layer
  session state it holds (cookies, auth tokens — if the user configured the
  gateway to maintain them). A new outbound request is made. The TSID does not
  itself carry application-layer auth; it only lets the gateway correlate
  requests from the same session.

### 9.3 Session table expiry

The `GatewaySessionTable` entries expire:
- when the last bound circuit expires (no `RESUME` arrived), OR
- after a gateway-configured idle timeout (default 300s), OR
- when the gateway's own authorization expires/revoked (all entries are
  discarded — the gateway can no longer serve).

The `SessionBindingKey` is erased on expiry. A `RESUME` for an expired TSID
is rejected; the session must start fresh.

## 10. In-Flight Packet Handling

### 10.1 The problem

When a circuit tears down (failure or recovery), packets already sent on it
are in-flight: they are in relay buffers, in transit, or already delivered to
the gateway. The frozen N2.3 layer says: after teardown, `forward_packet`
returns `UnknownCircuit` / `CircuitTornDown` for any further packet. There is
**no graceful drain** mechanism.

### 10.2 N2.4-04 handling

- **Packets already delivered to the gateway** before teardown: they are
  processed normally (the gateway's outbound connection already received
  them). No loss.
- **Packets in transit when the relay disappeared (F1):** lost. The relay
  that disappeared cannot forward them. The adjacent relay's
  `forward_packet` returns an error or silently drops.
- **Packets sent after teardown but before the new circuit is bound:**
  rejected by relays (`UnknownCircuit`). The session layer (in `RECOVERING`
  state) does NOT send user packets during this window — it buffers them
  (bounded, §13) or back-pressures the application.

### 10.3 Recovery of lost packets

N2.4-04 does **not** define a packet-level retransmission protocol. Lost
in-flight packets are recovered at a higher layer:

- **Mode A (request/response):** the request either completed (response was
  received before failure) or did not. If not, the session layer retries the
  request on the new circuit **only if the request is idempotent**. For
  non-idempotent requests, the application is notified and decides.
- **Mode B (byte-stream):** the byte stream is TCP. TCP's own retransmission
  handles in-flight bytes **within the outbound TCP connection** (which
  survives for R1). For R2 (gateway gone), the outbound TCP is gone — the
  bytes are lost and the application's TCP is reset.

### 10.4 No silent loss

A session transition to `FAILED` MUST notify the application. N2.4-04 forbids
silently dropping user data. If recovery fails, the application knows.

## 11. State Migration Rules (Composition)

### 11.1 What MIGRATES across circuit replacement

| State | Migrates? | Condition |
|-------|-----------|-----------|
| `TransportSessionId` (TSID) | Yes | Always — it is the session anchor |
| `SessionBindingKey` | Yes | R1 only (same gateway); NOT R2 (different gateway has no record) |
| Gateway's outbound TCP connection (Mode B) | Yes | R1 only; R2 cannot (§8.2) |
| Gateway's application-layer session state (Mode A) | Yes | R1 only, if the gateway maintains it |
| `destination` descriptor | Yes | Always — the session target is unchanged |

### 11.2 What is FRESH on each new circuit (NEVER migrated)

| State | Why fresh |
|-------|-----------|
| `circuit_id` | Frozen N2.3 binds it to a specific route; new route → new `circuit_id` |
| `commitment_hash` | New route → new commitment |
| Per-hop forwarding keys | Derived from `(ephemeral_secret, relay_pub, circuit_id, commitment_hash)` — all four change |
| `CircuitSeqState` | `!Clone`; new circuit owns a fresh allocator (`next_seq = 1`) |
| Replay window | Per-circuit; new circuit = fresh window |
| `expires_at` | New handshake → new expiry |
| `authorization_root` | New relay set → new root |

### 11.3 Composition invariant

> **The only state that crosses a circuit boundary is session-identity state
> (TSID +, for R1, the gateway's outbound connection and binding key). All
> cryptographic and sequence state is circuit-scoped and dies with the
> circuit.**

This is the formal rule that prevents N2.4-04 from accidentally turning
into frozen-semantics violation: because no cryptographic state migrates,
there is no nonce reuse, no sequence wraparound, no replay-window
contamination, no commitment-hash inconsistency. The frozen invariants hold
because each circuit is a clean, independent cryptographic instance.

## 12. Circuit Invalidity Conditions

A circuit is **invalid** (cannot carry new traffic) when any of:

1. `now >= expires_at` — circuit expired (F8).
2. `seq == u32::MAX` and `exhausted == true` — sequence exhausted (F9).
3. A `CircuitTeardown` was issued and processed — circuit torn down.
4. A relay on the route has restarted and lost its `RelayForwardingState`
   (F2) — the relay returns `UnknownCircuit`.
5. A relay on the route is unreachable (F1) — packets cannot traverse.
6. The gateway's authorization has expired or been revoked (F4/F5) —
   **but note**: per N2.4-03 §15, existing circuits continue until their own
   expiry. So the **circuit** is not immediately invalid; but the session
   layer SHOULD proactively recover (§7.4) because no new circuits can be
   established to that gateway.

An invalid circuit MUST NOT be used to send new traffic. The session layer
MUST transition to `RECOVERING` (or `FAILED` if budget is exhausted) upon
detecting invalidity.

## 13. Recovery Budget and Anti-Oscillation

### 13.1 Recovery budget

Each `TransportSession` has a bounded recovery budget:

```text
DEFAULT_RECOVERY_BUDGET = 3   // attempts
MAX_RECOVERY_BUDGET     = 5   // upper bound (configurable down, never up)
```

Each transition `ACTIVE → DETECTING → RECOVERING → (ACTIVE | FAILED)` that
returns to `ACTIVE` does NOT replenish the budget — but a sustained `ACTIVE`
period (default 60s without a new failure) DOES reset the budget to its
default. This prevents a permanently-flapping session from consuming recovery
attempts forever, while allowing a session that stabilizes to recover its
budget.

When the budget is exhausted, the session transitions to `FAILED`:

- Mode A: return an error to the pending request.
- Mode B: emit TCP RST.

### 13.2 Anti-oscillation

To prevent a session from oscillating between `ACTIVE` and `RECOVERING` (which
would amplify load across relays and gateways):

- **Recovery cooldown:** after a successful recovery, the session MUST remain
  in `ACTIVE` for at least `RECOVERY_COOLDOWN` (default 10s) before another
  recovery can be initiated. Failures during cooldown are buffered (not
  immediately recovered).
- **Backoff:** each successive recovery attempt within a budget window uses
  exponential backoff (base 1s, factor 2, cap 30s) before re-entering
  `RECOVERING`.
- **No concurrent recoveries for the same session:** a session has exactly
  one recovery in flight at a time. (Multiple sessions may recover
  concurrently — that is expected and allowed.)
- **Circuit establishment rate limit:** the source MUST NOT establish
  circuits faster than `MAX_CIRCUIT_ESTABLISHMENT_RATE` (default 10/min per
  gateway) to avoid hammering a recovering gateway or relay set.

### 13.3 Amplification bound

The recovery architecture MUST NOT become a DoS amplifier. If a relay is
flapping (up/down every few seconds), the source's recovery attempts are
bounded by the budget and backoff. After budget exhaustion, the session
fails — it does not retry indefinitely.

## 14. ShareNetOverlayDestination Classification (N2.4-03 dependency)

N2.4-03 §10.1.1 deferred the concrete classification mechanism for
`ShareNetOverlayDestination` to N2.4-04. This section fulfills that
dependency.

### 14.1 Classification mechanism

A gateway classifies a destination as a `ShareNetOverlayDestination` by
checking it against the gateway's **local authenticated peer table** — the set
of ShareNet transport endpoints the gateway has authenticated or currently
maintains sessions with:

```text
ShareNetOverlayDestination check (gateway-local):
    for each authenticated ShareNet transport endpoint E in the gateway's peer table:
        if destination.address matches E.address
           AND destination.transport matches E.transport:
            return IS_OVERLAY
    return IS_NOT_OVERLAY   (fail-open: unknown → not overlay)
```

- **Local, not global:** the gateway checks its own peer table. There is no
  global registry of all ShareNet node IPs. A destination the gateway has
  never seen as a ShareNet peer is classified `IS_NOT_OVERLAY`.
- **Authenticated:** the peer table contains only endpoints that have
  authenticated via the ShareNet transport handshake (Ed25519 → NodeId
  binding, per spec/02-identity.md). An unauthenticated endpoint claiming to
  be a ShareNet node is NOT in the table.
- **Transport-aware:** the classification matches on `(transport, address)`,
  not address alone — the same IP on a different transport (e.g., a ShareNet
  relay's public HTTPS port vs. its ShareNet overlay port) may be classified
  differently.
- **Fail-open for unknown, fail-closed for known:** if the destination
  matches an authenticated peer, it IS overlay → rejected (fail-closed). If it
  matches nothing in the table, it is NOT overlay → allowed (subject to the
  canonical egress deny set and gateway policy).

### 14.2 Completeness and the honest gap

This classification is **best-effort**: a ShareNet node the gateway has never
authenticated (e.g., a relay that joined after the gateway's last peer-table
sync) would not be classified as overlay. This is an accepted limitation. The
canonical egress deny set (N2.4-03 §10.1) still protects against the SSRF
ranges regardless; the overlay classification adds protection against
gateway-to-gateway loops for **known** overlay endpoints.

A future profile (N2.4-07+, if a `PacketProfile::V3` is introduced) MAY add an
in-band overlay-marker field to make the classification authoritative rather
than best-effort. N2.4-04 does not require it.

### 14.3 Gateway-to-gateway loop prevention

With §14.1, gateway-to-gateway loops are prevented as follows: when Gateway A
attempts to exit to a destination, it checks whether that destination is a
`ShareNetOverlayDestination` (i.e., another ShareNet node's transport
endpoint). If it is, the egress is rejected. This prevents Gateway A from
forwarding traffic to Gateway B over the overlay, which would create a loop
(circuit-in-circuit) and enable exfiltration and amplification.

## 15. Interaction with N2.4-03 Gateway Lifecycle

### 15.1 Gateway authorization expiry (F4)

Per N2.4-03 §15: when a gateway authorization expires, the gateway cannot
accept **new** circuits, but **existing** circuits continue until their own
`expires_at` (bounded staleness).

N2.4-04 adds the session-layer behavior:
- The source's pre-flight check (§5.2) detects the expiry before establishing
  new circuits to that gateway.
- Existing sessions on existing circuits continue normally until the circuit
  expires — then R0 recovery (§8.3) selects a **different** gateway (the
  expired gateway can no longer serve).
- Proactive recovery (§7.4) SHOULD rotate the session to a new gateway
  **before** the current circuit expires, to avoid a hard failure.

### 15.2 Gateway authorization revocation (F5)

Same as expiry, but urgent. The source's revocation-list check (run at
keepalive intervals) detects revocation. The session enters `RECOVERING`
immediately. The existing circuit (if still within its `expires_at`) continues
to carry traffic until the new circuit is ready (make-before-break), because
N2.4-03 §15 preserves existing circuits. Then the session switches to the new
circuit on a new gateway.

### 15.3 Issuer authority governance-revoked (F7)

Per N2.4-02 and N2.4-03 §15 (corrected in revision 3): governance revocation
prevents the issuer from issuing **new** authorizations; **existing**
authorizations remain valid until their own `validity_end` unless separately
subject-revoked.

N2.4-04 session-layer behavior:
- Existing circuits to gateways authorized by the revoked issuer continue
  until their own `expires_at`.
- No new circuits can be established to those gateways (the issuer cannot
  re-authorize; when the existing authorizations expire, the gateway cannot
  renew).
- The session layer proactively migrates to gateways authorized by a
  **different** issuer before the existing authorizations expire.

**If N2.4-04 (or a later ADR) wants an emergency "kill all active
authorizations from issuer I" mechanism** — that is a **new explicit protocol
decision**, not an accidental consequence of issuer revocation. It is NOT
defined in N2.4-04. It would require either (a) governance signing a
subject-level revocation for each affected gateway, or (b) a new protocol
mechanism (e.g., a governance-signed "authority-class revocation" that
invalidates all authorizations from a specific issuer immediately). Option (b)
is deferred to a future ADR if required.

## 16. What N2.4-04 MUST NOT Do (Frozen Semantics Boundary)

N2.4-04 MUST NOT:

1. **Modify N2.3 V1 or V2 packet format.** The 5-field / 8-field CBOR, the
   AAD construction, the nonce derivation, and the golden wire vectors are
   immutable (protocol-freeze.md).
2. **Re-use a `circuit_id` across different routes.** The frozen
   `commitment_hash` binding makes this a semantic violation. Each new route
   = new `circuit_id`.
3. **Migrate per-hop forwarding keys across circuits.** Keys are derived from
   `(ephemeral_secret, relay_pub, circuit_id, commitment_hash)`; migrating
   them would require migrating `circuit_id` (forbidden by #2) or reusing
   nonces (catastrophic for ChaCha20-Poly1305).
4. **Migrate `CircuitSeqState`.** It is `!Clone`. Two senders on the same
   circuit would emit duplicate `seq` under the same nonce — forbidden.
5. **Migrate replay windows.** A replay window is per-circuit; cross-circuit
   replay contamination is undefined and forbidden.
6. **Introduce in-band session resumption tokens in the packet.** Any such
   field would require `PacketProfile::V3` (deferred to N2.4-07). The TSID
   rides in the gateway application protocol, not the circuit packet.
7. **Claim transparent TCP migration across gateway failure (Mode B).** The
   origin-side socket lives on the gateway; when the gateway dies, the socket
   dies. Applications see a RST. N2.4-04 forbids UI, documentation, or
   protocol claims that imply otherwise (spec §6.7:433).
8. **Modify the replay-window ordering** (check-before-AEAD, commit-after-AEAD,
   O(WINDOW) update, `ProfileMismatch` before AEAD). All frozen.
9. **Modify `CircuitTeardown` semantics.** Teardown is source-signed and
   removes forwarding state immediately. N2.4-04 uses it as-is.
10. **Bypass the canonical egress deny set** (`CanonicalShareNetEgressDenySet`)
    during recovery. A replacement gateway's egress is subject to the same
    destination validation (N2.4-03 §5.3) as the original.
11. **Establish a recovery circuit to an unauthorized gateway.** The full
    N2.4-03 §8.2 selection ordering applies to every recovery circuit.

## 17. Does N2.4-04 Need PacketProfile::V3?

### 17.1 Analysis

The recovery architecture defined here operates **entirely above** the frozen
circuit layer:
- Detection uses transport timeouts and frozen `TrafficError` variants.
- Recovery uses frozen `CircuitTeardown` + frozen circuit establishment.
- Session rebinding uses the gateway application protocol (TSID), not the
  packet.
- No cryptographic state migrates across circuits.

Therefore **N2.4-04 does NOT require `PacketProfile::V3`** for the core
recovery mechanism. V1 and V2 circuits are replaced via teardown +
re-establishment; the session layer provides continuity.

### 17.2 When V3 would be needed

A future `PacketProfile::V3` would be needed only if the architecture wanted:
- In-band session-resumption tokens in the packet (to avoid the gateway
  application protocol carrying the TSID).
- In-band circuit-migration signaling (to avoid teardown + re-establishment
  for relay-only failure).
- Per-session (rather than per-circuit) replay windows.

These are **optimizations**, not requirements. N2.4-04 deliberately does NOT
introduce them, because:
- They would modify frozen packet semantics (forbidden).
- They would require new golden vectors and a new ADR (N2.4-07).
- The session-layer approach achieves the same continuity without packet
  changes.

### 17.3 Decision

`PacketProfile::V3` is **deferred to N2.4-07** (charter §6) as a conditional
future milestone. N2.4-04 does not block on it and does not introduce it.

## 18. Security Invariants

1. **N2.3 packet semantics are immutable.** N2.4-04 does not modify V1/V2
   wire format, AAD, nonce, replay ordering, or golden vectors.
2. **No `circuit_id` reuse across routes.** A new route always yields a new
   `circuit_id`. The frozen `commitment_hash` binding is preserved.
3. **No cryptographic state migration.** Keys, sequence state, replay windows,
   and `authorization_root` are circuit-scoped and die with the circuit. Only
   session-identity state (TSID, and for R1 the gateway binding key + outbound
   connection) migrates.
4. **No nonce reuse.** Because keys and `circuit_id` are fresh on each new
   circuit, the AEAD nonce space is injective per-circuit. The frozen
   no-wraparound invariant is preserved.
5. **Recovery does not bypass authorization.** Every recovery circuit goes
   through the full N2.4-03 §8.2 selection ordering. An unauthorized gateway
   cannot become a recovery target.
6. **Recovery does not bypass the canonical egress deny set.** A replacement
   gateway's egress is subject to `CanonicalShareNetEgressDenySet`
   unconditionally (N2.4-03 §5.3.1, §10.1).
7. **No transparent TCP migration across gateway failure.** Mode B gateway
   failure yields a TCP RST. The architecture does not claim otherwise.
8. **Recovery is bounded.** A session has a finite recovery budget
   (default 3, max 5) and backoff. It cannot retry forever or amplify load.
9. **No silent data loss.** A transition to `FAILED` notifies the application
   (error for Mode A, RST for Mode B). Buffered data is either delivered (on
   success) or reported lost (on failure).
10. **Teardown is best-effort, not blocking.** Recovery does not stall waiting
    for an unreachable relay's teardown acknowledgment. The relay's state
    expires at `handshake.expiry` or is wiped on restart.
11. **Issuer revocation does not kill existing circuits.** Consistent with
    N2.4-02 and N2.4-03 §15 (revision 3): existing authorizations remain
    valid until their own `validity_end`. An emergency kill mechanism, if
    ever needed, is a separate explicit protocol decision.
12. **`ShareNetOverlayDestination` classification is best-effort, not
    authoritative.** It uses the gateway's local authenticated peer table.
    Unknown destinations are classified `IS_NOT_OVERLAY` (fail-open). The
    canonical egress deny set remains enforced regardless.
13. **Two circuits for one session exist only during make-before-break.**
    Proactive recovery (§7.4) may briefly hold an old and a new circuit. They
    have different `circuit_id`s; the session sends on exactly one at a time.
    There is no circuit multiplexing.
14. **Recovery state is persistent across source restart (F11).** The
    `TransportSession` state (TSID, destination, recovery budget) is
    persisted per N2.4-02 invariant #11. On source restart, the session layer
    reconstructs sessions and enters `RECOVERING` (the old circuit is gone).
    In-flight data is lost (consistent with §10).
15. **Recovery does not weaken the composition rule.** The effective
    destination permission on a recovery circuit is still
    `auth_scope ∩ declared_policy ∩ canonical_egress_safety` (N2.4-03 §17
    invariant 18). Recovery introduces no exception to this intersection.

## 21. Implementation Boundaries

N2.4-04 defines the **architecture**. Implementation will produce:

- Transport session layer (client-side `TransportSession` state machine)
- Gateway session table (TSID → outbound connection / request context)
- `RESUME` control message handler (gateway application protocol)
- Recovery orchestration (detection → decision → teardown → re-establish →
  rebind)
- `ShareNetOverlayDestination` classification (gateway local peer table check)
- Make-before-break proactive recovery controller
- Recovery budget + backoff + cooldown enforcement

Implementation is **blocked** until:
- N2.4-04 is approved
- N2.4-05 (Transport Abstraction) is at least proposed (the session layer
  depends on the transport abstraction boundary)
- Conformance vectors are defined

**N2.3 frozen implementation MUST NOT be modified.**

Implementation MUST NOT:
- Add session-state fields to V1/V2 circuit packets.
- Reuse a `circuit_id` across routes.
- Migrate `CircuitSeqState`, forwarding keys, or replay windows.
- Bypass the canonical egress deny set during recovery.
- Claim transparent TCP migration across gateway failure.
