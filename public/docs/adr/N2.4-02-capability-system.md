# N2.4-02 — Capability System + Sybil/Admission Architecture

**Status:** DRAFT — awaiting review

**Parent:** N2.4-01 Threat Model (approved, `b0aafa3`)

**Baseline:** N2.3 frozen @ `425eccb` (tag: `v2.3.0-protocol`)

---

## 1. Problem Statement

N2.3 provides cryptographic identity (Ed25519) and authenticated route
establishment (signed acceptances). It does NOT provide:

- Sybil resistance (anyone can create unlimited valid identities)
- Capability authentication (a node can claim "I am a gateway" without proof)
- Capability authorization (even an authenticated claim may not be permitted)
- Capability policy (what a gateway is allowed to do)
- Capability revocation (removing a malicious gateway's authorization)

N2.4-02 defines the architecture that fills these gaps. Without it, N2.4-03
(Gateway Architecture) would make implicit authorization decisions that
belong in the capability system.

**Core invariant (from N2.4-01):**

> No self-asserted capability may by itself authorize privileged network
> behavior.

---

## 2. Terminology

| Term | Definition |
|------|-----------|
| **Capability** | A protocol-level ability a node can provide (e.g., INTERNET_GATEWAY). |
| **CapabilityClaim** | "I claim to provide X." Self-asserted, unsigned or signed by the node. |
| **AuthenticatedCapabilityClaim** | "This node cryptographically signed the claim." Verifiable by anyone with the node's public key. |
| **AuthorizedCapability** | "This claim is permitted to be used by the network." Requires an admission/authorization decision separate from the claim. |
| **CapabilityPolicy** | "What are the rules for using this capability?" (exit destinations, bandwidth, protocols, etc.) |
| **CapabilityCapacity** | "What resources does this capability provide?" (bandwidth, storage, compute — a claim, not a fact). |
| **ObservedCapability** | "The network has measured X happening." Empirical, not claimed. |
| **Authorization** | The process of turning an AuthenticatedCapabilityClaim into an AuthorizedCapability. |
| **Admission** | The process of allowing a node to participate in the network at a given trust level. |
| **Revocation** | The process of removing a previously-authorized capability. |

**Critical separation:**

```
AuthenticatedCapabilityClaim ≠ AuthorizedCapability
```

An authenticated claim proves the node signed it. It does NOT prove the
network permits it.

## 3. Capability Taxonomy

### 3.1 Initial protocol capabilities

| Capability | Risk class | Self-assertion sufficient for discovery? | Privileged admission required? |
|-----------|-----------|------------------------------------------|-------------------------------|
| `MESH_RELAY` | Low | Yes (discovery only) | No (anyone can relay) |
| `INTERNET_GATEWAY` | High | Yes (discovery only) | Yes (authorization required) |
| `DISCOVERY` | Low | Yes | No |
| `CONTENT_SEED` | Medium | Yes | No (but resource-limited) |
| `STORAGE` | Medium | Yes | No (but quotas apply) |
| `SYNC` | Low | Yes | No |
| `COMPUTE` | High | Yes (discovery only) | Yes (authorization required) |

### 3.2 Risk classification

- **Low-risk** capabilities (`MESH_RELAY`, `DISCOVERY`, `SYNC`): any
  authenticated node may self-assert. The worst case is a bad relay or a
  noisy discovery node — the N2.3 cryptographic model handles this (bad
  relays can't forge routes; bad discovery is non-authoritative).

- **Medium-risk** capabilities (`CONTENT_SEED`, `STORAGE`): self-assertion
  is sufficient for discovery, but resource quotas must apply to prevent
  exhaustion.

- **High-risk** capabilities (`INTERNET_GATEWAY`, `COMPUTE`): self-assertion
  is sufficient for discovery (so clients know the node exists), but
  privileged admission/authorization is REQUIRED before the network
  treats the capability as trustworthy.

### 3.3 Capability type structure

Capabilities are NOT collapsed into one struct. The protocol separates:

```
Capability (the type: INTERNET_GATEWAY)
    ↓
CapabilityClaim (self-asserted, signed by node)
    ↓
CapabilityPolicy (exit destinations, protocols, bandwidth — a claim)
    ↓
CapabilityCapacity (bandwidth, storage, compute — a claim)
    ↓
Authorization (separate from claim — from an issuer/admission system)
    ↓
ObservedCapability (measured by the network — empirical)
```

## 4. Trust Hierarchy

### 4.1 Trust levels

| Level | Capabilities | Admission requirement |
|-------|-------------|----------------------|
| **Tier 0 — Open** | `MESH_RELAY`, `DISCOVERY`, `SYNC` | None (any Ed25519 identity) |
| **Tier 1 — Self-asserted + resource-limited** | `CONTENT_SEED`, `STORAGE` | Self-assertion establishes **eligibility/advertisement** (not privileged authorization); intended mitigation: resource quotas (architecture deferred) |
| **Tier 2 — Authorized** | `INTERNET_GATEWAY`, `COMPUTE` | External authorization required (issuer-signed) |

**Vocabulary note:** For Tier 0/1, self-assertion establishes
**eligibility** (the node may advertise the capability), not
**authorization** (the network permits privileged behavior). Only Tier 2
capabilities require explicit **authorization**. This avoids the word
"authorization" meaning two different things.

### 4.2 The capability chain (normative)

```
Node identity (Ed25519)
    ↓
Capability claim (self-asserted, signed by node)
    ↓
Capability authentication (signature verification)
    ↓
Authorization / admission (Tier 2 only: external authorization)
    ↓
Policy / capacity (exit rules, bandwidth, region — claimed)
    ↓
User selection (client chooses from available authenticated gateways)
    ↓
Measured behavior (observed, audited — empirical)
```

For Tier 0/1 capabilities, authorization is implicit (self-assertion is
sufficient). For Tier 2 capabilities, an explicit authorization step is
required — the claim alone does NOT authorize.

## 5. Sybil/Admission Model

### 5.1 The problem

Ed25519 identity provides cryptographic uniqueness but not Sybil resistance.
An attacker can create unlimited valid identities. The threat model (N2.4-01)
leaves Sybil resistance as OPEN.

### 5.2 Separation of concerns

```
Identity creation cost       = how expensive is it to create a NodeId?
Capability admission         = who is allowed to claim a capability?
Routing trust                 = does the network route through this node?
Economic reputation           = does the node have a good track record?
```

These are SEPARATE concerns. A single mechanism should not conflate them.

### 5.3 Decision: hybrid model

N2.4-02 proposes a **hybrid admission model**:

**Tier 0 (Open):** Any Ed25519 identity may self-assert `MESH_RELAY`,
`DISCOVERY`, or `SYNC`. No admission gate. The N2.3 cryptographic model
(bad relays can't forge routes; topology hints are non-authoritative)
provides sufficient protection for these capabilities.

**Tier 1 (Self-asserted + quota):** Any identity may self-assert
`CONTENT_SEED` or `STORAGE`, but resource quotas are enforced per-node.
Sybil resistance is not provided — but resource limits bound the damage.

**Tier 2 (Authorized):** `INTERNET_GATEWAY` and `COMPUTE` require external
authorization. The authorization mechanism is:

- **Phase 1 (N2.4 initial):** Permissioned/curated. A set of
  authorization issuers (identified by their Ed25519 keys) sign
  capability authorizations. The list of authorized issuers is
  configured/curated by the network operator or governance body.
  
- **Phase 2 (future):** The authorization mechanism may evolve to
  invitation-based, stake-based, or proof-of-work — but this is a FUTURE
  decision, not an N2.4-02 decision. Phase 1 explicitly uses curated
  authorization because it is the simplest model that satisfies the
  "no self-asserted capability authorizes privileged behavior" invariant.

### 5.4 What N2.4-02 does NOT decide

- Proof-of-work vs stake vs invitation: **deferred to a future ADR.**
  The architecture separates authorization from the mechanism; Phase 1
  uses curated authorization; Phase 2 may substitute a different mechanism.
- Economic reputation system: **deferred.** Reputation may inform user
  selection but MUST NOT determine cryptographic authorization.
- Identity creation cost: **deferred.** Ed25519 key generation remains
  free. If identity creation cost is needed (for Sybil resistance), it
  will be a separate ADR.

### 5.5 Sybil risk acceptance

For Tier 0/1: Sybil risk is **explicitly accepted** with intended
mitigations (not yet designed):
- N2.3 cryptographic route integrity (bad relays can't forge routes) —
  already implemented.
- Resource quotas (intended to bound damage) — **enforcement architecture
  deferred to N2.4-09; residual risk remains OPEN.**
- Non-authoritative topology hints (Sybil nodes can't become authoritative
  without real X25519 circuit keys and signed acceptances) — already
  implemented.

For Tier 2: Sybil risk is **mitigated by curated authorization**. An
attacker cannot become an authorized gateway without an authorization
signature from a recognized issuer with appropriate issuer authority.

## 6. Authorization Model

### 6.1 Issuer Authority Profile

An issuer is not a single super-authority that can sign any capability
with any scope. Each issuer has an **IssuerAuthority** that bounds what
it may authorize:

```text
IssuerAuthority {
    issuer_id:              [u8; 32],   // NodeId of the issuer
    capabilities_authorized: Vec<Capability>,  // e.g., [INTERNET_GATEWAY]
    maximum_scope:          AuthScope,  // e.g., destinations=*, protocols=*
    validity_limit:         u64,         // issuer authority expiry
    delegation_allowed:     bool,        // can this issuer delegate?
    status:                 IssuerStatus, // Active / Revoked
    issuer_authority_signature: [u8; 64], // signed by governance root
}
```

The issuer authority itself is signed by a **governance root** (a
higher-level key or multi-sig that bootstraps the issuer set). This
prevents any single issuer from becoming an unrestricted super-authority.

### 6.2 Authorization structure

```text
CapabilityAuthorization {
    issuer_id:       [u8; 32],    // NodeId of the authorization issuer
    subject_id:      [u8; 32],    // NodeId of the authorized node
    capability:      Capability,  // e.g., INTERNET_GATEWAY
    scope:           AuthScope,   // constraints (destinations, protocols)
    validity_start:  u64,         // unix seconds
    validity_end:    u64,         // unix seconds (expiry)
    nonce:           [u8; 16],    // freshness
    issuer_signature: [u8; 64],   // Ed25519 signature by issuer
}
```

### 6.3 Authorization provenance

The authorization is signed by the **issuer's** Ed25519 key, not the
subject's. The subject cannot forge or self-sign an authorization.

The list of recognized issuers and their IssuerAuthority profiles is a
**network configuration parameter**, not a protocol constant. Different
ShareNet deployments may have different issuer sets with different
authority profiles.

### 6.4 Authorization verification

Authorization verification checks **authenticity and currency** —
NOT scope applicability (which requires a specific requested operation):

```text
verify_authorization(auth, subject_id, capability, now):
    1. issuer_signature is valid under issuer_id's public key.
    2. issuer_id is in the recognized issuer set.
    3. issuer_id's IssuerAuthority includes `capability` in
       capabilities_authorized.
    4. issuer_id's IssuerAuthority maximum_scope encompasses auth.scope.
    5. issuer_id's IssuerAuthority is active and not expired.
    6. validity_start <= now < validity_end.
    7. subject_id matches the node claiming the capability.
    8. capability matches the claimed capability.
    9. The authorization has not been revoked (check revocation list).
    → Returns: authorization is authentic and current.
```

### 6.5 Scope evaluation (separate from verification)

Scope evaluation checks whether a **requested operation** falls within
an authorization's scope. This is a separate operation from
`verify_authorization`:

```text
evaluate_scope(auth, requested_operation):
    1. Does requested_operation.destination fall within auth.scope.destinations?
    2. Does requested_operation.protocol fall within auth.scope.protocols?
    3. Does requested_operation fall within auth.scope.constraints?
    → Returns: allow / deny.
```

**Critical separation:**

```
verify_authorization()
    → Is this authorization authentic and current?

evaluate_scope()
    → Does this requested operation fall within its authorized scope?
```

Do NOT have `verify_authorization()` pretend to evaluate a scope against
no request. Scope evaluation requires a specific operation to evaluate
against.

## 7. Policy Model

### 7.1 Policy vs authorization

Authorization says "you are allowed to be a gateway." Policy says "what
are you allowed to do as a gateway."

Policy is **claimed by the node**, not issued by an authority. The network
verifies authorization; the user evaluates policy.

### 7.2 Policy structure

```text
CapabilityPolicy {
    destinations_allowed:  PolicyRule,   // allowlist / denylist / wildcard
    protocols_allowed:     PolicyRule,   // TCP / UDP / QUIC / all
    bandwidth_claim:       u64,           // claimed bandwidth (bps)
    byte_quota_per_period: Option<u64>,   // claimed quota
    period_seconds:        u64,           // quota period
    region:                Option<String>, // claimed geographic region
    exit_logging:          bool,          // does the gateway log? (claimed)
}
```

### 7.3 Policy is a claim, not a fact

Policy fields are self-asserted by the gateway. They are NOT automatically
trusted. The user/client evaluates policy alongside authorization and
observed behavior. A gateway may claim "no logging" while actually logging.

**Architectural invariant:** The protocol authenticates authorization.
It does NOT enforce policy honesty. Policy enforcement is an
application-layer concern.

---

## 8. Capacity Model

Capacity is a **claim** about resources:

```text
CapabilityCapacity {
    bandwidth_bps:     u64,
    storage_bytes:     Option<u64>,
    compute_units:     Option<u32>,
    max_concurrent_circuits: u32,
    uptime_percentage: u8,   // claimed (0-100)
}
```

Capacity is claimed, not verified by the protocol. ObservedCapability
(provided by monitoring/reputation systems, not the protocol itself) may
contradict capacity claims.

---

## 9. Observation Model

### 9.1 Claimed vs measured

```
CapabilityClaim     = "I can do X"           (self-asserted)
CapabilityCapacity  = "I have Y resources"   (self-asserted)
ObservedCapability  = "The network saw X"    (empirical)
```

### 9.2 What observations can and cannot authorize

Observations CANNOT authorize capabilities. Only authorization (from a
recognized issuer) can do that.

Observations CAN:
- Inform user selection (a user prefers gateways with good observed uptime)
- Trigger revocation proposals (if a gateway is observed violating policy)
- Feed reputation systems (future, separate from protocol)

Observations CANNOT:
- Grant authorization (no "I've been good, therefore I'm authorized")
- Override revocation (no "I'm still working, keep me authorized")
- Replace cryptographic authorization

## 10. Revocation / Expiry

### 10.1 Lifecycle

```
issued
    ↓
active (validity_start <= now < validity_end)
    ↓
restricted (issuer narrows scope — optional)
    ↓
expired (now >= validity_end)
    ↓
or revoked (issuer signs revocation)
    ↓
inactive (no longer valid)
```

### 10.2 Revocation

- Revocation is signed by the **issuer** (same key that authorized).
- Revocation is **not** signed by the subject (a malicious gateway cannot
  revoke itself to avoid detection, nor can it refuse to revoke).
- Revocation includes a timestamp + nonce for freshness.

### 10.3 Propagation

- Revocation lists are distributed via the topology/discovery protocol.
- A relay/gateway MUST check the revocation list before accepting a circuit
  that relies on an authorized capability.
- During a network partition, a node may have a stale revocation list.
  The risk: a revoked gateway continues to accept traffic until the
  partition heals. Mitigation: short authorization validity periods
  (e.g., 1 hour) so stale state expires naturally.

### 10.4 Expiry

- Every authorization has a `validity_end`.
- After expiry, the authorization is automatically invalid — no
  revocation needed.
- The subject must re-request authorization before the next validity
  period.
- This bounds the stale-state window during partitions.

### 10.5 Partition behavior

During a partition:
- A node cannot verify new authorizations (can't reach the issuer).
- A node cannot receive revocation updates.
- Existing authorizations remain valid until `validity_end`.
- After `validity_end`, the capability is automatically invalid.

This means: the worst case during a partition is a revoked gateway
continues operating until its authorization expires. The expiry bounds
this window.

## 11. Privacy Implications

### 11.1 What is exposed

- A node's capability claims are public (advertised in discovery).
- A node's authorizations are public (verifiable by anyone).
- A node's policy is public (advertised for user selection).
- A node's capacity is public (advertised).

### 11.2 What is NOT exposed

- The issuer's internal decision process (why was this node authorized?).
- The user's selection rationale (why did they choose this gateway?).
- Observed capability measurements (these are reputation-system data,
  not protocol data — their visibility depends on the reputation system
  design, which is out of scope for N2.4-02).

### 11.3 Correlation risk

Capability advertisements are signed by the node's Ed25519 key. This
means capability advertisements are linkable to the node's identity.
Multiple capabilities from the same node are correlatable. This is
acceptable — node identity is meant to be persistent and linkable.

## 12. Civic Points Separation

### 12.1 Explicit prohibition

```
CivicPoints >= X
    ⇒
INTERNET_GATEWAY authorized
```

This is **FORBIDDEN**. Economic balance MUST NOT determine cryptographic
authorization.

### 12.2 What Civic Points MAY influence

- Resource availability (a node with more points may allocate more bandwidth)
- User selection priority (a user may prefer high-point gateways)
- Reputation weight (a node with more points may be trusted more by users)

### 12.3 What Civic Points MAY NOT influence

- Cryptographic authorization (only an issuer signature authorizes)
- Routing security decisions (the protocol must work without Civic Points)
- Revocation (only the issuer can revoke)
- Replay protection (independent of economics)

### 12.4 Architectural invariant

```
Authorization
    ↓
independent security decision (issuer signature)

Civic Points
    ↓
economic/resource accounting (separate layer)
```

Economic incentives may influence **availability**, not **cryptographic
authority**.

## 13. Security Invariants

1. **No self-asserted capability authorizes privileged behavior.** A claim
   is a claim, not an authorization.

2. **Authorization requires an issuer signature.** The subject cannot
   self-authorize Tier 2 capabilities.

3. **Authorization is bounded by time.** Every authorization has an expiry.
   No permanent authorizations.

4. **Revocation is issuer-signed.** Only the issuer can revoke. The subject
   cannot revoke itself or refuse revocation.

5. **Stale state expires.** During partitions, expired authorizations
   become invalid automatically.

6. **Observations do not authorize.** Only issuer signatures authorize.
   Observed behavior informs user selection, not protocol authorization.

7. **Policy is a claim.** The protocol authenticates authorization, not
   policy honesty. Policy enforcement is application-layer.

8. **Economics ≠ authority.** Civic Points (or any economic mechanism)
   must not determine cryptographic authorization.

9. **Sybil resistance is tiered.** Tier 0/1 accept Sybil risk with
   mitigations. Tier 2 requires curated authorization.

10. **Capability types are separate.** Claim, authorization, policy,
    capacity, and observation are distinct concepts, not collapsed into
    one struct.

## 14. Threat Mitigations

| Threat (from N2.4-01) | Mitigated by | Status |
|----------------------|-------------|--------|
| Capability spoofing | Authorization required for Tier 2 | ✅ for Tier 2; 🔲 OPEN for Tier 0/1 |
| Capability authorization abuse | Issuer signature + revocation | ✅ CLOSED (Phase 1) |
| Capability policy violation | Policy is a claim; enforcement is application-layer | ⚠️ INHERENT RISK |
| Sybil route influence (Tier 2) | Curated authorization | ✅ CLOSED (Phase 1) |
| Sybil route influence (Tier 0/1) | N2.3 crypto mitigates forgery; quotas intended but deferred | ⚠️ ACCEPTED RISK (quota enforcement OPEN) |
| Sybil reputation gaming | Reputation is separate from authorization | ✅ CLOSED (separation) |
| Stale authorization during partition | Expiry bounds stale state window | PARTIALLY MITIGATED / BOUNDED RISK (revoked gateway may continue until expiry) |
| Revocation propagation delay | Short validity periods + expiry | PARTIALLY MITIGATED |

## 17. Implementation Boundaries

N2.4-02 defines the **architecture**. Implementation will produce:

- Rust types for `Capability`, `CapabilityClaim`, `CapabilityAuthorization`,
  `CapabilityPolicy`, `CapabilityCapacity`, `ObservedCapability`
- Authorization verification logic
- Revocation list management
- Capability advertisement in the discovery/topology protocol

Implementation is **blocked** until:
- N2.4-02 is approved
- N2.4-03 (Gateway Architecture) references N2.4-02's authorization model
- Conformance vectors are defined

---

## 18. Relationship to N2.3

N2.4-02 does NOT modify N2.3. The existing `Capability` enum in the
Rust reference (which currently has `Relay` and `Gateway`) remains as-is
for N2.3 compatibility. N2.4 will introduce the new capability taxonomy
as a separate type, with a migration path from the existing `Capability`
enum.

The existing `NodeAdvertisement` type (which carries capabilities) will be
extended, not replaced.
