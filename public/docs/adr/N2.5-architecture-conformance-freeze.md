# N2.5 — Architecture Conformance Freeze

**Status:** COMPLETE

**Parent:** N2.4-06 Mobile Node Lifecycle (approved)

**Baseline:** commit `f7bd6ec` (N2.4-I1 rev5)

---

## 1. Problem Statement

The repository at `f7bd6ec` is substantially farther along than the original
architecture handoff suggested. The network core (identity, discovery,
topology, progressive route discovery, distributed circuits, per-hop
encrypted traffic, capability authority) is **implemented and tested**.

However, the implementation has not been fully reconciled with the frozen
architecture. There are:

1. **Stale documentation** that contradicts the actual implementation
   (claims routing/gateways/circuits are unimplemented, claims TypeScript
   is authoritative, describes obsolete gateway-anchored routing).
2. **Two disconnected capability systems** — the legacy `Capability`
   (Client/Relay/Gateway) and the N2.4 `ProtocolCapability` (7 variants)
   with no bridge between them.
3. **No evidence-class separation** — routing/economic code cannot
   distinguish authenticated claims from reported metrics from derived
   metrics.
4. **Incomplete service negotiation** — `ServiceAgreement` is a typed stub
   with empty requirements.
5. **Gateway identity/service conflation** — `GatewayAdvertisement` mixes
   node identity with gateway service state.
6. **Missing conformance vectors** for N2.1.1.1 topology and route/circuit.
7. **No architecture guards** preventing regression to old semantics.

N2.5 is the **closure** milestone — not more architecture invention, but
making the existing implementation conform exactly to the frozen
architecture.

## 4. T2 — Capability Model Unification (COMPLETE)

### What was done

Extended the legacy `Capability` enum (`identity.rs`) from 3 variants
(Client/Relay/Gateway) to the full extensible set from the frozen
architecture:

```
Client (deprecated), Relay (deprecated), Gateway (deprecated),
MeshRelay, InternetGateway, ContentSeed, Storage, Discovery, Sync,
Compute, CryptoRelay, CryptoGateway, PaymentRelay
```

Added:
- `is_gateway_capability()` — recognizes Gateway + InternetGateway + CryptoGateway
- `is_relay_capability()` — recognizes Relay + MeshRelay + CryptoRelay
- `to_protocol_capability()` — bridges to the N2.4 authority-level
  `ProtocolCapability`

Updated all consumers:
- `VerifiedNodeAdvertisement::is_gateway()` / `is_relay()` — now use
  `is_gateway_capability()` / `is_relay_capability()` (covers all variants)
- `VerifiedNodeDescriptor::is_gateway()` / `is_relay()` — same
- `NodeAdvertisement::verify_into_verified()` role/key consistency —
  uses `is_gateway_capability()`
- `RemoteNodeHint::claims_gateway()` / `claims_relay()` — now use typed
  `Capability::from_str()` + `is_gateway_capability()` instead of raw
  string matching
- `commit_route()` capability-role binding — uses
  `is_gateway_capability()` / `is_relay_capability()`

### Relationship: NodeCapability vs GovernedAuthorityCapability

```
NodeAdvertisement
    ↓
NodeCapabilities (Capability enum — what services this node provides)
    ↓
optional: to_protocol_capability() bridge
    ↓
Governance/Authorization context (ProtocolCapability — authority-level)
```

The node-level `Capability` answers: **"What network service can this node
provide?"**

The authority-level `ProtocolCapability` answers: **"Under what trusted
authority/policy is this capability authorized or constrained?"**

### Exit criteria

- ✅ There is exactly one meaning for "this node has capability X" across
  advertisement, route discovery, gateway, governance, conformance, tests
- ✅ A node may advertise multiple capabilities simultaneously
- ✅ Old and new capability strings coexist (backward compatible)
- ✅ `RemoteNodeHint` no longer does raw string matching

### Tests

`reference/snp-node/tests/n25_capability_unification.rs` — 9 tests:
1. Legacy capability strings parse + round-trip
2. New capability strings parse + round-trip
3. Unknown capability string returns None
4. `is_gateway_capability()` covers all gateway variants
5. `is_relay_capability()` covers all relay variants
6. `to_protocol_capability()` bridge maps correctly
7. Node can advertise multiple capabilities
8. `RemoteNodeHint.claims_gateway()` recognizes all gateway variants
9. `RemoteNodeHint.claims_relay()` recognizes all relay variants

## 5. Remaining Tasks (T3–T9)

### T3 — Evidence-class separation

Create types for:
```
AuthenticatedClaim
ObservedMetric
ReportedMetric
DerivedMetric
InferredMetric
```

Apply to: `LinkMetrics`, `RouteMetrics`, `GatewayCapacity`,
`GatewayMeasurement`, `Topology`.

### T4 — Service/capability negotiation

Implement:
```
ServiceRequirement
CapabilityOffer
PolicyConstraint
CapacityConstraint
ServiceAgreement (enhanced)
```

The negotiation pipeline:
```
route candidate → service requirement → capability check →
policy check → capacity check → agreement → route proposal
```

### T5 — Gateway service state model

Refactor gateway-specific identity into:
```
AuthenticatedNodeRecord
    └── GatewayCapability
            └── GatewayServiceState
                   ├── Policy
                   ├── CapacityClaim
                   └── Measurement
```

### T6 — N2.1.1.1 conformance vectors

Frozen vectors for:
```
RemoteNodeHint, fake gateway, gateway_hints(), direct_gateways(),
PropagationSequence, replay, stale propagation, provenance,
hint → authenticated-record rejection
```

### T7 — Route/circuit conformance vectors

Frozen vectors for:
```
RouteProposal, RouteAcceptance, CommittedRoute, LinkAttestation,
distributed circuit setup, relay handshake, hop authorization,
traffic forwarding
```

### T9 — Architecture guards

Compile-time / lint checks preventing regression to old gateway/topology
semantics.

## 6. Exit Criteria for N2.5

N2.5 is complete when:

1. The spec matches the implementation (no contradictions)
2. There is one unified capability model
3. Evidence classes are explicit (no accidental self-reported-as-observed)
4. Service negotiation is real (not just typed strings)
5. Gateway service state is separate from node identity
6. N2.1.1.1 conformance vectors are frozen and consumed by tests
7. Route/circuit conformance vectors are frozen and consumed by tests
8. No stale documentation claims remain
9. Architecture guards prevent old semantics

---

## 7. What N2.5 is NOT

N2.5 is **not**:
- Implementing a real Internet gateway service (that's N2.8)
- Building a multi-process network harness (that's N2.9)
- Route recovery (that's N3.0)
- Android adapter (that's N3.3)

N2.5 is **closure** — making the existing implementation conform exactly
to the frozen architecture before any new features are built on top of it.
