# N3.0 — Route Recovery

**Status:** COMPLETE

**Parent:** N2.9 Contribution Proof Loop

**Baseline:** commit `9245055`

---

## 1. Problem Statement

N2.8 proved the Internet gateway thesis. But in a real mesh, gateways
disappear — links fail, volunteers turn off their devices, advertisements
expire. An active client must survive gateway failure by establishing a
new route through a replacement gateway.

N3.0 implements the route failure/recovery pipeline:
```
Gateway A disappears
    → detect failure
    → invalidate route
    → find replacement gateway
    → new circuit via Gateway B
```

## 2. What Changed

### 2.1 RouteFailureDetector

New module: `reference/snp-node/src/node/route_recovery.rs`

Detects route failure based on observed metrics (Evidence level: Observed):
- **Link down** — immediate failure when the gateway's link goes Down.
- **Repeated failures** — N consecutive transit request failures (default 3).
- **Advertisement expired** — gateway's advertisement has expired.

`record_success()` resets the consecutive failure count.

### 2.2 RouteRecoveryManager

Manages the recovery pipeline:
1. **Detect** — `RouteFailureDetector` detects the failure.
2. **Invalidate** — the route is declared failed.
3. **Find replacement** — query alternative gateways registered with the manager.
4. **Select** — pick the first available alternative (production would use
   health/capacity-based selection).
5. **Recover** — return a `RecoveryResult` with the replacement gateway.

### 2.3 RecoveryResult

Records:
- `failed_gateway` — the NodeId of the gateway that failed.
- `replacement_gateway` — the NodeId of the replacement.
- `failure_reason` — why the original failed (LinkDown, AdvertisementExpired,
  RepeatedFailures).
- `recovered_at` — when recovery was performed.
