# ADR-0001 — TypeScript as reference implementation language (sandbox)

## Context

`07-MIGRATION-AND-ROADMAP.md` §3 ("Recommended repository structure")
specifies the reference implementation as **Rust on Linux**:

> `reference/` is Rust on Linux — no platform obstacles, so protocol
> bugs surface as protocol bugs.

The architecture's reasoning is sound: Rust/Linux has no platform
obstacles, no SDK surprises, no managed-runtime timing weirdness, and a
single-language reference avoids the Kotlin/Python divergence that the
audit (§3.2) found. The conformance bootstrapping order (06 §B9) makes
the reference implementation the *second* step after spec + vectors,
owned by Z.ai, in Rust.

**The problem this ADR addresses:** this sandbox runs Next.js 16 +
TypeScript. There is no Rust toolchain, no Linux daemon target, no
`reference/` Rust crate scaffold. The sandbox is the environment
available *now*, and the conformance foundation (N0/N1) is the
critical-path deliverable that blocks every downstream agent. Waiting
for a Rust environment would mean either (a) not starting N0/N1 until a
Rust toolchain is provisioned, or (b) starting N0/N1 in TypeScript and
porting later.

The audit's central lesson (06 §A1, 00-AUDIT.md §3.3) is that **prose
did not constrain the implementation; executable vectors would have.**
The constraint that matters is the *vectors*, not the language they are
generated in. Vectors are language-independent JSON. A signature made
by `@noble/ed25519` in TypeScript and a signature made by
`ed25519-dalek` in Rust both verify against the same RFC 8032 test
vector (`ed25519-rfc8032-test1-verify` in `03-identity.json`). If they
did not, one of them would be wrong — and that is exactly what the
conformance suite exists to catch.

## Decision

**TypeScript is the reference language *in this sandbox*.** The
conformance vectors in `public/conformance/vectors/*.json` are
authoritative: they are generated by the TypeScript reference
(`snp-typescript-reference`, per each file's `generatedBy` field) and
committed. Other implementations (Kotlin, Python, Rust, Swift) consume
the vectors and may never regenerate them.

**Production reference remains Rust**, per 07-MIGRATION-AND-ROADMAP.md
§3. When a Rust reference exists, it MUST regenerate the vectors from
Rust and the TypeScript vectors MUST match byte-for-byte. If they do
not match, the Rust reference is wrong (Tier 0 beats Tier 3) and is
fixed; the TypeScript vectors are not silently overwritten.

This ADR does **not** change `07-MIGRATION-AND-ROADMAP.md` §3. It
documents a sandbox deviation and pins the production path.

## Rationale

- **The constraint is the vectors, not the language.** 06 §A3 defines
  the vector format as language-independent JSON. 06 §A2 specifies
  "exactly one generator" — that generator is, for now, TypeScript. The
  rule being enforced is "one generator," not "the generator is Rust."
- **The critical path is N0/N1.** 06 §B9: "No implementation work
  begins before step 1 is complete." Step 1 is spec + vectors + ADR
  process. Blocking step 1 on a Rust toolchain would delay every
  downstream agent (Gemini/Android, future iOS, etc.) for an
  environmental reason, not a protocol reason.
- **The crypto is real, not stubbed.** `@noble/ed25519`, `@noble/curves`
  (X25519), and `@noble/hashes` (SHA-256, HKDF-SHA256) are vetted,
  audited pure-TypeScript implementations. RFC 8032 §7.1 Test 1 passes
  (`ed25519-rfc8032-test1-verify`); RFC 5869 Test Case 1 passes
  (`hkdf-sha256-rfc5869-test1`). See ADR-0002 for the full rationale.
- **CBOR is hand-rolled but pinned by vectors.** The SNP-CBOR encoder
  (`src/lib/snp/cbor.ts`) is a hand-written canonical-CBOR encoder.
  Suite 01 (`01-cbor.json`, 18 vectors) and Suite 14
  (`14-negative.json`, 4 CBOR MUST-REJECT vectors) pin its output
  byte-for-byte. Any deviation from RFC 8949 §4.2.1 is a CI failure,
  not a silent drift.
- **Tier 2 is the right tier.** The decision sits at Tier 2 (API
  contract) because the *reference status* of the TypeScript
  implementation affects which language's output defines Tier 0 truth.
  The language itself is Tier 3 (free choice); the *authoritative
  generator* designation is Tier 2. A Rust reference can supersede this
  ADR (status → `superseded`) without violating any invariant.

## Alternatives considered

### (a) Wait for a Rust environment before starting N0/N1

**Rejected.** The audit (06 §A1) shows what waiting produced: a
repository with placeholder vectors (`sha256("cbor-manifest-0")`),
all-zero signatures, and a README claiming byte-identical golden
vectors that did not exist. The conformance foundation is the fix for
that failure mode; delaying it for environmental reasons reintroduces
the exact failure mode it exists to prevent.

**Revisit when:** a Rust toolchain is provisioned in this sandbox, or a
separate Rust CI environment is available.

### (b) Port to Rust later — accepted as the production path

**Accepted.** When a Rust reference exists:

1. Regenerate every vector from Rust (`01-cbor.json` through
   `14-negative.json`, 14 files, ~130 vectors).
2. Diff against the TypeScript-generated vectors.
3. If they match: update each file's `generatedBy` field from
   `snp-typescript-reference` to `snp-rust-reference`, supersede this
   ADR.
4. If they do not match: the Rust implementation is wrong (Tier 0
   beats Tier 3). Fix the Rust implementation. Do not silently
   overwrite the TypeScript vectors — file an ADR documenting the
   discrepancy and which side was wrong.

The TypeScript implementation is preserved as a runnable reference for
the dashboard / Next.js sandbox, but loses "authoritative generator"
status.

### (c) Hand the reference to a third party (e.g. Gemini/Kotlin)

**Rejected.** 06 §B5 assigns the reference to Z.ai specifically because
"the reference implementation must be built by one agent in one
language to avoid the divergence the audit found." Handing it to the
Android owner would re-create the Kotlin/Python split. The reference
stays with Z.ai; only the language changes (TypeScript now, Rust
later).

## Conformance impact

**None.** The vectors are language-independent JSON. Every vector file
in `public/conformance/vectors/` carries:

```json
{
  "generatedBy": "snp-typescript-reference",
  "generatedAt": "2026-08-11T..."
}
```

When a Rust reference exists, the only field that changes is
`generatedBy`. The `expected` payloads (`cborHex`, `hashHex`,
`nodeIdHex`, `rootHex`, `verifies`, etc.) MUST be byte-identical. If
they are not, file an ADR — do not edit the vector.

Vectors affected by this ADR: **all 14 suites, ~130 vectors** — but
only the `generatedBy` field. No `expected` payload changes.

Suites in scope:

- `01-cbor.json` (19 vectors) — SNP-CBOR canonical encoding.
- `02-hashing.json` (17 vectors) — SHA-256, HKDF-SHA256, NodeId
  derivation, all 12 `SIG_CONTEXT` domain separators, Merkle empty
  root.
- `03-identity.json` (7 vectors) — Ed25519 sign/verify, remote-key
  verification, cross-context rejection, four-way identity split.
- `04-chunking.json` (6 vectors) — Gear table, boundary cases, 5 MiB
  deterministic stream.
- `05-merkle.json` (12 vectors) — RFC 6962, 1/2/3/5/8 leaves, proofs,
  empty, odd-count non-duplication.
- `06-manifest.json` (3 vectors) — sign/verify, tamper rejection,
  `chunkCount` binding.
- `07-receipts.json` (5 vectors) — delivery, transit, gateway,
  custody, cross-type replay rejection.
- `08-frames.json` (13 vectors) — encode/decode, TTL decrement, TTL=0
  drop, class A/B/C, padding buckets.
- `09-descriptors.json` (3 vectors) — NodeDescriptor, GatewayAdvert,
  iOS/MESH_RELAY rejection.
- `10-routing.json` (4 vectors) — RouteAdvert sign/verify, loop
  detection, seq regression, gateway migration.
- `11-gateway.json` (19 vectors) — Mode A TransitRequest/Response, 12
  RFC 1918/loopback/link-local/multicast rejections, 4 public
  allow-list, mandatory `tlsTermination`, mode-A-without-tls rejection.
- `12-civic-points.json` (5 vectors) — sub-linear volume factor,
  value computation, diversity collapse, holdback, scarcity.
- `13-revocation.json` (3 vectors) — monotone un-revoke rejection,
  CRITICAL priority, seq monotonicity.
- `14-negative.json` (14 vectors) — every MUST-REJECT in the spec.

## Migration path

**To a Rust reference (future):**

1. Provision a Rust toolchain (stable ≥ 1.75, `ed25519-dalek`,
   `x25519-dalek`, `sha2`, `hkdf`, `cbor`/`ciborium` with custom
   canonical encoding, `rand_core`).
2. Implement `snp-cbor`, `snp-crypto`, `snp-identity`, `snp-object`,
   `snp-link`, `snp-routing`, `snp-gateway`, `snp-civic` crates per
   07-MIGRATION-AND-ROADMAP.md §3.
3. Write a Rust vector generator that produces the same JSON shape as
   the TypeScript generator.
4. Run both generators; diff the `expected` payloads.
5. Resolve discrepancies by filing an ADR per mismatch (the Rust side
   is presumed wrong; if the TypeScript side is wrong, the ADR
   documents the bug fix).
6. Once all 14 suites match byte-for-byte, flip `generatedBy` to
   `snp-rust-reference` and supersede this ADR.

**Rollback:** if the Rust reference cannot match the TypeScript vectors
within a reasonable effort, the TypeScript reference remains
authoritative. This is not a failure — it is the Tier 0/3 conflict
resolution working as designed. The cost is that the architecture's
"Rust on Linux" recommendation is not yet realised; the conformance
foundation is still sound.

**Interop during transition:** the Kotlin/Android port (Gemini) and any
Python port consume the JSON vectors. They do not care which language
generated them. The transition from TypeScript to Rust is invisible to
consumers as long as the `expected` payloads do not change.

## Consequences

### Positive

- N0/N1 (spec + conformance foundation) starts immediately, on the
  available environment, without blocking on a Rust toolchain.
- The full conformance suite (14 suites, ~130 vectors) exists today and
  is exercised by the integration-tests API route (`/api/integration-tests`).
- Every downstream agent (Gemini/Android, future iOS, future Rust
  reference) has a concrete, executable spec to implement against.
- The audit's "prose did not constrain the implementation" failure
  mode is closed: any disagreement with a vector is a CI failure,
  regardless of language.

### Negative

- The architecture's stated "Rust on Linux" reference is not what this
  sandbox ships. This ADR documents the deviation, but the deviation
  exists.
- A hand-rolled CBOR encoder in TypeScript is a maintenance surface
  that a Rust `ciborium`-based encoder would not be. Mitigated by
  Suite 01 + Suite 14 vectors pinning the output byte-for-byte.
- The simplified Noise_IK (ADR-0003) and the absence of post-handshake
  AEAD in `EstablishedLink` are both consequences of the TypeScript
  sandbox not having a vetted Noise library readily available. A Rust
  reference would use `snow` or `noise-rust` and close both gaps
  cleanly. See ADR-0003 for the human-review gate.
- Future Rust engineers must treat the TypeScript vectors as
  authoritative truth during porting, which is psychologically
  awkward ("this other language's output defines my correctness") even
  though it is mechanically correct.

### Neutral

- The `generatedBy` field in every vector file records the originating
  language. Future archaeologists will see `snp-typescript-reference`
  and know to consult this ADR.
