# N2.5.1 — Architecture Freeze Declaration

**Status:** FROZEN — DO NOT MODIFY

**Parent:** N2.5 Architecture Conformance Freeze (complete)

**Baseline:** commit `39dee10`

---

## 1. Purpose

This ADR declares that the following N2.5 architecture semantics are
**frozen** and cannot change without a new ADR (N2.6 or later).

Any change to the frozen semantics listed below is a **protocol break** and
requires:

1. A new ADR documenting the change
2. Regeneration of all affected conformance vectors
3. Verification that all implementations (Rust, Kotlin, Python, Swift)
   agree on the new semantics

---

## 2. Frozen Semantics

### 2.1 Capability Model (frozen)

The `Capability` enum variants and their string representations are frozen:

| Variant | String | Gateway? | Relay? |
|---------|--------|----------|--------|
| `Client` | `"client"` | no | no |
| `Relay` | `"relay"` | no | yes |
| `Gateway` | `"gateway"` | yes | no |
| `MeshRelay` | `"mesh-relay"` | no | yes |
| `InternetGateway` | `"internet-gateway"` | yes | no |
| `ContentSeed` | `"content-seed"` | no | no |
| `Storage` | `"storage"` | no | no |
| `Discovery` | `"discovery"` | no | no |
| `Sync` | `"sync"` | no | no |
| `Compute` | `"compute"` | no | no |
| `CryptoRelay` | `"crypto-relay"` | no | yes |
| `CryptoGateway` | `"crypto-gateway"` | yes | no |
| `PaymentRelay` | `"payment-relay"` | no | no |

The `to_protocol_capability()` bridge mapping is frozen:

| Node Capability | ProtocolCapability |
|----------------|-------------------|

| Discovery | Discovery (1) |
| Sync | Sync (2) |
| Compute | Compute (6) |
| PaymentRelay | None |

### 2.2 Evidence Model (frozen)

The five evidence levels and their trust classifications are frozen:

| Level | `is_routing_evidence()` | `is_untrusted()` |
|-------|------------------------|------------------|
| `Authenticated` | true | false |
| `Observed` | true | false |
| `Reported` | false | true |
| `Derived` | false | false |
| `Inferred` | false | true |

### 2.3 Topology Model (frozen)

- `RemoteNodeHint` ≠ `AuthenticatedNodeRecord` — a remote claim can never
  become an authenticated record without a verified advertisement.
- `direct_gateways()` returns `Vec<&AuthenticatedNodeRecord>` — authenticated + reachable.
- `gateway_hints()` returns `Vec<&RemoteNodeHint>` — non-authoritative claims.
- There is NO `all_known_gateways()` that conflates the two.
- `PropagationSequence` is monotonic per-sender; equal/lower sequences are rejected.

### 2.4 Route Model (frozen)

- `RouteProposal` ≠ `CommittedRoute` — commitment requires participant acceptances.
- `commit_route()` checks: proposal signature, path↔proposal match, structural
  validity, capability↔role binding, required participants, acceptance signatures,
  acceptance proposal-hash match, role match, no duplicates, complete acceptance set.
- Acceptance order does NOT affect the commitment (canonical sorting by NodeId).
- Changing acceptance conditions changes the commitment.

### 2.5 Gateway Service Model (frozen)

- `GatewayServiceState` is separate from `NodeAdvertisement` (static identity).
- `GatewayPolicy` is an `AuthenticatedClaim` (signed by gateway operator).
- `GatewayCapacityClaim` is a `ReportedMetric` (untrusted gateway claim).
- `GatewayMeasurement` is an `ObservedMetric` (measured by this node).
- Changing remaining_quota, bandwidth, or queue_depth does NOT require changing
  the node's cryptographic identity.

### 2.6 Service Negotiation (frozen)

- `ServiceRequirement.is_satisfied_by(offer, policy, capacity)` checks:
  capability match, destination allowed, protocol allowed, bandwidth, latency.
- `NegotiatedServiceAgreement::negotiate()` returns `None` if the requirement
  is not satisfied — a route cannot be committed without a valid agreement.

### 2.7 Capability Authority (frozen — from N2.4-I1 rev5)

- `verify_authorization()` enforces `IssuerStatus::Active` (Step 0).
- `SubjectCapabilityRevocation` is bound to exact `issuer_authority_version` + `issuer_authority_digest`.
- Persistence is durable (fsync temp + rename + fsync parent dir).
- Post-rename durability failure enters `FailedClosed` state.
- Semantic validation runs on construction, acceptance, and load.

## 3. Frozen Conformance Vectors

The following vector file is frozen and consumed by the cross-platform
conformance runner:

```
public/conformance/vectors/16-capability-authority.json
```

This file contains 17 vectors across 2 suites:

### Suite: capability-authority (4 vectors)

| ID | Object | What's verified |
|----|--------|-----------------|
| `issuer-authority-v1` | IssuerAuthority | CBOR round-trip + governance signature + authority digest |
| `capability-authorization-v1` | CapabilityAuthorization | Signing preimage + issuer signature |
| `governance-issuer-revocation-v1` | GovernanceIssuerRevocation | CBOR round-trip + governance signature + revocation digest |
| `subject-capability-revocation-v1` | SubjectCapabilityRevocation | CBOR round-trip + issuer signature + revocation digest (authority-version bound) |

### Suite: capability-model (13 vectors)

One vector per `Capability` variant, verifying:
- String round-trip (`as_str()` / `from_str()`)
- `is_gateway_capability()` classification
- `is_relay_capability()` classification
- `to_protocol_capability()` bridge mapping

## 4. Cross-Platform Agreement Contract

The frozen vectors are **language-independent serialized artifacts**. Any
implementation (Rust, Kotlin, Python, Swift) that loads the vector file
must produce identical results:

```
Given: cbor_hex + signer_public_key_hex + signature_hex + preimage_hex
Check: ed25519_verify(signer_pk, preimage, signature) == true
Check: sha256(cbor_bytes) == expected_digest
Check: encode(decode(cbor_bytes)) == cbor_bytes  (canonical CBOR)
```

A Rust conformance runner is at:
`reference/snp-node/tests/n251_conformance_runner.rs`

Future Kotlin/Python/Swift runners MUST consume the SAME vector file and
produce the SAME pass/fail results.

---

## 5. What Cannot Change Without a New ADR

1. **Capability variant names** (the 13 strings above)
2. **Evidence level classifications** (is_routing_evidence / is_untrusted)
3. **Topology separation** (RemoteNodeHint ≠ AuthenticatedNodeRecord)
4. **Route commitment semantics** (proposal ≠ commitment, acceptance order independence)
5. **Gateway service state separation** (identity ≠ service state)
6. **Service negotiation pipeline** (requirement → offer → policy → capacity → agreement)
7. **Capability authority verification algorithm** (the 12-step verify_authorization)
8. **Persistence durability model** (commit-point, FailedClosed)
9. **Conformance vector file format** (protocol_version, input, expected)

---

## 6. What CAN Change

1. **Adding new Capability variants** (additive, not breaking — old strings still parse)
2. **Adding new evidence subtypes** (additive)
3. **Adding new vector suites** (additive)
4. **Implementation details** (as long as the frozen semantics are preserved)
5. **Performance optimizations** (as long as the canonical encoding is unchanged)

---

## 7. Freeze Enforcement

The architecture guards at:
`reference/snp-node/tests/n25_architecture_guards.rs`

verify that the frozen types and methods exist at compile time. If someone
removes a module or reverts a semantic, the guards fail to compile.

The conformance runner at:
`reference/snp-node/tests/n251_conformance_runner.rs`

verifies that the frozen vectors produce the expected byte-level results.
If someone changes the canonical encoding, the runner fails.

Together, these two test files enforce the freeze.
